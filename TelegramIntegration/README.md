# Telegram AI coding bridge

Однопользовательский Telegram-интерфейс к локальному Codex App Server или Claude Code CLI. Каждый владелец запускает отдельный экземпляр со своим Telegram-ботом, AI-аккаунтом и рабочей папкой.

## Требования

- Node.js 20 или новее;
- установленный и авторизованный Codex CLI либо Claude Code CLI;
- Python 3.10 или новее — только для распознавания и синтеза голосовых сообщений.

## Установка

Создайте бота через `@BotFather`, узнайте свой числовой Telegram user ID, затем выполните из этой папки:

```powershell
python install.py
npm run doctor
npm start
```

Установщик создаёт изолированный runtime в `%LOCALAPPDATA%\Tyrael\TelegramIntegration` (в Linux — под `$XDG_STATE_HOME`). Там хранятся конфигурация с токеном, runtime-state и версионные копии исполняемого бота; в рабочей папке остаются только исходники и тесты. Для голосовых сообщений используйте:

```powershell
python install.py --install-voice
```

Для миграции существующей установки или публикации новой версии выполните:

```powershell
npm run runtime:deploy
npm run runtime:activate
npm run doctor
```

`runtime:deploy` создаёт новый неизменяемый release и атомарно переключает `current.json`, сохраняя предыдущую версию для `npm run runtime:rollback`. Команда `runtime:activate` один раз переносит конфигурацию, данные и модели из рабочей папки во внешний runtime, создаёт маркер активации и удаляет старый workspace-`config.json`. Выполняйте её только при остановленном старом боте; для живой установки сначала дождитесь завершения ходов.

Текущий runtime можно проверить через `npm run runtime:status`. После активации `/restart` запускает release, указанный в `current.json`, поэтому новая публикация начинает действовать при следующем штатном рестарте. Автозапуск Windows также указывает на внешний launcher. В Windows фоновый запуск проходит через GUI-хост `wscript.exe` и `launch.vbs`, поэтому бот не создаёт окно PowerShell или вкладку Windows Terminal.

Для ручной настройки используйте `%LOCALAPPDATA%\Tyrael\TelegramIntegration\config.json`. Путь к другому конфигу можно передать через `TELEGRAM_CODEX_CONFIG`, а токен — через `TELEGRAM_BOT_TOKEN`.

После активации workspace-команды `send-message.mjs` и `send-images.mjs` не читают Telegram-токен. Они передают только разрешённую операцию, аргументы и идентификатор вызывающей AI-сессии в локальный IPC живого runtime; уже доверенная release-копия выполняет отправку. Произвольные команды и переменные с секретами IPC не принимает.

### Отправка сообщения из скрипта

Отдельный процесс может отправить владельцу сообщение через локальный IPC того же бота:

```powershell
node send-message.mjs "Обработка завершена"
```

То же через npm:

```powershell
npm run send -- "Обработка завершена"
```

Текст можно передать через stdin; для нескольких разрешённых чатов укажите `--chat-id <id>`. Параметр `--silent` отправляет уведомление без звука. Скрипт делит текст длиннее лимита Telegram на несколько сообщений и не выводит токен в командную строку или журнал.

Из Windows PowerShell 5.1, фонового watcher или `.ps1` с русским текстом безопаснее передавать сообщение через UTF-8-файл. Это не даёт PowerShell перекодировать кириллицу в аргументах запуска:

```powershell
Set-Content -LiteralPath notification.txt -Encoding UTF8 -Value "Обработка завершена"
node send-message.mjs --bind-current --category done --message-file notification.txt
```

`--message-file` взаимоисключаем с текстом в командной строке. Отправщик также отклоняет текст, похожий на повреждённый UTF-8 (`РўСЂ...`), вместо публикации битого уведомления.

Чтобы ответ на уведомление автоматически вернул бота к текущей задаче, отправьте его с привязкой:

```powershell
node send-message.mjs --bind-current --category action "Нужен ваш ответ"
```

`--bind-current` определяет вызывающую AI-сессию по точному идентификатору: `CODEX_THREAD_ID` для Codex или `CLAUDE_CODE_SESSION_ID` для Claude Code. Он не использует выбранную в боте задачу как неявный fallback: если идентификатора вызывающей сессии нет, отправка завершается ошибкой до обращения к Telegram. Это исключает привязку уведомления из VS Code/CLI к чужой задаче, оставшейся активной в `data/state.json`.

Если требуется осознанно привязать сообщение именно к задаче, выбранной сейчас в Telegram-боте, используйте отдельный параметр:

```powershell
node send-message.mjs --bind-active --category info "Сообщение для активной задачи бота"
```

Привязанное уведомление отправляется как тонкая медиа-карточка фиксированного размера: PNG-баннер показывает категорию, а подпись — жирное название текущей задачи с одним `🧵` слева и текст. Кнопка `👀 Показать сообщение` прикреплена к этой же карточке: она выбирает привязанный thread и показывает текущий ход либо последний полный ответ. Исходники и воспроизводимый генератор баннеров находятся в `assets/notification-cards`. Поддерживаются категории:

- `action` — `ТРЕБУЕТСЯ ДЕЙСТВИЕ`;
- `done` — `ЗАДАЧА ВЫПОЛНЕНА`;
- `intermediate` — `ПРОМЕЖУТОЧНЫЙ РЕЗУЛЬТАТ`;
- `progress` — `ЗАДАЧА ВЫПОЛНЯЕТСЯ`;
- `warning` — `ВНИМАНИЕ`;
- `info` — `ИНФОРМАЦИЯ` (по умолчанию).

Если Telegram временно не принимает PNG, `send-message.mjs` автоматически отправляет прежнее текстовое оформление, поэтому важное уведомление не теряется.

`done` используется только после полного завершения всей задачи, когда больше не осталось работы и агент заканчивает ход. `action` означает, что дальнейшая безопасная работа действительно невозможна без ответа или действия пользователя. Для существенного готового этапа, после которого работа продолжается, используется `intermediate`; для обычного текущего состояния — `progress`; для риска или отклонения, ещё не требующего вмешательства, — `warning`. Нейтральные сообщения, не подходящие ни под одну специальную категорию, отправляются как `info`.

Например, полное завершение задачи отправляется командой `node send-message.mjs --bind-current --category done "Обработка завершена"`. Переключение выполняется при Telegram-действии «Ответить» или по кнопке показа. Простое новое сообщение и ответ на уведомление, отправленное без `--bind-current` или `--bind-active`, текущую задачу не меняют. Если другая задача выполняется, бот не прерывает её автоматически. При фактической смене бот присылает заголовок `Текущая задача изменена`. Если `showProjectButton` включён, ниже выводятся жирное имя проекта и курсивное название задачи; если выключен — только жирное название задачи. Служебное сообщение прогресса и итоговый ответ, отправленные самим ботом, тоже получают привязку к породившей их задаче.

### Скриншоты кода

Для переписки с телефона фрагмент исходника можно отрендерить в читаемые PNG. Длинный диапазон автоматически разбивается на несколько изображений:

```powershell
python render-code-images.py `
  "C:\Projects\App\Module.bsl" `
  "C:\Projects\App\WIP\code-images" `
  --start 190 --end 260 `
  --title "Копирование коллекций"
```

Готовые PNG отправляются одним изображением или Telegram-альбомом. Привязка работает так же, как у `send-message.mjs`, поэтому ответ на картинку возвращается в правильную задачу:

```powershell
node send-images.mjs --bind-current --caption "Код после правки" `
  "C:\Projects\App\WIP\code-images\Module-190-234.png" `
  "C:\Projects\App\WIP\code-images\Module-235-260.png"
```

Поддерживается до десяти PNG в одном альбоме. `--bind-active` намеренно привязывает изображения к выбранной в боте задаче, `--silent` отключает уведомление. Для рендеринга используется Pillow из `requirements.txt`.

Кнопка `Показать сообщение` не создаёт новый ход. Она перерисовывает компактное представление выбранной задачи: удаляет доступные боту сообщения этой задачи из Telegram, сверху создаёт навигацию истории, затем показывает последнюю пару `👤 Вы` → `🤖 агент` и создаёт новую живую progress-карточку последней в чате. Старый ID progress-сообщения одновременно отсоединяется от run, поэтому обновления не продолжают уходить в карточку выше истории. Для запущенной ботом задачи используется тот же run. Для внешнего Codex бот читает текущий turn через App Server, а для внешнего Claude — локальный transcript соответствующего `session_id`; сообщение продолжает обновляться до завершения. Выбранная задача дополнительно проверяется автоматически: если ход запущен из VSCode/CLI, бот молча подключает observer, обновляет локальный статус и блокирует параллельный turn, но не отправляет progress-карточку без запроса. Живое представление появляется только после `Показать сообщение`; итоговый ответ после завершения по-прежнему доставляется. Если активного хода нет, показывается полный последний ответ. Если ни хода, ни ответа найти нельзя, бот сообщает об этом и не подставляет данные другой задачи.

Кнопка `👀 Показать ещё` расположена в первом сообщении компактного представления, то есть визуально выше показанной переписки. Каждое нажатие добавляет ровно одну пару: `1 → 2 → 3 → 4…`. Telegram не позволяет вставлять новые сообщения задним числом, поэтому при догрузке бот удаляет текущее представление и строит его заново с большим числом пар в хронологическом порядке. Источником истории остаются локальные треды Codex и transcript Claude; удаление Telegram-сообщений историю агента не затрагивает.

В личном чате бот может удалять как исходящие, так и входящие пользовательские сообщения моложе 48 часов. Новые входящие тексты, изображения и голосовые сообщения привязываются к задаче, чтобы при следующем открытии убрать оригинал и показать его как `👤 Вы`. Сообщения старше ограничения Telegram и старые пользовательские сообщения, ID которых бот ещё не сохранял, автоматически удалить нельзя. Незакрытые запросы разрешения с кнопками сохраняются.

## Что изменено в текущей версии

### Потоковый ход выполнения

- Codex обрабатывает `agentMessage`, доступное резюме анализа, план, команды, изменения файлов и вызовы MCP по мере поступления событий App Server.
- Claude Code запускается с `stream-json --verbose --include-partial-messages`; текст, инструменты, повторные API-запросы и `session_id` доступны до завершения процесса.
- Для задачи дольше трёх секунд бот создаёт одно служебное сообщение и редактирует его не чаще одного раза в 1,5 секунды. В первой строке компактного заголовка указаны агент, модель и reasoning; проект добавляется только при включённой кнопке проекта. Во второй строке указано название задачи, отдельной строкой — владелец выполнения: `VSCode App Server`, `Integration App Server`, `Codex Desktop App` или `Codex CLI`. В коротких кнопках списка используются соответственно `VSC`, `INT`, `APP` и `CLI`. Короткие ответы приходят сразу одним итоговым сообщением без лишнего «Задача принята».
- Heartbeat различает доступность потока и реальную работу: зелёный статус показывается только при свежих событиях, а после двух минут без новых событий появляется оранжевое предупреждение с длительностью простоя. Успешный `thread/read` сам по себе больше не изображает продвижение задачи.
- После завершения служебное сообщение сворачивается до краткого статуса, а полный ответ отправляется отдельно. Бот берёт именно `final_answer` завершённого Codex-turn, а если итог ещё не появился в снимке — повторно перечитывает turn перед доставкой; промежуточные commentary не подменяют итоговый ответ.

### Несколько задач одновременно

- Выбранная задача — только адрес для следующего обычного сообщения. Она не является глобальной блокировкой бота.
- Пока одна задача выполняется локально, через `/tasks`, `/projects`, `/agent` или ответ на привязанное сообщение можно выбрать другую и запустить её. Работа первой продолжится в фоне.
- Реестр запуска хранит отдельно для каждого `проект + агент + thread/session`: процесс или turn, прогресс, ответ, временные файлы и последний diff.
- Исполнитель у каждого хода только один. Если turn уже выполняется через `VSCode App Server`, Telegram подключает наблюдение и сохраняет новое сообщение для выбора действия или очереди, но не запускает параллельный turn. Ход, начатый Telegram, помечается `Integration App Server`. Штатная панель VSCode не читает lock бота, поэтому жёсткая блокировка гарантируется со стороны Telegram; обнаруженный встречный VSCode-ход всё равно сразу попадает в локальный реестр и становится наблюдаемым.
- `/tasks` строится заново из локального каталога Codex и файлов сессий Claude, поэтому показывает задачи обоих агентов во всех разрешённых папках, а не только уже открывавшиеся через бота. Индекс названий Codex читается один раз на обновление каталога, а увеличившиеся rollout-файлы разбираются только с последней сохранённой позиции. Список разбит на страницы; выполняющиеся задачи отмечены символом `⏳`. Команда `/rename <название>` переименовывает и закрепляет текущую задачу по её `provider + threadId`; последующие автоматически сгенерированные заголовки Codex не меняют это имя в боте.
- `/status` отправляется как прямоугольная карточка 3:1 с логотипом выбранного агента. Для каждого показа случайно выбирается одна из семи синих шапок Codex или семи терракотовых шапок Claude; если одновременно активны задачи обоих агентов, используется одна из трёх совместных шапок. Первая строка показывает агента, модель и reasoning, вторая — режим и состояние. Каталог выводится только при включённой кнопке проекта. Карточка показывает число выполняющихся задач без дублирования их названий в тексте. Если такие задачи есть, после лимитов появляется заголовок `🧵АКТИВНЫЕ ЗАДАЧИ🧵` и отдельные кнопки: выбранная помечена `✅ ТЕКУЩАЯ`, нажатие на другую сразу выбирает её агент, проект и thread/session. Запуски самого бота определяются точно; для внешнего Codex бот сопоставляет lifecycle-события свежего rollout (`task_started`/`task_complete`/`turn_aborted`) по `turn_id`, поэтому завершение или остановка параллельного хода не скрывает другой продолжающийся ход. Для внешнего Claude используется незавершённая сессия со свежим transcript: у Claude нет живого App Server, поэтому незакрытый transcript считается выполняющимся ходом только пока обновлялся в последние 30 минут. Один и тот же признак свежести применяется в каталоге, при наблюдении и при проверке занятости перед отправкой сообщения, поэтому брошенная сессия не блокирует новый ход, а зависшее наблюдение снимается само. Это эвристика только для внешнего Claude: действительно работающая команда, которая не пишет transcript более 30 минут, временно выглядит остановленной. Для Claude, запущенного самим ботом, используется PID и такого таймаута нет. После подтверждённой отмены управляемого Claude-процесса бот запоминает снимок его transcript и не воскрешает незавершённый хвост как внешний ход; новая реальная активность или следующий запуск в этой сессии снимают отметку.
- `/cancel` останавливает только выбранную задачу. Для подключённого внешнего хода бот отключает observer и запоминает это состояние, поэтому наблюдение не подключается повторно само. Пока внешний ход действительно выполняется, новый запрос в тот же thread/session всё равно не запускается; повторное подключение доступно через `Показать сообщение`. Другие запуски продолжаются.
- Два агента могут одновременно работать в одном проекте без отдельного предупреждения о возможном конфликте файлов. Перед обычным сообщением бот повторно проверяет выбранный thread/session и не запускает в нём второй параллельный ход.
- Если выбранная задача уже выполняется, новый текст, голосовая расшифровка или изображение не теряются и не подменяются текущим прогрессом. Бот сохраняет вход и предлагает четыре действия: отправить в новую задачу, поставить в очередь исходной задачи, показать текущий ход или отменить сообщение. Очередь запускается автоматически после завершения занятого хода; сохранённые и поставленные в очередь входы переживают перезапуск бота.
- Все привязанные уведомления и сообщения о смене задачи используют единый контракт кнопки `👀 Показать сообщение`: она выбирает именно привязанный `проект + агент + thread/session`, подключает его текущий живой ход и показывает актуальный прогресс. Если ход уже завершён, показывается его последний полный ответ. Старый callback `show-last-message` поддерживается для ранее отправленных Telegram-сообщений и работает так же. Переключение представления не останавливает фоновые задачи и не запускает дополнительный ход. Если переключение выполнено самой кнопкой показа, новое уведомление о переключении отправляется без кнопки, чтобы не создавать рекурсивную цепочку.

### Сохранение и восстановление задач

- Активный запуск сохраняется в `data/state.json`: агент, проект, `threadId`/`session_id`, `turnId`, время запуска, ID служебного Telegram-сообщения и уже полученная часть ответа.
- Общий локальный индекс `data/task-sync.json` синхронизирует между независимыми интерфейсами каталог, историю, фактический статус, `turnId`, владельца App Server, последний этап и текст выбранной задачи. Для Codex источником истины остаются локальные thread/rollout-файлы, для Claude — transcript. Индекс является безопасным кэшем: если отдельный App Server временно недоступен, кнопка просмотра берёт историю только соответствующего `provider + threadId`; статус `running` из кэша автоматически устаревает через десять минут и не создаёт вечную фантомную задачу. Кэш ограничен тысячей задач; при переполнении удаляются самые старые завершённые записи, активные не вытесняются.
- Неизменившийся снимок задачи не перезаписывает `task-sync.json`. События собственного `Integration App Server` остаются основным мгновенным каналом обновления, а `thread/read` используется раз в пять секунд только как страховка от потерянного события. Внешний `VSCode App Server` проверяется чаще, чтобы новый ход быстро появлялся в статусе. Одновременные чтения одного треда и повторные открытия `/tasks` в коротком интервале объединяются; индекс названий Codex перечитывается только после изменения файла.
- При разрыве Codex App Server бот автоматически запускает его снова, возобновляет поток и читает сохранённую задачу через `thread/read`. Для продолжающегося хода восстанавливается наблюдение; для завершённого — найденный ответ доставляется в Telegram.
- Если `thread/resume` временно ошибается при запуске бота, но для этого же треда сохранён активный run, бот не создаёт новый выбранный тред. Он сохраняет прежнюю привязку и передаёт ход процедуре восстановления, исключая две параллельные задачи из одного пользовательского продолжения.
- Если управляемый Telegram-ход после переподключения остался в `waitingOnApproval`, но сам JSON-RPC-запрос погиб вместе со старым App Server, в режиме автоподтверждения бот откатывает только незавершённый turn и продолжает задачу новым turn с требованием проверить уже сделанные файлы и не повторять завершённые действия.
- Запросы дополнительных разрешений App Server (`item/permissions/requestApproval`) показываются в Telegram так же, как подтверждения команд и файлов. Запросы MCP (`mcpServer/elicitation/request`) обрабатываются отдельно: безопасная форма-разрешение с булевыми полями, утвердительными вариантами или готовыми значениями принимается в режиме автоподтверждения; форма, для которой пришлось бы выдумывать текст, пароль или неоднозначный выбор, всегда показывается пользователю. Неизвестный MCP-запрос больше не остаётся без JSON-RPC-ответа и не зависает скрыто. Техническое сообщение `Бот запущен` при фоновом рестарте не отправляется.
- Ошибка доставки финального ответа в Telegram не оставляет завершённый ход в реестре активных задач. Ответ сначала сохраняется локально для последующего просмотра кнопкой с глазами, а запуск освобождается независимо от состояния сети; состояние `finishing` после аварийного рестарта также перечитывается и завершается.
- Observer запоминает текст ответа на момент подключения, но при фактическом завершении наблюдаемого хода всегда доставляет его итог отдельно. Это закрывает гонку, когда внешний ход успел завершиться между обнаружением и первым опросом: старый ответ не подменяет текущий, а уже готовый текущий финал не теряется.
- Claude сообщает `session_id` первым событием и бот сохраняет его сразу, а не только после успешного завершения.
- Запущенный ботом ход Claude переживает перезапуск бота. CLI стартует отдельным процессом, а его `stream-json` пишется в файл хода `data/claude-runs/<turnId>.jsonl`, который бот читает хвостом с потоковым UTF-8-декодером. Русский текст и эмодзи сохраняются, даже если опрос пришёлся на середину многобайтного символа. После перезапуска ход подключается заново по сохранённому PID и файлу вывода: живой процесс продолжает вести ту же progress-карточку, а завершившийся отдаёт финальный ответ из файла. Прерванным ход помечается, только если процесса уже нет и результата в файле тоже. По той же причине `/restart` не ждёт завершения ходов Claude, а `/cancel` останавливает ход и после перезапуска — по сохранённому PID.
- При запуске удаляются файлы `data/claude-runs`, которые не принадлежат ни одному восстановленному активному ходу. `/cancel` в Windows останавливает всё дерево Claude через `taskkill /T /F` с резервной остановкой корневого процесса; в Unix сигнал получает detached-группа процессов.
- Записи состояния сериализуются через очередь и атомарно заменяют `state.json`, поэтому параллельные события и авария во время записи не оставляют обрезанный JSON. Не реже одного раза в 30 секунд сохраняется `state.json.bak`; при повреждении основного файла бот восстанавливается из резервной копии и не удаляет output потенциально живых detached-процессов. Хранилище текстов озвучки использует тот же атомарный механизм.

### Надёжность процесса

- Эксклюзивность процесса обеспечивается локальным системным каналом, уникальным для `dataDir`, поэтому две копии не могут одновременно читать `getUpdates` и дублировать ответы даже при гонке за устаревший файл. `data/bot.lock` хранит PID, случайный token, время запуска и имя канала только для диагностики и совместимости со старой версией; PID, переиспользованный Windows после аварии, не создаёт вечную блокировку. Штатный `/restart` не обрывает управляемые ботом ходы и не бросает уже принятую фоновую загрузку, распознавание или озвучивание: при необходимости перезапуск откладывается до безопасной передачи работы ходу Codex, чей App Server перезапускается вместе с ботом. Старая копия сначала прекращает polling и фоновые таймеры, завершает всё дерево Codex App Server/MCP и локальный TTS-worker, и только затем освобождает системный lock и запускает замену; соседний Telegram update из уже полученного пакета остаётся для новой копии и обрабатывается ровно один раз. Ходы Claude перезапуск не задерживают, потому что подключаются заново. Внешние наблюдаемые задачи после запуска подключаются снова по сохранённому thread/session и сохраняют фактического владельца (`VSC`, `APP`, `CLI`, `EXT`). Сообщение `Перезапускаю бота…` редактируется в итоговую карточку `БОТ ПЕРЕЗАПУЩЕН`; технический статус `interrupted` при таком восстановлении пользователю не отправляется.
- Фоновое наблюдение повторно сверяет выбранные `provider + project + threadId` после каждого асинхронного чтения snapshot и ещё раз проверяет реестр запусков. Переключение задачи или старт Telegram-хода во время чтения не могут подключить observer к старой задаче либо создать второй запуск поверх нового.
- Codex App Server автоматически переподключается с повторными попытками, а пользователь видит состояние соединения в служебном сообщении.
- Каждый Codex JSON-RPC вызов ограничен `codexRpcTimeoutSeconds` (по умолчанию 30 секунд). Ошибка запуска App Server, закрытие stdin или зависший RPC завершают конкретное ожидание ошибкой вместо бесконечной блокировки Telegram polling.
- Перед запуском `Integration App Server` проверяет только локальные HTTP MCP из пользовательского `config.toml`. Недоступные порты отключаются аргументами лишь для этого экземпляра App Server, поэтому не создают повторяющиеся fatal-записи и не меняют глобальную конфигурацию. На следующем безопасном перезапуске проверка выполняется заново, и уже запущенные MCP снова подключаются.
- При обрыве Telegram polling бот продолжает работу локальных ходов и повторяет `getUpdates` с ограниченной задержкой `3 → 6 → 12 → 24 → 30` секунд. После первого успешного запроса задержка сбрасывается; при долгом обрыве одинаковые ошибки журналируются разреженно.
- `telegramApiBaseUrl` применяется ко всем JSON- и multipart-запросам, загрузке файлов, изображениям и голосу — локальный Bot API server или прокси не обходится прямыми обращениями к `api.telegram.org`.
- Если новое состояние прогресса пришло во время уже выполняющегося `editMessageText`, оно помечается ожидающим и отправляется сразу после текущей правки, а не теряется до следующего события.
- Ошибки Claude разбираются из финального JSON даже при ненулевом коде процесса. Для `rate_limit_event` бот показывает настоящую причину и время сброса вместо общего сообщения «завершился с кодом 1».
- Telegram offset сохраняется только после обработки конкретного update. Штатный `/restart` запускает замену лишь после записи offset и runtime-state, поэтому новая копия не обрабатывает повторно саму команду рестарта. Ошибка обработчика показывается в том же чате и не приводит к молчаливой потере последующих сообщений.
- Ключ каждого ручного подтверждения — неповторимый UUID, привязанный к точному Telegram chat/message и активному run. Кнопки до рестарта честно протухают и не могут разрешить уже другую операцию. Меню, меняющие текущую задачу, проект, агента, модель или режим, содержат отпечаток контекста; старая кнопка не архивирует и не перенастраивает задачу, выбранную позднее.
- Привязки Telegram-сообщений записываются независимыми append-only событиями в `data/telegram-thread-bindings.d`. Параллельные `bot.mjs`, `send-message.mjs` и `send-images.mjs` больше не перезаписывают общий JSON друг у друга; прежний `telegram-thread-bindings.json` читается как совместимый базовый слой. После 500 событий журнал под межпроцессной блокировкой атомарно сворачивается в базовый JSON, поэтому каталог не растёт бесконечно и конкурентная запись во время компактации не теряется.
- При штатной остановке очищаются индикатор набора, таймеры очереди, прогресса и наблюдения; незавершённые очереди и запуски остаются в состоянии для восстановления после старта.
- Изображения, голосовые и запросы озвучивания до фиксации Telegram offset атомарно сохраняются отдельными работами в `data/background-jobs/`. Ограниченные FIFO-очереди восстанавливаются после аварийного завершения процесса, сохраняют исходную задачу, модель и режим и удаляют запись после обработки. Внешние API не имеют общего ключа идемпотентности, поэтому гарантия — at-least-once: потеря принятой работы закрыта, но при падении точно между внешним действием и локальной отметкой его завершения редкий повтор теоретически возможен.
- Важные итоговые ответы и уведомления из `send-message.mjs` при временной сетевой ошибке сохраняются отдельными атомарными файлами в `data/delivery-outbox/`. Для медиа-карточки при ошибке загрузки сначала используется текстовый fallback, который и попадает в надёжную очередь. Очередь безопасно принимает сообщения от параллельных процессов Codex/Claude, переживает рестарт, сохраняет порядок частей одного ответа, заменяет устаревший недоставленный progress и повторяет доставку с экспоненциальной задержкой, учитывая Telegram `Retry-After`. Если одна часть финала попала в очередь, остальные части того же финала больше не обходят её прямой отправкой. Служебные действия (`typing`, callback-ответы и редактирование старого прогресса) намеренно не ставятся в очередь. При сетевом таймауте Telegram не поддерживает ключ идемпотентности, поэтому редкий повтор уже принятого сервером сообщения технически возможен.
- `telegram-codex.log` и `telegram-codex-error.log` ротируются внутри процесса. По умолчанию каждый файл ограничен 5 МБ и хранится до пяти архивов вида `telegram-codex.1.log`; лимиты задаются через `logMaxBytes` и `logMaxFiles`.

### Озвучка

- Последние 100 текстов, связанных с кнопками `🔊 Озвучить`, сохраняются в `data/speech-texts.json`. Кнопки новых сообщений продолжают работать после рестарта бота.
- Silero TTS запускается отдельным коротким worker-процессом для каждого запроса и создаёт OGG Opus. Изоляция запросов не позволяет зависшему или повреждённому каналу предыдущей озвучки ломать следующие нажатия. Старые кнопки, созданные до появления постоянного хранилища, восстановить невозможно.

### Настройки интерфейса и доступа

Панель быстрых действий отправляется как постоянная `ReplyKeyboardMarkup`. Обычные ответы без собственных inline-кнопок повторно прикрепляют её, чтобы Telegram Desktop восстанавливал панель после локального скрытия. Если клиент всё же не показывает значок клавиатуры, синяя системная кнопка `Меню` содержит первой команду `⌨️ Показать кнопки` (`/menu`); она заново отправляет панель. Это обход клиентского ограничения Telegram: `is_persistent` является запросом к приложению, а не принудительной блокировкой скрытия.

- `showTaskProject` управляет префиксом проекта в `/tasks`, когда включена кнопка проекта; если `showProjectButton` или `showTaskProject` равен `false`, список остаётся компактным.
- `autoApproveOnStart` включает автоматические подтверждения после каждого запуска. Для Codex автоматически принимаются запросы команд, файловых изменений, дополнительных разрешений и безопасно заполняемые MCP-формы разрешений; произвольные формы ввода не автозаполняются. Для Claude используется `bypassPermissions`. В публичном примере значение оставлено `false`.
- `codexRpcTimeoutSeconds` ограничивает ожидание ответа локального Codex App Server; значение по умолчанию — 30 секунд.
- Выбранные проект, агент, задача, модели, Reasoning и режим Plan/Work сохраняются между перезапусками.
- В итоговой статистике задачи категории показываются в условных единицах: вход ×1, кэш ÷10, выход ×6 и думы ×6. В заголовке остаётся только общая сумма с единственной подписью `у.е.`; строки категорий содержат числа без повторения этой подписи. Для каждой категории также выводится её доля от общей суммы; округлённые доли всегда складываются ровно в 100%.

### Codex models

`/model` switches the Codex model used for the next `turn/start` request. `/reasoning` selects the reasoning effort, and `/mode` selects `Work` (`default`) or `Plan` (`plan`). The Reasoning and Plan/Work buttons are in the second menu row. The selected values are saved in `data/state.json` and sent explicitly with every Codex turn, including turns in resumed tasks. Defaults are configured in `config.json`:

On Windows, the bot prefers the newest Codex binary bundled with the VS Code extension. Set `codexExecutable` or `CODEX_EXECUTABLE` only if you need to force a specific CLI path.

```json
{
  "codexExecutable": "",
  "codexModel": "gpt-5.6-sol",
  "codexReasoningEffort": "high",
  "codexCollaborationMode": "default",
  "logMaxBytes": 5242880,
  "logMaxFiles": 5,
  "deliveryRetryIntervalSeconds": 15,
  "codexModels": [
    { "value": "gpt-5.5", "label": "GPT-5.5" },
    { "value": "gpt-5.6-sol", "label": "GPT-5.6-Sol" },
    { "value": "gpt-5.6-terra", "label": "GPT-5.6-Terra" },
    { "value": "gpt-5.6-luna", "label": "GPT-5.6-Luna" },
    { "value": "gpt-5.4", "label": "GPT-5.4" },
    { "value": "gpt-5.4-mini", "label": "GPT-5.4-Mini" },
    { "value": "gpt-5.3-codex-spark", "label": "GPT-5.3-Codex-Spark" }
  ]
}
```

For Claude Code, `/model` still switches `sonnet`, `opus`, or `haiku`.

### Claude Code (опционально)

Codex остаётся провайдером по умолчанию. Чтобы использовать Claude Code, сначала установите и авторизуйте CLI, затем укажите:

```json
{
  "provider": "claude",
  "claudeExecutable": "claude",
  "claudeModel": "sonnet",
  "claudePermissionMode": "acceptEdits"
}
```

Либо запустите установщик с `python install.py --provider claude`. Провайдер также переопределяется переменной `AI_PROVIDER`, путь к CLI — `CLAUDE_EXECUTABLE`, модель — `CLAUDE_MODEL`. При стандартном значении `claude` в Windows Integration на каждом старте выбирает самый новый установленный native binary из расширений Claude Code для VSCode и глобального npm-пакета; поэтому обновление расширения автоматически выравнивает версию. Явный путь или `claudeExecutableArgs` всегда отключает автопоиск и используется без подмены.

Claude запускается в headless-режиме с `stream-json` и сохраняет `session_id` сразу после события инициализации; продолжение доступно через `/resume <ID>`. Поскольку CLI не предоставляет отдельный машиночитаемый реестр сессий, `/tasks` безопасно индексирует локальные transcript-файлы `~/.claude/projects`, отбрасывает subagent-сессии и служебные command-only сессии (`/usage` и подобные), затем оставляет только задачи из разрешённых папок. Для названий бот предпочитает последние записи `ai-title`, которые генерирует сам Claude Code, и использует пользовательский запрос только как запасной вариант. `/status` получает актуальные лимиты через встроенную команду Claude Code `/usage`, не обращаясь к модели. Режим `acceptEdits` разрешает правки в рабочей папке, но не произвольные команды. Telegram-кнопка автоподтверждения включает `bypassPermissions` и должна использоваться лишь в доверенной рабочей папке. По умолчанию автоматический режим сбрасывается после перезапуска; постоянное включение задаётся локальным параметром `"autoApproveOnStart": true`.

### Несколько рабочих папок

Добавьте разрешённые папки в `projects`. Значение `projectRoot` задаёт папку по умолчанию и должно совпадать с одним из путей:

```json
{
  "projectRoot": "C:\\Projects\\Main",
  "projects": [
    { "name": "Основной", "path": "C:\\Projects\\Main" },
    { "name": "Сайт", "path": "C:\\Projects\\Website" }
  ]
}
```

Если `projects` отсутствует, бот продолжает работать с единственным `projectRoot`. В Telegram используйте `/projects` или кнопку «📁 Проект». Кнопка показывается по умолчанию; чтобы скрыть её, установите `"showProjectButton": false` — команда `/projects` продолжит работать. Имя проекта перед названием задачи в `/tasks` показывается только вместе с кнопкой проекта; `"showTaskProject": false` позволяет отдельно скрыть этот префикс. При переключении проекта создаётся новая выбранная задача, а уже запущенные задачи в других проектах продолжают выполняться.

## Безопасность

- Доступ проверяется одновременно по `allowedUserIds` и `allowedChatIds`.
- По умолчанию принимаются сообщения только из приватных чатов.
- Codex работает с `workspaceWrite`, без сетевого доступа для команд агента.
- Claude Code использует собственную систему разрешений; рекомендуемый режим — `acceptEdits`.
- Подтверждения команд, изменений файлов и дополнительных профилей разрешений отправляются владельцу в Telegram.
- Автоподтверждение после запуска определяется локальной настройкой `autoApproveOnStart`; безопасное значение в примере — `false`.
- Не публикуйте внешний `config.json`, каталоги runtime-`data`, окружения моделей и логи.

Бот предоставляет удалённый доступ к Codex и папкам из `projects` (либо к `projectRoot` в однопроектной конфигурации). Не добавляйте недоверенных пользователей в разрешённый список. Текущая версия не предназначена для совместного использования одного процесса несколькими людьми: состояние Codex и активная задача общие.

## Проверка и запуск

```powershell
npm run check
npm test
npm run test:e2e
npm run test:all
npm run doctor
npm start
```

`npm run test:e2e` выполняет полностью локальную CLI-приёмку настоящего `bot.mjs` через fake Telegram Bot API, Codex App Server и Claude CLI. Рабочий бот, токен, задачи и `data` не затрагиваются. Полное покрытие сценариев перечислено в [E2E_TEST_MATRIX.md](E2E_TEST_MATRIX.md). `telegramApiBaseUrl`, `codexExecutableArgs`, `claudeExecutableArgs` и `progressStartDelayMs` служат безопасными точками подмены для стенда; производственные значения по умолчанию остаются прежними.

`npm run check` одним процессом синтаксически разбирает все `.mjs` модули без их исполнения. `npm test` проверяет модули функционально, а `npm run test:e2e` — жизненный цикл отдельного процесса бота.

В Windows также доступны `start.ps1` и `install-autostart.ps1`. После активации они направляют запуск во внешний runtime; PowerShell используется только как launcher и для интеграции с автозапуском Windows, сам бот работает в Node.js.

Команды: `/agent`, `/model`, `/reasoning`, `/mode`, `/projects`, `/new`, `/tasks`, `/resume`, `/rename`, `/archive`, `/current`, `/thread`, `/status`, `/approvals`, `/restart`, `/diff`, `/cancel`, `/help`. Старое имя `/engine` сохранено как совместимый псевдоним.

`/archive` архивирует текущую задачу Codex и автоматически выбирает первую оставшуюся задачу из списка. Та же команда доступна кнопкой `❌ Архивировать текущую задачу` в конце `/tasks`. При архивации через кнопку исходное меню обновляется на месте: архивированная задача исчезает, а автоматически выбранная помечается как текущая.

При обычном выборе задачи Codex или Claude через `/tasks` бот сразу переключает локальный адрес агента, проекта и thread/session, а дорогое `thread/resume` выполняет только перед фактическим обращением к Codex. Удаление списка и отправка уведомления выполняются параллельно. Если выбрана другая задача, бот присылает то же форматированное уведомление `Текущая задача изменена`, что и при переходе по ответу на привязанное сообщение. Повторный выбор текущей задачи через список, карточку статуса или `/resume <ID>` присылает уведомление `Текущая задача уже выбрана` с кнопкой показа последнего сообщения.

`/thread` показывает ID выбранного потока. Откройте активную папку в Codex App или VS Code и выберите этот поток в истории; из CLI его можно продолжить командой `codex resume <ID>`. Не отправляйте сообщения одновременно из нескольких интерфейсов в один и тот же поток, пока в нём выполняется активный turn.

## Голосовые сообщения

Голос распознаётся локально через `faster-whisper`. Модель выбирается параметром `whisperModel`; файлы модели и временные аудиофайлы не попадают в Git.

Для каждого непустого итогового ответа бот по умолчанию показывает кнопку `🔊 Озвучить`. Синтез выполняется локально через Silero TTS, а результат отправляется как Telegram voice message в OGG Opus. Запросы выполняются последовательно через ограниченную и сохраняемую на диск очередь максимум из десяти работ: повторные нажатия не создают неограниченное число одновременных синтезов, а принятый запрос переживает рестарт процесса. Для каждого запроса запускается изолированный worker, который завершается после одного OGG: следующий запрос не наследует его pipe, память или ошибочное состояние. Worker сообщает о принятии запроса, загрузке модели, начале и завершении каждого фрагмента и кодировании результата. Если текущий этап не даёт прогресса дольше `ttsRequestTimeoutSeconds` (по умолчанию 60 секунд), всё дерево зависшего worker принудительно останавливается; сообщение об ошибке содержит название этапа. Поэтому длинное исправно обрабатываемое сообщение не обрывается через 60 секунд от начала синтеза. Последние 100 текстов кнопок сохраняются в `data/speech-texts.json`, поэтому новые кнопки переживают рестарт. Модель, голос, минимальная длина обычного ответа и максимальный объём озвучиваемого текста задаются параметрами `ttsModel`, `ttsSpeaker`, `ttsButtonMinChars` и `ttsMaxChars`; значение `ttsButtonMinChars` по умолчанию равно `1`. При первом озвучивании Silero скачивает модель во внешний runtime-кэш `data/models/silero`.

Команда `npm run tts:smoke` проходит тот же Node → Python → Silero → OGG тракт без отправки в Telegram, проверяет непустой результат и удаляет диагностический файл.

Если пользователь отвечает на сообщение Telegram через «Ответить», бот добавляет текст или подпись цитируемого сообщения в запрос как отдельную цитату. Команды `/...` при этом продолжают распознаваться по самому новому сообщению.

## Изображения

Бот принимает Telegram-фотографии и файлы с MIME-типом `image/*`. Подпись к изображению используется как запрос; без подписи Codex анализирует картинку с учётом предыдущей переписки. Загрузка изображений и распознавание голоса выполняются вне последовательного цикла Telegram-обновлений: долгий файл не блокирует команды и переключение, а будущий ход остаётся закреплён за задачей, моделью и режимом, выбранными в момент получения. Общая сохраняемая FIFO-очередь обрабатывает один медиафайл за раз и принимает максимум 20 работ, поэтому серия голосовых не запускает параллельно несколько тяжёлых Whisper-процессов и не теряется при аварийном рестарте бота. Временный файл удаляется после завершения задачи.
