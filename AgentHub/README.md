# Agent Hub Server

Native source delivery after a normal Test/Await return uses existing
`task:await-cutover` with `--returned-native-test` instead of
`--initial-native-test`, plus `--expected-returned-result-commit` naming the
preserved unique accepted result. All exact source/tree/branch, Task CAS/caller,
main/dev/publication/candidate/plan/runtime arguments and `--confirm-cutover`
remain required. SQL verifies successful Test and normal-return originals itself;
Git requires descendant source. This does not clear refs, rewrite receipts, publish
or install. Retry UNKNOWN with its original request and arguments. Verified installed
native capability closes new bootstrap admissions and retains historical recovery;
ordinary Test subsequently uses that installed owner.

Ранние этапы запуска сохраняют строки `[startup]` в существующем `agent-hub.log`
до открытия SQLite и запуска фоновых обработчиков. Строки связываются через PID,
релиз и `operationSpanId`; последнее `started` без результата помогает определить
место прерванного запуска. После инициализации CommandTrace завершённые замеры
передаются в общий механизм диагностики. Для ранних строк действуют обычные
настройки размера и ротации логов.

Локальный сервер задач и личного журнала Codex App Server и Claude Code CLI. Каждый участник запускает собственный экземпляр со своим AI-аккаунтом, локальными rollout и разрешёнными рабочими папками. Telegram, Telegram Mini App и Android App подключаются как отдельные необязательные компоненты.

Telegram, Web App, VS Code и [Android-клиент](AndroidApp/README.md) видят общий каталог, локальную историю, выбранный поток, настройки и живые ходы; второй процесс Codex/Claude не запускается. Android-клиент переиспользует опубликованный интерфейс Mini App, но авторизуется ключом доверенного устройства из Android Keystore, а не через Telegram. Обычный браузер на публичном HTTPS-адресе добавляется тем же одноразовым кодом: неэкспортируемый ключ P-256 хранится в IndexedDB только этого браузерного профиля, а отзываемая сессия обновляется автоматически. После однократной установки версии с updater Android-приложение само получает у настроенного HTTPS Hub более новый APK, проверяет его размер, SHA-256 и подпись пакета и передаёт системному установщику. На Android 12+ приложение запрашивает установку без лишнего окна; если ОС не разрешает фоновое обновление, автоматически открывается штатное системное подтверждение.

Текущее состояние работ по надёжности и оставшиеся задачи ведутся в [STABILIZATION_CHECKLIST.md](STABILIZATION_CHECKLIST.md).
Штатная фоновая очистка транспортных копий и её границы описаны в [storage-retention.md](docs/storage-retention.md).

## Крупные вложения и продолжение загрузки

Передача исходящего файла включается оператором в runtime `config.json`:
`miniApp.fileTransfer.enabled: true`, `publicBaseUrl` — существующий публичный
HTTPS origin без пути, `trustedProxyAddresses` — только адреса своего proxy
(например, `127.0.0.1` для Caddy на том же компьютере). Остальные бюджеты приведены
в `config.example.json`. После изменения нужен штатный безопасный перезапуск.
Прямой HTTPS gateway обслуживает `/transfer/` и авторизованные owner API;
отдельный Cloudflare Worker автоматически эти маршруты не получает.
Получатель использует поддерживаемый браузер с native Save File Picker;
WebView предлагает открыть ссылку в браузере. Для приёмки проверяют SHA-256
фактически сохранённого синтетического файла, а не только серверный статус.

Закрытие передачи запрещает новые подготовки и GC, дожидается уже принятых
операций и лишь затем закрывает SQLite. Сохранённый Caddy с прежней конфигурацией
заменяет существующий gateway controller после подтверждённого выхода старого
Hub-родителя. Проверяются точные executable/command line/PID/время создания и
байты executable/config; живой или неизвестный владелец оставляет барьер и старую
конфигурацию. Новый listener до подтверждённого выхода прежнего не запускается.
Явная политика `no-referrer` backend сохраняется, обычные страницы получают
прежнее значение gateway по умолчанию.

Клиенты с `agent-hub-attachment-upload-v1` передают файлы частями до 1 МиБ.
По умолчанию разрешено 128 МиБ на файл и 256 МиБ суммарно для загрузок одного
пользователя. Пределы задаются в байтах через `AGENT_HUB_ATTACHMENT_MAX_BYTES`
и `AGENT_HUB_ATTACHMENT_USER_MAX_BYTES` в окружении runtime и Worker; верхние
границы — 256 и 512 МиБ соответственно. Клиент получает фактические пределы
из capabilities сервера. В одном сообщении по-прежнему не больше восьми файлов.

После остановки подготовки или обрыва соединения исходный черновик можно
отправить повторно: Хаб проверит сохранённые части и дошлёт недостающие. Части
хранятся 30 минут без продления срока повторными запросами. Истёкшую или явно
удалённую загрузку нужно начать новым выбором файла. Процент загрузки означает
подготовку вложений; отправка сообщения агенту начинается только после проверки
готовых файлов. Отмена подготовки не отменяет уже принятое Хабом сообщение.

Браузер сохраняет исходные файлы как Blob в IndexedDB. Если политика браузера
или квота не позволяет сохранить черновик, интерфейс сообщает, что он доступен
только до перезагрузки; автоматическая перезагрузка блокируется. Существующие
base64-черновики и старые серверы поддерживаются с прежним пределом 20 МиБ.
Крупные файлы не отправляются через старый транспорт целиком.
В VS Code при отключённых Mini App и Android те же части до 1 МиБ передаются
через локальный IPC. Загрузками продолжает управлять общий серверный сервис;
включать веб-компоненты для вложений не требуется. После обновления моста
расширения выполните `Developer: Reload Window` в VS Code.
Локальное хранилище файлов ограничено 512 МиБ и 128 записями; срок хранения —
семь дней. Это отдельный срок от 30 минут для начатой серверной загрузки.

Общий веб-интерфейс используется также в Mini App, Android и VS Code. Для файлов,
отправленных непосредственно Telegram-боту, действует внешний предел
[Telegram getFile](https://core.telegram.org/bots/api#getfile) — 20 MB.
Такие крупные файлы следует прикладывать через веб-интерфейс Hub. Отдельный
локальный Telegram Bot API Server этим изменением не устанавливается.
Загрузка частями включена в поле отправки сообщений чата. Отдельные формы
вложений карточки Task и отчёта об ошибке пока используют прежний транспорт
с пределом 20 МиБ.

## Требования

Обязательные инструкции Hub (Guide, Global, Workspace, Stream и MCP-контекст)
передаются в каждом `turn/start` через `additionalContext` вида `application`
полным упорядоченным снимком: `agent-hub`, `agent-hub-0001` и далее.
Каждая часть меньше 3000 байт UTF-8; идентификатор снимка принадлежит текущему
запуску. Это предотвращает усечение длинных правил в Codex и восстанавливает
их на следующем ходе после сжатия истории. Повтор RPC использует тот же снимок.
Настройки режима Default/Plan не являются
каналом этих инструкций: каталог модели может заменить их штатным текстом.
Проверка совместимости Codex получает MCP capability из середины длинного
контекста приложения, а не из пользовательского сообщения или его короткого хвоста.
Сжатие внутри уже выполняющегося хода может удалить application context до
следующего хода; его немедленное восстановление внутри Codex не гарантируется.

Стандартный резервный каталог включает GPT-6 Astra, GPT-6.1 Sol, GPT-6 Sol и GPT-6 Luna.
Явно заданный локальный список остаётся резервным до полного успешного ответа провайдера.
После запуска Codex App Server Hub запрашивает все страницы `model/list` текущего аккаунта
и обновляет выбор моделей в Desktop и Telegram без ожидания ответа при восстановлении ходов.
Для этого фонового запроса действует отдельный предел 20 с на страницу и 60 с на
полный каталог; после неудачи Hub дважды повторяет его с задержкой 10 и 30 с.
Открытый диалог Stream позволяет отдельно нажать «Обновить доступные модели» без
перезапуска Hub; для этой команды Desktop допускает 180 с, включая сохранение
каталога и снимок после фонового запроса. Диалог показывает сохранённые настройки именно этого Stream,
а не модель глобальных настроек; пустое значение означает наследование.
Смена модели Stream не меняет модель уже выполняющегося хода.
Ручной порядок — 6 Astra, 6.1 Sol, 6 Sol, 6 Luna, 5.6 Sol, 5.6 Terra, 5.6 Luna,
затем остальные — не ограничивает доступность: все видимые ID из полного ответа
доступны для выбора, новые ID располагаются сверху и сохраняют этот приоритет после
рестарта. Первый успешный ответ задаёт исходный каталог, а не объявляет все его ID
новыми. После полного обновления исчезнувшие ID удаляются из выбора; неполный ответ
или ошибка сохраняют прежний список. Историческая модель остаётся в настройках
Stream и учёте, но не возвращается в список доступных моделей.
Для Claude Code Hub запрашивает метаданные `supportedModels()` через Claude Agent
SDK без пользовательского сообщения и вызова модели. Если метаданные CLI
недоступны, но задан `ANTHROPIC_API_KEY`, используется официальный Models API.
При ошибке или неполном ответе остаётся прежний список; полный пустой каталог
означает отсутствие доступных для выбора моделей. Сохранённый выбор модели
не сбрасывается. Каталог моделей влияет на выбор следующих ходов, а тарифы
исторического расчёта cr и QU хранятся отдельно и не выводятся из каталога.

- Node.js со встроенным `node:sqlite`: 22.5 или новее, рекомендуется 24+;
- установленный и авторизованный Codex CLI либо Claude Code CLI;
- Python 3.10 или новее — только для распознавания и синтеза голосовых сообщений.
- Для сборки необязательного Android-клиента: JDK 17, Android SDK API 36 и Gradle 8.13. Обычная установка HUB их не требует.

## Установка

Основа Agent Hub всегда включает личный журнал, сбор статистики, App Server и локальные интерфейсы Desktop/VS Code. Дополнительно включаются:

- `telegram` — Telegram-бот;
- `mini-app` — Telegram Mini App; автоматически включает `telegram`;
- `android-app` — отдельное Android-приложение, не связанное с Telegram ID;
- `shared-dashboard-bot` — единый командный Telegram-бот для добавления карточек в личный Dashboard каждого участника.
- `test-contour` — изолированная кандидатная сборка с локальным Web UI,
  отдельным VS Code-расширением, браузерным smoke и списком моделей
  Spark/Luna/Fake Codex;
  production runtime, hooks и Telegram не используются.

### Вопросы агента

Асинхронные вопросы Codex показываются в своём Stream отдельной формой:
варианты выбора, поле собственного ответа и кнопка `Ответить`. Вопрос остаётся
после завершения хода и перезапуска Hub. Фоновые обновления сохраняют введённый
черновик формы. При неоднозначном результате отправки форма сохраняет ответ и
предлагает явный повтор с тем же идентификатором; автоматически ответ не уходит.

### Профили проверок

Обычный набор сохраняет критическое поведение и репрезентативную проверку
контраста. `npm run test:cosmetic` включает остальные матрицы тем и размеров,
`npm run test:stress` — многократные повторения взаимодействий. Эти команды
исполняют содержащие проверки файлы целиком. `npm run test:reliability` запускает
дорогой сценарий конкуренции очереди; его известное падение и стоимость
зафиксированы в `tests/unreachable-tests.json`, поэтому зелёный обычный набор не
означает, что этот сценарий пройден. Выключенные профили печатают причину пропуска.

Полный этап `publish:changed -- --full-tests` выполняется без общего лимита
времени. Сохраняются контроль отсутствия вывода и локальные пределы тестов,
сетевых операций, сборки и готовности. Другие шаги публикации сохраняют свои
конечные пределы; прежние failed receipts не переписываются.

Для проверки именно готового Windows-артефакта без повторной сборки используйте
[проверку замены runtime](docs/release-artifact-acceptance.md). Её результат
отдельно перечисляет подтверждённые сценарии и пробелы production parity.

### Тестовый контур

Компонент устанавливается отдельно и не меняет production runtime:

```powershell
python install.py --enable-component test-contour
```

`npm run contour:refresh` находит управляемый worktree ветки `dev`, фиксирует
его точный `HEAD`, собирает эти исходники в отдельный immutable runtime и
запускает его на `127.0.0.1:8877`. `npm run contour:open` открывает
локальный UI, `npm run contour:status` показывает candidate release и модель,
`npm run contour:stop` останавливает только контур. Повторный `contour:refresh`
сохраняет его изолированные данные и быстро поднимает новую кандидатную сборку
без полного набора тестов.

Установщик также ставит независимое расширение `agent-hub.agent-hub-test-contour`
с командами `agentHubTestContour.*`. Оно подключается только к
`AgentHub-TestContour`, имеет собственную Activity Bar-кнопку и не разделяет
состояние панели с production-расширением.

```powershell
npm run contour:refresh
npm run contour:clone-data
npm run contour:open
npm run contour:verify
```

Для многошаговой ручной проверки сначала подготовьте нужную версию и получите
её точные `operationId`, `source.headCommit` и `releaseId` через
`npm run contour:status -- --json`. Затем запустите foreground-команду удержания:

```powershell
npm run contour:lock -- --owner S2 --owner-provider codex --owner-thread <threadId> --owner-turn <claimedTurnId> --request-id manual-check-1 --expected-operation <operationId> --expected-head <headCommit> --expected-release <releaseId> --json
```

Команда печатает `acquisitionId` и `releaseToken`, а затем остаётся запущенной,
удерживая тот же per-root interprocess lock, которым пользуются `refresh`,
`stop`, `verify`, clone/adopt и uninstall. В другом терминале можно проверить
владельца командой `npm run contour:lock-status -- --json`. `threadId` берётся
из текущего Agent Hub context, а `claimedTurnId` — из результата штатного
`hub_task_claim` этого же хода; helper до захвата подтверждает эту точную
активную запись в основном Hub и продолжает следить за её terminal receipt.
Для нестандартной установки путь к её data directory задаётся явно через
`--owner-runtime-data <path>`; по умолчанию используется штатный production
Agent Hub. Сразу после
завершения, ошибки или отмены проверки освободите именно этот захват:

```powershell
npm run contour:unlock -- --request-id manual-check-1 --acquisition <acquisitionId> --release-token <releaseToken> --json
```

Повтор команды с тем же `request-id` возвращает тот же захват или его уже
завершённую квитанцию. Чужой либо устаревший unlock не освобождает новый lock.
Обычные `refresh`, `stop` и `verify` не обходят ручной захват: они ждут тот же
lease до 10 минут, после чего завершаются ошибкой ожидания, если тестовая сессия
ещё не освободила контур. Это ожидание не является отдельной очередью операций.
В `lock-status` состояние `stale` означает лишь, что сохранённая ручная
квитанция больше не совпадает с текущим operation lock; вложенное поле `lock`
нужно проверить отдельно, потому что другой refresh/stop/verify всё ещё может
владеть корнем.
Foreground-владелец освобождает lock при штатном unlock и обработанной отмене;
provider-run terminal ledger привязанного хода (`completed`, `failed` или
`aborted`) для Codex и Claude, включая отмену хода при всё ещё живом helper,
также штатно завершает удержание. Для Codex сохраняется и прежний terminal
receipt. Простое исчезновение active-run без точного terminal evidence считается
неизвестным исходом и lock не снимает. После
аварийной смерти самого helper его PID следующий владелец восстанавливает
канонический lock только по подтверждённой смерти, а не по возрасту или
heartbeat. Захват делается после подготовки и повторно сверяет точную версию и
активность хода уже внутри lock, закрывая обе гонки. Не удерживайте его во время
разработки, исправлений, локальных тестов, ревью или ожидания человека.

`contour:clone-data` делает согласованный SQLite backup текущего production
`journal.sqlite`, сохраняет прежнюю базу контура и запускает контур с копией.
Workspace, Stream, Dashboard, журнал, статистика и история лимитов сохраняются;
все Stream переводятся на `fake-codex`, боевые provider thread-id
отвязываются, а runtime/project-пути активных ходов заменяются synthetic project
контура. Immutable release archive/evidence не переписывается. Provider task read model очищается, чтобы startup не привязал
production Thread заново; завершённая история остаётся в каноническом журнале.
Транспортный `runtime.sqlite`, receipts, locks и секреты не копируются.
Каждый Workspace получает рабочую директорию synthetic project контура и
выключенный release workflow: иначе Stream с пустой рабочей директорией
унаследовал бы production-путь Workspace. Исторические Task Git-ссылки сохраняют
Task, ветку и result commit, но их репозиторий переназначается на несуществующий
путь `detached-git/<ключ репозитория>` внутри контура. Поэтому удаление или
закрытие клонированной Task падает в контуре и не удаляет ветки и refs в
production-репозитории.

Для проверки восстановления с исходными Workspace/Stream/Thread, очередью и
квитанциями добавлен [recording-контур](docs/recording-contour.md). Он использует
общий снимок трёх SQLite и JSON-очередей, отдельную рабочую копию и локальный
провайдер с явными результатами сценария. Обычный `clone-data` не заменяет этот
сценарий и отказывается изменять уже подготовленный recording-контур.

Test Contour всегда один и собирается из локальной ветки `dev`. Task-ветки
попадают в него после перехода в `Awaiting implementation`; отдельные runtime
для веток не создаются. Статус контура хранит точный показанный head `dev`.
Новая candidate-сборка подготавливается до остановки текущего runtime, поэтому
ошибка Git или подготовки не гасит уже работающий контур.

Обычный boot/default контура использует `fake-codex`, а в том же списке моделей
Stream доступны `gpt-5.3-codex-spark` и `gpt-5.6-luna`. Обе реальные модели
обращаются к Codex и расходуют лимиты аккаунта. Fake Codex работает только внутри
marker-owned Test Contour: любой отправленный ему пользовательский ход
завершается локальным ответом `Принято`, поэтому им можно проверять intake,
очередь, live/history projection, финал и доставку без вызова модели. Внутренний
stdio-мультиплексор сохраняет один provider identity `codex`, но маршрутизирует
каждый turn по выбранной модели; production runtime этот fake не использует.

`contour:verify` заново собирает candidate, запускает headless Edge, проверяет
загрузку и переключение основных экранов, отправляет сообщение через настоящий
Web UI локальному `fake-codex` и сохраняет screenshot вне Git в каталоге
компонента. `publish:all` и `publish:changed` запускают этот gate только с явным
аргументом `--test-contour`, после автоматических тестов и до первого внешнего
deploy. Без этого аргумента релиз не требует установленный компонент и
пропускает контур.
Для локальной автоматизации Web UI в `devDependencies` закреплён
`playwright@1.62.1`. Он запускает установленный Microsoft Edge через канал
`msedge`; отдельный Chromium скачивать командой `playwright install` не нужно.

Матрица `file-transfer-browser-feasibility.test.mjs` требует Edge и настоящий
Google Chrome. Для изолированной QA-копии Chrome оператор может создать
`release-qa-browsers.json` рядом с runtime-файлом `AGENT_HUB_CONFIG`:
`schemaVersion: 1`, объект `chrome` с `executablePath` (абсолютный путь),
`sha256` (нижний регистр) и точной четырёхкомпонентной `version`. Файл содержит
только тестовую зависимость; основной config с секретами тест не читает.
Перед включением пути проверяются официальный Google источник и цифровая
подпись извлечённого браузера; SHA и версия закрепляются в QA evidence.
Тест повторно проверяет байты EXE и фактическую версию, запускает чистый
профиль с ограниченным окружением. Путь сохраняется при изолированном
LOCALAPPDATA. Без явного QA-файла остаётся обычный Chrome channel; отсутствие
браузера означает отказ проверки, а не SKIP. Установка браузера, изменение
профилей пользователя и глобальных политик этим файлом не выполняются.

Telegram внутри контура полностью loopback-синтетический, Sentry выключен, а
Codex получает только отдельный synthetic project с `workspace-write`.
Контур обрабатывает собственные Codex rollout и каждые пять минут записывает
Codex-лимиты в свою SQLite; фоновый опрос Claude в Codex-only контуре выключен.
Для авторизации в отдельный `codex-home` контура копируется только локальный
`auth.json`; production sessions, archived sessions, config, hooks и MCP туда не
переносятся.

`mini-app` и `android-app` автоматически запускают общий внутренний Web App. Worker, quick tunnel и прямой HTTPS-шлюз являются способами его публикации; голосовой ввод и озвучка включаются своими настройками.
При публикации через Worker общий транспорт Telegram Mini App, Android App и Web App использует короткие подписанные запросы с клиентской паузой. Durable Objects не держат long poll и могут гибернировать между запросами, что не расходует free-tier duration во время ожидания. Текущее состояние интерфейса публикуется отдельно одной версионированной snapshot-проекцией на разрешённого пользователя и читается через `/api/snapshot`, не создавая сохраняемую команду на каждый UI-poll. Изменяющие команды остаются в Durable-очереди, но выбираются по ограниченному временному индексу доступности; завершённая история не сканируется при постановке, ожидании результата и получении следующей команды.
Клиент также повторяет короткие запросы результата команды с ограниченной паузой. Периодические снимки
имеют версию: неизменное состояние возвращается коротким `notModified`, а
удалённый снимок не повторяет текст последнего ответа при наличии точного turn ID.
Обычный UI-poll использует общий 30-секундный кэш каталога задач и не форсирует
полный обход Codex и Claude; локальные изменения инвалидируют кэш немедленно.
Фоновое обновление открытого внешнего хода запрашивает только страницу истории,
не выбирая задачу повторно и не строя второй полный snapshot. Названия задач
сверяются с журналом после фактического изменения каталога и контрольным
проходом раз в пять минут.
Страницы истории также имеют версию: пока завершённая часть чата не изменилась,
фоновый запрос не повторяет её содержимое и продолжает показывать текущий ответ
из компактного live-snapshot.

## Дашборд задач

Раздел `Дашборд` показывает задачи по workflow-статусам с небольшими отступами
по краям. Workspace и `Заметки` выбираются в левом каталоге.
Существующие папки Workspace представлены группами: название выбирает всю папку,
кнопка справа раскрывает выбор отдельного Workspace. В режиме `Все задачи` и при
выборе папки название Workspace показано между ID и потоком над заголовком задачи.
`Бэклог` остаётся отдельным первым столбцом во всех режимах.
Заголовки статусов оформлены как Бэклог: обычный текст и счётчик с нижним
разделителем, без цветных подложек и скруглённых рамок.
В выбранном Workspace кнопка `Создать` в колонке New добавляет задачу без
авторазбора. Workspace, `Заметки` и карточки можно переставлять перетаскиванием; их
порядок сохраняется в SQLite. Для карточек native HTML5 drag остаётся основным
путём и поддерживает перенос в Stream, а mouse/pen pointer fallback внутри доски
сохраняет move/reorder, если браузер не начинает native drag. Один жест отправляет
не больше одного move, реальный drag не открывает карточку кликом, а touch-scroll
и перетаскивание Workspace остаются независимыми. Native drag показывает компактное
растровое превью только выбранной задачи, без соседних карточек и групп.
Перенос карточки на Workspace
или `Заметки` меняет её размещение; перенос между статусами отправляет существующую
команду смены статуса и сохраняет все серверные проверки релизного процесса.
Из Бэклога можно перенести задачу прямо в ячейку статуса: Workspace берётся из
группы, карточки под курсором или выбранного Workspace. Для общей колонки в
режиме «Все» или папки сначала появляется выбор Workspace. Перенос между
Workspace требует подтверждения со старым/новым названием и предупреждением
о снятии привязки к потоку. Отмена не отправляет команду. Сначала подтверждается
размещение, затем запрашивается статус штатным lifecycle; при отказе статуса
задача остаётся в новом Workspace с фактическим прежним статусом и уведомлением.
Открытые задачи со статусом Done остаются на доске до явного закрытия.
`Фильтры` раскрывают переключатель закрытых задач; язык статусов находится в настройках.
В статусном виде обе кнопки стоят рядом с заголовком левого каталога:
отдельной пустой полосы над колонками нет. Раскрытые фильтры занимают место
только слева. На узком экране управление и каталог расположены над доской.
На широком экране один клик показывает детали справа в общей сетке, не перекрывая
доску. Двойной клик или Shift+Enter открывает стандартную модальную карточку.
Кнопка `Изменить` в правой панели открывает редактор. На узком экране карточка становится
модальным окном; черновик сохраняется при изменении ширины окна.
В нижней левой панели диалога показываются задачи выбранного
Workspace. Карточку можно перетащить на Stream: она добавится в его черновик
отдельным Task-вложением, не отправится автоматически и не будет означать команду
начать работу. К вложению можно дописать обычное сообщение; агент получает ссылку
`agent-hub://task/<id>` и читает актуальную карточку через `hub_task_get`, поэтому
полный текст задачи не копируется в промпт и не устаревает. Так можно приложить
Task из Backlog или другого Workspace. MCP-список, чтение и изменение Dashboard
Task доступны между Workspace; ограничения Workspace продолжают действовать для
Stream, правил и релизов.
В истории сообщения ссылка отображается отдельной Task-карточкой, а техническая
prompt-обвязка скрывается. `intent=context` задаёт роль ссылки как контекста, но
решение начинать работу определяется сопровождающим сообщением пользователя.
Прежняя служебная формулировка распознаётся только как migration guard для
сохранённой истории; guard удаляется после того, как в retention не останется
provider prompt, созданных до релиза `2026.8.30`.
Кнопка `Начать работу`
предлагает продолжить существующий Stream или создать новый и отправляет такую же
ссылку с явным намерением начать работу вместо сырого текста и файлов задачи.

В Telegram команда `/task <текст>` сохраняет одну запись. Команда `/task`
включает постоянный режим захвата обычных текстовых сообщений для текущего чата,
а `/task off` возвращает сообщения в выбранный диалог. Отдельная кнопка этого
режима не показывается в постоянной клавиатуре бота; команда остаётся доступна
напрямую и продолжает принимать нажатия старой клавиатуры. После сохранения отдельный
read-only запуск Codex Spark исправляет только очевидные ошибки, создаёт заголовок
и описание, определяет задачу или заметку и предлагает Workspace. Короткая
однострочная запись до 100 символов целиком остаётся заголовком, а описание у неё
пустое. На доске показывается только заголовок; клик открывает карточку с описанием
и действиями. `Сохранить изменения` закрывает карточку только после подтверждённой
записи; при ошибке введённый текст остаётся в форме для повторной отправки.
Карточка растёт по высоте вместе с заголовком до шести строк; более длинному
заголовку автоматически подбирается минимальная дополнительная ширина, а колонка
расширяется вместе с ним без перекрытия соседних карточек.
В открытой карточке поле редактирования заголовка также автоматически растёт по
высоте по мере переноса текста и не показывает внутреннюю прокрутку.
Карточка Workspace содержит опциональный переключатель `Релизный процесс`. Он
одновременно включает Task-backed release tracking и встроенную release-oriented
developer-политику только для этого Workspace. `hub_task_claim` и
`hub_task_start` создают отдельную ветку и worktree Task; исполнитель продолжает
работу только по возвращённому пути. При переходе в `awaiting_implementation`
Hub фиксирует весь Task-worktree локальным commit, получает manifest из Git,
сливает Task-ветку в общий `dev` и записывает Git-derived evidence прямо в Task.
Конфликт merge показывается явно, но не запрещает выбранный пользователем статус.

Если принятый локальный `main` уже ушёл вперёд опубликованного коммита, а
управляемый `dev` сохранил результаты других Test, оператор сначала отдельно
сверяет и принимает точные новые коммиты `main`. Затем доступна одна явная
операция `npm run release:policy -- task-dev-bootstrap enable --project-root
<repository> --accepted-main <sha> --expected-dev <sha> --published-revision
<sha> --published-generation <generation> --merge-base <sha> --request-id
<stable-id>`. Она работает только с чистым управляемым `dev`, проверяет
публикацию/историю и выполняет CAS без изменения Task, primary или remote.
Когда единственный конфликт — `CHANGELOG.md`, оператор может добавить
`--reviewed-changelog-file <regular-file> --resolved-tree <sha>`: владелец
принимает только эти проверенные байты и только если всё итоговое дерево
совпадает с указанным SHA; другой конфликт или несовпадение отменяет merge
до CAS. Это не принимает входящие коммиты автоматически.
Неизвестный результат проверяют повтором только с тем же `request-id` и теми
же входами; конфликт не является разрешением слить rolling dev в Task.

Встроенные правила `Релизный процесс` и роли `Релиз-менеджер` разрешают явно заданный
пользователем порядок текущей работы вместо стандартных требований workflow:
например, иной объём тестов или порядок публикации. Агент должен сохранить
согласованное исключение при продолжении и ротации до завершения этой работы
или нового указания; срочность сама по себе исключения не создаёт. Системные
требования, безопасность и проверки полномочий/целостности в инструментах
сохраняются. Пропущенные проверки и фактическую публикацию агент сообщает явно.
Сохранённые пользовательские правила автоматически не переписываются.

План релиза хеширует Task IDs, ревизии приёмки и Git-результаты, включает
разрешённые Tasks из `Await` и явно показывает как `blocked` карточки без полного
Git evidence. `hub_release_run` сохраняет точный состав, validation mode и цели,
сразу возвращает ID durable операции и асинхронно строит immutable generation в
независимом Agent Hub-owned clone под runtime data. Его `.git`
не связан с `.git` пользовательского clone; там строится `PreRelease`, сохраняются
content-addressed manifest и точный head поколения. Старые linked holders только
показываются в диагностике, не переиспользуются и не удаляются.
Название, описание, чек-лист и смена исполнителя повышают ревизию карточки для
CAS, но не меняют принятую версию результата и не требуют нового кандидата.
Открытые Done-карточки остаются в аудите, не входят в идентичность выпуска.
Возврат и повторная приёмка, изменение результата или согласованной основы
создают следующее поколение той же разрешённой операции до начала внешней
публикации. Manifest хранит состав и доказательства выпуска, SQLite operation и
step receipts — этапы выполнения и ссылки для восстановления. Неизменный повтор
использует те же данные; смена даты не меняет зафиксированную версию.
Startup audit получает working directory каждого release-enabled Workspace прямо
из каталога и поэтому обнаруживает detached primary и linked holder даже при
пустом `release-repositories`, до первого candidate/checkpoint. Такой audit только
читает Git state: clone, checkout, switch и cleanup не выполняются. Для старой
Workspace-записи без working directory используется runtime default project root,
но не исторические thread roots. В injected
Workspace/Release Manager rules и tooltip единственным release checkout указан
`releaseCandidates[].releaseRoot`; прежняя рекомендация обновлять local `main`
или использовать integration worktree удаляется из эффективных Release Manager rules.
Ожидаемый managed `releaseRoot` проверяется даже без checkpoint: orphan clone,
невалидный marker или общий Git common dir дают только `manual_required` и не
усыновляются, не исправляются и не удаляются startup-кодом.
По команде `Релиз` только Stream с `settings.releaseManager=true` создаёт durable
operation, валидирует exact generation, публикует и атомарно закрывает
включённые Tasks. `publish:all` и `publish:changed` отказываются работать из
зарегистрированного Workspace или clone без Agent Hub release marker. Обычный status update может свободно
поставить видимый `done`, но не создаёт deployment evidence.
`hub_task_complete` и финальный текст агента также не создают release evidence.
Отдельного mutable checkpoint owner, freeze-команды или скрытого readiness-состояния нет:
`CHANGELOG.md` остаётся канонической историей, Task владеет workflow, а
`ReleaseOperation` — progress конкретного выпуска.
Hub включает один внутренний MCP `agent_hub` и автоматически подключает его к
запущенным через Hub Codex App Server и Claude Code. На каждый ход в developer-
контекст добавляется подписанная capability текущего Thread; MCP по ней определяет
Workspace и Stream. Данные Stream, правил и релизов другого Workspace остаются
недоступны, а Dashboard Task являются общей сущностью и доступны между Workspace.
Агент может получить собственный контекст, увидеть параллельные Stream и активные
ходы, прочитать ограниченную историю Stream и действующие developer-правила,
создавать, править, переставлять, завершать и удалять общие задачи Dashboard независимо
от их Workspace, читать их вложения
и прикладывать файлы из текущего проекта. `hub_stream_message_send` после явного
`confirm_send: true` отправляет сообщение в другой Stream текущего Workspace через
штатные режимы `queue` или `steer`; источник виден агенту, а в общей истории и
поиске сообщение подписывается `Workspace - Stream` вместо `Вы`. `hub_task_start` после явного
`confirm_launch: true` отправляет ссылку на задачу в существующий либо новый
Stream через обычный контур очереди Hub и только после приёма помечает карточку
начатой. Dashboard Task проходит workflow-статусы `New`, `In progress`, `Testing`,
`Awaiting implementation`, `Done`; запуск переводит её в `In progress`. На
карточке статус показан компактной плашкой серого, синего, жёлтого, оранжевого
или зелёного цвета. Переключатель языка статусов `en|ru` в «Настройках» доски
меняет подписи на `New / InProg / Test / Await / Done` или `Новая / ВРаботе /
Тест / Прим / Готово` и сохраняет выбор в браузере.

Dashboard в режиме «По статусам» показывает Workspace и их сворачиваемые папки слева, как «Диалоги».
Нажатие на имя папки выбирает всю группу, кнопка справа раскрывает её Workspace.
В строке задачи сверху находятся ID, Workspace и поток, ниже — заголовок.
При выборе одного Workspace среднее поле остаётся пустым. Бэклог показан во всех
режимах отдельно от статусных колонок: его задачи в них не дублируются.
У задач Бэклога скрыты плашка статуса и поле статуса в карточке; сохранённое
значение статуса не меняется. Переключатель «По статусам / По воркспейсам»
выбирает статусные колонки или прежнюю группировку по Workspace с Бэклогом
и Заметками. В режиме «По воркспейсам» левый каталог скрыт, показаны все Workspace,
а статус находится справа от потока в верхней строке задачи.
Доступны создание задач и перетаскивание между колонками. Выбор каталога сохраняется
для возврата в режим «По статусам».

По умолчанию режим «По статусам» группирует задачи горизонтальными полосами по
Workspace; заголовки статусов общие и закреплены при вертикальной прокрутке.
Группы можно сворачивать. Заметки образуют отдельную группу, Бэклог остаётся
самостоятельной колонкой без статусов. Настройка «Группировать по воркспейсам»
выключает полосы и возвращает обычные статусные колонки; выбор сохраняется в
браузере. В legacy-виде «По воркспейсам» эта настройка скрыта.
Перетаскивание внутри группы меняет статус; перенос между Workspace выполняется
через левый каталог или карточку задачи. Подложки задач используют цвета темы.
Геометрия статусной доски единая для всех тем: скруглённые подложки сохраняются
у обычных, начатых и закрытых задач; семантические цвета выделяют заголовки статусов.
Плоские списки Pulsar применяются за пределами статусной доски.

«Фильтры» содержат отбор текущих/закрытых задач. Кнопка с иконкой ползунков открывает
настройки: вид доски, язык статусов и способ открытия: «В окне» — модальная карточка по клику,
«Справа» — только боковая панель, «Справа + окно» — панель по клику и стандартная
карточка поверх неё по двойному клику или Shift+Enter. Вид доски и способ открытия
сохраняются в браузере; по умолчанию выбраны «По статусам» и «Справа + окно».
Закрытие модальной карточки в комбинированном режиме
сохраняет панель и текущий черновик. Пока модальная карточка открыта, фон
показывает инертную проекцию панели без второго редактора или DOM-идентичностей.
На узком экране каталог расположен над доской, карточка открывается модально.

Проверка Dashboard и связанных действий:
`node --test tests/public/dashboard-layout-dom.test.mjs tests/public/task-board-drag.test.mjs tests/public/task-board-completed-filter.test.mjs tests/public/task-checklist-dom.test.mjs`.

Переход Task в `Testing` сначала создаёт непустой result commit, интегрирует его
в `dev`, а затем одним CAS обновляет workflow-статус и Git references. Empty diff
возвращается как `no_result`; конфликт или ошибка Git сохраняют прежние статус и
references. `Awaiting implementation` не создаёт новый result: он проверяет уже
принадлежащий Test результат и его интеграцию, включает его в композицию
`PreRelease` и только после успеха фиксирует статус одним CAS. `Done` опирается
на проверенную публикацию и не создаёт результат. `Done` становится
release-completion evidence только после проверенного production-релиза.
Release Manager читает Task-backed план через `hub_release_plan_get`, затем вызывает
`hub_release_run` с точными Task IDs, validation mode и approved targets. После
durable ACK состояние читается через `hub_release_get`; технические ожидания и
исправления выбранной Task автоматически продолжают ту же operation. Каждое
готовое поколение фиксирует принятые результаты, согласованную основу main,
manifest и clean release root. Оно не обновляет тестовый контур из rolling dev.
Штатный source consumer — `node release.mjs run|continue|get|accept --provider
<provider> --thread <thread-id> --stream <stream-id> --request-file <business.json>`.
`accept` передаёт обычный публичный Await-запрос (`task_id`, `status`, `request_id`,
точные `expected_task_revision`/`expected_workflow_status`) и, если нужны разрешения
нескольких native-конфликтов, один `native_resolution_review` с
`bundlePath`, `bundleSha256`, `reviews`. Каждый review содержит исходные
`requestId` и полный authenticated `text`; sequencer проверяет весь набор до
применения. Токен в JSON не передаётся: consumer получает его из действующего
provider/thread/stream. Та же команда дожидается уже запущенной этим принятием
работы release owner; после потери ответа читают исходную квитанцию и operation,
а не создают новый выпуск. Отдельный entry/driver/config на каждый префикс не нужен.
Окончательная фиксация версии/CHANGELOG остаётся частью единого release pipeline. Проверки
тестового контура выполняются по необходимости; настроенные проверки других
репозиториев сохраняются и проверяют именно подготовленный кандидат.
При подготовке Await основа PreRelease берётся из подтверждённой публикации
этого репозитория. Новая основа допускается по сохранённому согласованию точного
результата включённой задачи; обычный fetch и изменение local main/origin/main
сами её не меняют. При отсутствии подтверждённой основы требуется штатное явное
принятие истории публикации. При переходе в Await состав сначала компонуется,
а затем фиксируется Task CAS; конфликт сохраняет задачу в Test и прежний кандидат.
Возврат задачи сохраняет старую принятую интеграцию; проверенная коррекция
создаёт новый result и следующее поколение без удаления исторического dev merge.
После проверки exact revision каждого repository, publication generation и
deployment evidence операция атомарно переводит в `Done` только Tasks, которые
всё ещё называют опубликованный result. Более новая работа не перезаписывается. Обычное
`hub_task_complete` и destructive `hub_task_delete` сначала возвращают точный
cleanup preview/token и требуют отдельного подтверждённого вызова. Complete не
закрывает implementation Task до workflow `Done` и не удаляет неопубликованный
result; Delete удаляет DB-строку только после успешного Git cleanup.
Для служебной Task уже опубликованного релиза Release Manager использует
`hub_task_complete` с `completion_mode=published_release_service`: owner сверяет
все Done-пункты checklist с неизменяемым manifest и durable publication state,
затем закрывает только карточку по preview/token, сохраняя её worktree и историю.
После подтверждённой публикации основной Workspace синхронизируется только
безопасным fast-forward, пока он остаётся на `main`. Если его локальные dirty
пути пересекаются с опубликованными, обновление не является fast-forward либо
инвариант нарушен, релиз остаётся успешным, а primary HEAD и локальные байты не
изменяются; диагностика возвращает `manual_required`.
Курсорная команда
`hub_events_list` без long poll возвращает ограниченную ленту изменений задач,
релизов и завершений ходов текущего Workspace. Изменение Workspace/Stream-правил
применяется к следующему ходу. Все изменяющие MCP-вызовы требуют `request_id`,
атомарно записываются в SQLite и при точном повторе возвращают сохранённый результат
без повторного действия. MCP слушает только случайный loopback-порт, использует
секретный URL и не публикуется через Mini App, Worker или внешний домен.
Codex ограничивает только внутренние вызовы `agent_hub` клиентским deadline в 75
секунд: он оставляет запас после 60-секундного server dispatch timeout, но
останавливает вызов, который завис до HTTP admission. После transport failure
соединение MCP перезагружается; read-only вызов можно повторить, а mutation
сверяется по точному `request_id` с журналом операций и не создаёт второй эффект.
`Закрыть задачу` убирает обычную карточку с активной доски после приёмки заказчиком
либо когда отдельная сдача работ не требуется; release completion закрывает
выпущенные Tasks автоматически.
`Удалить` открывает отдельное подтверждение `Вы уверены?`; карточка закрывается
только после подтверждённого удаления, а при ошибке остаётся доступной для повтора.
Этот авторазбор применяется только к
Telegram-входящим; ручное создание в дашборде его не запускает. Автоматический перенос выполняется только
при уверенности не ниже `taskBoard.autoPlaceConfidence`; неоднозначная запись и
ошибка классификации остаются в `Backlog`. Исходный текст сохраняется отдельно от
исправленного и раскрывается в карточке по ссылке `Показать исходный текст`.
Модель и порог задаются в `config.json` параметрами
`taskBoard.triageModel` и `taskBoard.autoPlaceConfidence`.
Новые отчёты из `Настройки → Обратная связь → Сообщить о баге` можно персонально
добавлять в Dashboard без Spark: укажите имя целевого Workspace в
`taskBoard.bugReportWorkspaceName`. Hub запоминает локальную Git-ревизию и после
следующего `git pull` подхватывает только добавленные `AgentHub/Bugs/bug-*/report.md`;
при первом включении он также импортирует все уже существующие отчёты, не создавая
дубли для ранее сохранённых карточек. Проверка выполняется
раз в пять минут и после локальной отправки отчёта. Пустое значение выключает
функцию. Workspace ищется по имени без учёта регистра и лишних пробелов; если он не
найден, карточка остаётся в `Backlog`.

### Требования компонентов

- Базовый Hub: Node.js 22.5+, Codex CLI либо Claude Code CLI, локальный доступ к разрешённым workspace. Публичный адрес не нужен.
- `telegram`: BotFather token, числовой Telegram user ID и исходящий доступ к Telegram Bot API.
- `mini-app`: всё необходимое для `telegram`, публичный HTTPS-адрес с действующим сертификатом и настроенная кнопка Mini App у бота.
- `android-app`: Android 8.0 / API 26 или новее, установленный APK, публичный HTTPS-адрес Hub и однократное добавление телефона в доверенные устройства. Telegram-аккаунт и Telegram ID не нужны.
- `shared-dashboard-bot`: один централизованно созданный BotFather token и Cloudflare Worker нужны владельцу бота; участникам токен, собственный бот и публичный адрес локального Hub не нужны.

Для прямого входа из Chrome, Edge, Firefox или Safari откройте публичный HTTPS-адрес Hub. На уже авторизованной поверхности выберите `Сервер → Доверенные устройства → Добавить устройство`, затем перенесите одноразовый код в браузер. При включённом Worker все поверхности используют его единый реестр доверенных устройств: код из Telegram Mini App, Desktop или VS Code одноразово принимается как на Worker-, так и на прямом HTTPS-адресе, но после первого успешного сопряжения повторно не действует. Активные устройства из прежнего локального реестра безопасно импортируются перед атомарным переключением. Без Worker реестр остаётся локальным. Доверие относится к одному браузерному профилю и origin Hub: другой браузер, профиль, режим инкогнито или компьютер сопрягается отдельно. Очистка данных сайта удаляет локальный ключ. Любой пользователь с доступом к уже разблокированному профилю браузера получает те же права до отзыва устройства.

Контекстное меню локальной workspace-ссылки всегда показывает `Показать в Проводнике` и `Скопировать файл`. В VS Code и локальном Web UI команды используют native Hub. На удалённом Windows-компьютере с доверенным браузером один раз устанавливается [File Bridge](FileBridge/README.md). Hub выдаёт только короткоживущий одноразовый билет на выбранный файл; обычный browser API не получает постоянного path-based доступа к файлам Workspace. File Bridge принимает билет только от закреплённого HTTPS origin, сохраняет файл в локальный bounded cache и передаёт его Проводнику либо в Windows clipboard как `CF_HDROP`.

Для `mini-app` и `android-app` доступны два варианта внешнего адреса:

1. Субдомен общего `darksanctuary.ru`. Владельцу компонента не нужен собственный домен; маршрут и сертификат настраиваются централизованно. Сейчас общий шлюз работает на домашнем компьютере владельца `darksanctuary.ru`, поэтому такие адреса доступны, пока этот компьютер включён. Ограничение исчезнет после покупки и переноса шлюза на постоянно работающий сервер. Если одновременно настроены прямой HTTPS-шлюз и Cloudflare Worker, кнопка Telegram Mini App использует прямой адрес, а Worker остаётся единым реестром доверенных устройств и транспортом синхронизации.
2. Собственный домен или субдомен. Нужны права на его DNS, публичный IPv4/IPv6 либо внешний reverse proxy, HTTPS-сертификат и маршрут до компьютера с Hub. Такой адрес не зависит от `darksanctuary.ru`; сам Hub или заменяющий его сервер всё равно должен быть включён.

Вторая команда выдаст одноразовую строку `/link XXXX-XXXX`. Отправьте её общему
боту в личном чате. Первая пересылка открывает пачку: следующие пересланные
сообщения, изображения и ваши ответы/уточнения собираются в одну карточку.
Кнопка `✅ Отправить пачку` (или `/done`) закрывает её и отправляет в `Backlog`;
после этого следующая пересылка начинает отдельную карточку. Кнопка
`📤 Отправить раздельно` (`/separate`) создаёт по отдельной карточке для каждой
пересланной реплики, а ответы пользователя остаются уточнениями к сообщению,
на которое он ответил. `🗑 Отменить` (`/cancel`) отменяет пачку до
отправки. Обычный текст вне открытой пачки по-прежнему создаёт самостоятельную
карточку. Изображение, отправленное ответом на собственное исходное сообщение уже
созданной карточки, прикрепляется к ней без новой карточки и без повторного Spark;
вложение показывается на доске и в карточке задачи. Если короткий собственный
комментарий отправлен непосредственно перед пересылкой, следующая пересылка в
течение минуты включает его в пачку; при отправке пачки уже созданная карточка
дополняется и повторно разбирается Spark вместо появления второй карточки.
Текстовый ответ на собственное сообщение уже созданной карточки также добавляется
к ней как уточнение, повторно запускает Spark для объединённого текста и не создаёт
новую карточку; ответы цепочкой на предыдущие уточнения сохраняют ту же связь.
Служебные правила о порядке и авторах передаются только в промпт Spark и
не попадают в текст самой задачи. `/unlink` удаляет привязку. Локальный Hub получает команды только исходящими
HMAC-подписанными long-poll запросами; его входящие порты и Telegram-токен не
публикуются. Если компьютер выключен, сообщение хранится в очереди до 30 дней.
Уведомление `⏳` подтверждает только постановку в удалённую очередь. Подтверждение
`✅` приходит после сохранения задачи локальным Hub; ошибка приёма приходит как
`⚠️`. Уведомления отвечают на исходное сообщение либо карточку отправленной пачки.
Недоставленный итог сохраняется вместе с командой и повторяется после временной
ошибки Telegram и перезапуска Worker, без повторного создания задачи. Если Telegram
принял уведомление, но потерялся его ответ, возможно повторное уведомление.
Старые завершённые команды без сохранённого состояния доставки автоматически
не переотправляются.
Если постановка пачки оборвалась без подтверждения, через пять минут она выходит
из состояния отправки: те же кнопки снова позволяют безопасно повторить действие
или закрыть зависшую пачку. Повтор использует прежний `sourceKey`, поэтому уже
принятая Dashboard задача не создаётся второй раз. Новая пересылка не подмешивается
в такую пачку молча, а бот явно просит сначала повторить отправку или отменить её.

При подготовке runtime с production-зависимостями установщик выполняет

неопубликованной сборки. Пакет и его зависимости входят в проверяемый manifest;
dev-зависимости и `node_modules` исходного checkout не переносятся. Ошибка
установки оставляет текущую работающую версию неизменной.

Для сопровождающего полная публикация всех поверхностей выполняется одной
командой из `Utilities/AgentHub`:

```powershell
npm run publish:all
```

Команда сама выполняет полный набор проверок исходников, unit-тестов, процессных
E2E и тестов расширения VS Code — отдельно запускать их перед публикацией не
нужно. Перед `npm run publish:all` не запускайте вручную `npm run check`,
`npm test`, `npm run test:e2e` или тесты расширения: это только повторит уже
встроенный прогон. Полный gate не останавливается на первом тестовом файле:
он собирает ошибки всех групп и возвращает их одним отчётом. Успешные файлы
checkpoint-ятся по содержимому самого теста, его локальных импортов и исходников
релиза, поэтому исправление одного устаревшего assertion не повторяет уже
пройденные независимые файлы. Файлы с доказанно раздельными временными Git,
lock, port и browser-profile ресурсами выполняются не более чем по два; без
такой декларации файл остаётся эксклюзивным. Параллельный режим включается
только при запасе CPU и памяти, а причина промаха кэша печатается без значений
окружения. Затем команда публикует Cloudflare Worker, создаёт и активирует
runtime-релиз, устанавливает локальное расширение VS Code и через защищённый
локальный control channel запрашивает штатный перезапуск Agent Hub.
Если выполняются активные задачи, сервер сам откладывает перезапуск до
безопасного момента. Для локальной отладки доступны параметры `--skip-tests`,
`--skip-worker` и `--skip-restart`; обычная публикация использует полный набор.
Для Workspace-релиза используйте `publish:changed` из управляемого release clone.
Команда читает его manifest только для авторизации состава и становится тонким
клиентом одной durable ReleaseOperation. Application owner создаёт изолированное
immutable generation, запускает проверки и публикацию через стабильный runner,
сверяет эффекты и завершает только точные опубликованные Tasks. Низкоуровневый
`publish:all` без Workspace-адаптера сообщает только `published`: это публикация
поверхностей, а не завершённый Workspace-релиз.

Релиз-менеджер готовит одну общую запись `CHANGELOG.md` в PreRelease: включённые задачи
указываются кликабельными ссылками с кратким описанием, обычно из названия. Для
крупных задач добавляются основные изменения из чек-листа, а при его отсутствии —
из результата. В ветках задач CHANGELOG не ведётся и версия вручную не повышается.
Механизм публикации назначает версию по правилам Workspace; общий процесс не
навязывает другим продуктам формат Hub.

Для Agent Hub базовая версия хранится в `package.json` в формате CalVer, например
`2026.8.25`. Стабильный runner при фиксации operation generation сам приводит её
и обе записи `package-lock.json` к локальной календарной дате и коммитит вместе
с CHANGELOG до финальных проверок. Повтор той же operation сохраняет
зафиксированные версию, manifest и candidate даже на следующий день.
Отдельные `release:version` и `publish:all` сохраняют прежнюю проверку календарной
версии; они не заменяют штатный Workspace pipeline. Каждый развёрнутый runtime
получает дополнительный последовательный номер внутри календарного дня: первый
релиз показывается как `v2026.8.25.1`, следующий — `v2026.8.25.2`. Счётчик
восстанавливается по сохранённым runtime-манифестам; прежний манифест без суффикса
считается первым релизом дня. Полная версия показывается на странице «Сервер»,
публикуется через MCP и записывается в runtime-manifest и диагностику. Версия VS Code Extension
остаётся отдельной, потому что расширение выпускается независимо. Номер runtime
резервируется при подготовке артефакта и сохраняется при повторе того же выпуска;
`releaseId` остаётся отдельным
техническим идентификатором конкретного immutable runtime.

Каждый процесс HUB публикует новый `instanceId`, а каждый неизменяемый runtime —
свой `releaseId`. Это технические идентификаторы экземпляра и развёртывания, а
не номер версии продукта. При остановке сервер закрывает SSE, long-poll, named pipe и
локальные HTTP-подключения. После запуска клиенты переподключаются к новому
экземпляру; при смене именно релиза Web App, Mini App и панель VS Code загружают
новую оболочку. Набранный текст и цитаты перед перезагрузкой сохраняются.
Перезагрузка откладывается, пока пользователь вводит сообщение, открыто модальное
окно, выполняется отправка или в любом черновике остаются ещё не отправленные
вложения, потому что браузер не имеет права молча восстановить выбранный файл.
Android при обнаружении нового экземпляра дополнительно проверяет manifest APK.

Публикация сверяет готовность с точным `current`: новый control endpoint должен
отвечать от того же release и PID, что готовый runtime-lock. Если Hub был
остановлен, публикация проверяет манифест и установленный launcher и запускает
его один раз. Неопределённый результат запроса рестарта не вызывает второй
запуск. Настройка автозагрузки при публикации сохраняется; отсутствующий после
карантина ярлык восстанавливается отдельно штатным включением автозапуска.

После первой полной публикации последующие локальные изменения можно выпускать
выборочно:

```powershell
npm run publish:changed -- --stream <stream-id> --thread <thread-id>
```

После durable ACK стабильный worker сравнивает generation commit с последней
успешно опубликованной ревизией и собирает только затронутые поверхности. Общие Web UI-файлы обновляют
runtime и Worker без повторной Android-сборки; Android, Desktop и VS Code
собираются только при изменении их собственных исходников. Неизвестный путь
автоматически возвращает полный безопасный сценарий. Для самой первой выборочной
публикации допустимо явно задать уже опубликованный commit:
`npm run publish:changed -- --stream <stream-id> --thread <thread-id> --from <commit>`. Время каждого этапа печатается в
консоль. Авторитетное состояние читается через `hub_release_get`; журналы
дочернего стабильного runner сохраняются как step evidence, а не как второй
release owner. Поэтому потеря PTY не требует нового request ID или повторения
неизвестно завершившегося эффекта. Изменение исполняемого кода проходит синтаксическую проверку, весь
unit-набор и межповерхностный процессный E2E. Параллельные публикации из разных
worktree сериализуются общим lock, а checkout старее текущего `main` не может
перезаписать уже опубликованный runtime.

До замены установленного runtime все предустановочные проверки плана — freeze,
prepare и проверка перед Git-публикацией — выполняет стабильный current-owner
runner над точным candidate root. Код кандидата поставляет проверяемые байты, но
не подменяет transition executor. Несовместимая схема или дрейф плана
останавливают публикацию до внешних эффектов. Установленный owner завершает
подтверждённую публикацию и финализирует Task.
Устаревший параметр `--bootstrap-mcp-context` отклоняется явно.

Один исполнитель поддерживает три явно различимых режима:

- `npm run publish:changed -- --stream <stream-id> --thread <thread-id> --full-tests` (или `--validation=full`) — полный
  контрольный прогон. Smoke замороженного кандидата выполняется до дорогих тестов.
- `npm run publish:changed -- --stream <stream-id> --thread <thread-id> --validation=focused` — проверки и сборки по
  затронутым поверхностям; неизвестные пути требуют полного набора.
- `npm run publish:changed -- --stream <stream-id> --thread <thread-id> --quick` — явно запрошенная быстрая публикация
  без тестового gate. Проверки идентичности кандидата, Git, deployment и готовности
  runtime сохраняются. Неизвестные пути расширяют сборку до всех поверхностей,
  но не переключают явно выбранный quick на полный тестовый режим.
  Команда не подменяет согласие пользователя на этот режим.

Первый ACK сообщает `operationId`. `npm run publish:changed -- --status --operation <operation-id>` читает исходный durable result,
а `npm run publish:changed -- --resume --operation <operation-id>` продолжает именно его сохранённое поколение,
режим и step receipts, даже если текущий Thread или CLI-флаги сменились. `--resume` без исходного ID не создаёт новую операцию.
Git перед deployment всегда проверяется заново: точный
уже опубликованный SHA не отправляется повторно, движение `origin/main` блокирует
продолжение. Изменение состава или исходников требует нового кандидата.
Штатный pipeline после проверок подготавливает необходимые артефакты Android,
Worker, runtime и расширения **до Git push**, затем применяет именно их. Подготовка
runtime не переключает работающую версию; Worker публикуется из готового bundle.
При повторе проверяются сохранённые файлы и фактически установленные компоненты.
Подтверждённый потерянный ответ не приводит к повторной установке или загрузке.
Если исход уже начатой установки нельзя подтвердить, повтор останавливается с
причиной; отметка этапа сама по себе не доказывает установленный результат.
Артефакты и их хеши сохраняются до завершения восстановления. После выполнения
deployment повтор продолжает проверку результата, readiness и финализацию.
Старый незавершённый прогон, уже дошедший до deployment без этих артефактов,
завершается прежним исполнителем; готовая стадия финализации совместима.
Ожидание штатного restart имеет статус `awaiting_restart`, частичная финализация —
`awaiting_finalization`; ни один из них не является успехом. Новый готовый runtime
сам продолжает pending-финализацию под общим publication lock, без повторной
сборки, отправки Git или deployment. Успех Workspace-релиза — `succeeded`.
При отложенном безопасном рестарте команда возвращает агенту явный handoff
`yield_current_turn`: текущий ход заканчивается без новых операций, а сам
рестарт по-прежнему выполняет существующий safety gate.

Файловый кэш тестов версии 2 сохраняется после полного прогона и публикации
до 30 дней (не более 2000 результатов). Переиспользование требует совпадения
содержимого теста и доказанных зависимостей, runner/policy, Node/ОС/архитектуры,
lockfiles, параметров и хэша окружения. Значения окружения в кэш не записываются.
Динамические файловые/процессные входы без явного описания не кэшируются.
Неуспешный файл автоматически не повторяется. Полный тестовый этап ограничен
двумя часами и десятью минутами без stdout/stderr; истечение срока — ошибка,
а не доказательство отсутствия побочного эффекта.

Автоматическая Git-публикация сейчас поддерживает один репозиторий в Workspace.
Для старого frozen manifest без Workspace требуется `--workspace <id>` либо
повторное замораживание; старые журналы без точного completion draft автоматически
не завершаются. Кэш прежнего формата не считается доказательством прохождения.

`runtime:deploy` создаёт новый неизменяемый release и атомарно переключает `current.json`, сохраняя предыдущую версию для `npm run runtime:rollback`. CLI сравнивает физические пути точки входа, поэтому эти команды и `send-message.mjs`/`send-images.mjs` корректно запускаются также из workspace, открытого через Windows junction. Команда `runtime:activate` один раз переносит конфигурацию, данные и модели из рабочей папки во внешний runtime, создаёт маркер активации и удаляет старый workspace-`config.json`. Выполняйте её только при остановленном старом боте; для живой установки сначала дождитесь завершения ходов.

Текущий runtime можно проверить через `npm run runtime:status`. После активации `/restart` запускает release, указанный в `current.json`, поэтому новая публикация начинает действовать при следующем штатном рестарте. Автозапуск Windows также указывает на внешний launcher. В Windows фоновый запуск выполняет `AgentHub.RuntimeHost.exe`: он самостоятельно проверяет `current.json`, runtime-manifest и SHA-256 файлов, а затем напрямую запускает `node.exe` без VBS, `wscript.exe`, скрытого PowerShell и `ExecutionPolicy Bypass`. При первом успешном запуске Runtime Host удаляет прежние `launch.vbs`, `runtime-launch.vbs` и `launch.ps1`.

После `runtime:deploy` установите пользовательские `UserPromptSubmit`- и `Stop`-hooks командой `npm run hook:install` и проверьте `npm run hook:status`. Установщик атомарно копирует launcher из текущего неизменяемого runtime-релиза в постоянный путь `%USERPROFILE%\.codex\agent-hub-hooks`; поэтому заблокированный работающим сервером стабильный Runtime Host не может оставить hooks на старой версии. Статус сверяет точную команду и содержимое установленной копии с текущим release, а также показывает последние фактически принятые start/stop-вызовы. Первый hook до начала модели сразу сохраняет точный запрос, а затем дополняет ту же запись Git-baseline; повторная фаза объединяется с первой и не может стереть уже сохранённые данные. Если клиент Codex не вызывает hook, постоянно работающий terminal-аудит замечает активный ход по rollout и сам создаёт Git-baseline; `apply_patch` дополнительно сохраняется как резервный diff. Второй hook в конце передаёт статус, usage и данные rollout; ошибка чтения rollout обозначается как `unknown`, пока terminal-аудит не уточнит результат. Установщик аккуратно объединяет `%USERPROFILE%\.codex\hooks.json` с существующими hooks. Codex требует отдельно просмотреть и доверить новые или изменившиеся hooks через `/hooks`; доверие привязано к их точному содержимому. После обновления launcher подтвердите оба Agent Hub hook, затем перезапустите Agent Hub Server, а открытые клиенты Codex — переоткройте.

Если Task workflow остался с неизвестным результатом из-за недоказанного завершения дерева Git-процессов, обычный повтор и новый `request_id` запрещены. Release Manager использует `hub_task_operation_reconcile`; для локального cutover до установки исправленного runtime доступна та же операция через `npm run task:reconcile-operation -- --workspace <id> --task <id> --operation <request-id> --repository <root> --guard <guard-id> --summary <evidence> --confirm-system-restart`. Для guard без сохранённой process identity команда принимает только проверяемую границу: `Win32_OperatingSystem.LastBootUpTime` должен быть позже времени создания guard. Доказательство записывается до снятия guard. Если lifecycle уже имеет точный terminal outcome/rollback/failure, guard и restart proof не требуются: та же команда вызывается только с `--workspace`, `--task`, `--operation` и `--repository` и завершает исходный receipt без Git replay. Для receipt, созданного one-shot Await cutover, команда также получает точные исходные `--expected-task-revision`, `--expected-workflow-status`, `--cutover-source-commit` и `--cutover-projector-sha256`; для cross-Task cutover к ним добавляются `--cutover-source-task` и `--cutover-source-task-revision`. Все поля сверяются с durable prior Task/evidence и исходным полным arguments hash. Exact arguments hash связывает reconciliation с фактическим target workflow status (`Test`, `Await` или другим поддерживаемым переходом), а текущие status и revision доказывают отсутствие Task CAS. Операция под Task/repository locks либо продолжает исходный pending lifecycle, либо без Git replay завершает исходный MCP receipt по уже записанному точному outcome/rollback/failure; смешанное состояние остаётся `unknown`.

Если Await блокирует дефект уже исправленного, но ещё не установленного release-проектора, единственный владелец перехода может выполнить one-shot cutover из чистого принятого Task checkout: `npm run task:await-cutover -- --workspace <id> --stream <id> --provider <provider> --thread <id> --task <id> --request <new-request-id> --repository <root> --expected-task-revision <n> --expected-source-commit <sha> --expected-projector-sha256 <sha256> --confirm-cutover`. Если сначала нужно принять другую Task-зависимость, добавляются `--source-task <id> --expected-source-task-revision <n>`: код загружается из результата source Task, а статус и release membership меняются только у `--task`. Команда до открытия production stores сверяет чистый checkout, точный `HEAD` и SHA-256 resolver, затем под детерминированно упорядоченными блокировками обеих Tasks повторно проверяет source Task, её Test revision, единственный result commit, checkout и актуальные Workspace/Stream repository settings. Начало lifecycle в той же SQLite-транзакции атомарно фехтует target и source Task, обе Stream, оба repository root, source result reference и включённый release workflow. Pending reconciliation переносит исходную immutable source identity в terminal outcome. После этого команда вызывает обычный `hub_task_status_update` через текущий `HubMcpService`. Она сохраняет MCP receipt, Task/repository/Await locks, lifecycle CAS, snapshot/dev integration, полный rebuild плана и rollback/unknown semantics. Startup reconciliation других операций отключается только в этом one-shot процессе; новый request нельзя повторять после неопределённого исхода.

Для доставки независимо проверенного native Git owner до установки этот же CLI поддерживает `--initial-native-test --confirm-cutover` с обычными `--workspace`, `--stream`, `--provider`, `--thread`, `--task`, `--request`, `--repository`, `--expected-task-revision` и exact pins: `--expected-source-commit`, `--expected-source-tree`, `--expected-source-branch`, `--expected-main-commit`, `--expected-dev-commit`, `--expected-publication-sha256`, `--expected-candidate-sha256`, `--expected-plan-revision`, `--expected-runtime-sha256`. Projector/squash/source-Task аргументы с этим режимом не смешиваются. Source проверяется до stores; Task должна принадлежать current caller/Thread и оставаться Progress с пустыми refs. Existing preflight `initialNativeTestState` и readonly `inspectInstalledNativeTestOwner` дают hashes без изменения состава. Выполняется обычный canonical Test с original receipt, lifecycle/native intent и существующими leases. Текущий prepared candidate не меняется; дальнейший Await обычный. Когда verified active installed owner предоставляет native status, новые bootstrap admissions закрыты. Повтор exact команды с тем же request восстанавливает только исходный результат/UNKNOWN через existing reconciliation, даже после Test или установки owner; новые request IDs, обход guard и ручной exported runtime helper для production stores запрещены. Production install/restart/push/publication этим source cutover не выполняются. Focused tests: `node --test --test-concurrency=1 tests/interfaces/cli/initial-native-test-cutover.test.mjs tests/interfaces/cli/task-await-cutover.test.mjs`.


Для единственного bootstrap уже проверенного squash-результата эта же команда
принимает `--squash-bootstrap` и полный набор exact-полей: source Task/revision,
clean-before/new-result/dev-after tree, ожидаемые source/main/dev/preserved trees,
пути и SHA-256 ZIP/bundle/manifest/files. Первый запуск без
`--confirm-cutover` возвращает два hash и ничего не меняет. Подтверждение имеет
новый `--request` и добавляет `--proof-request`, оба `--expected-*-hash` и
`--confirm-cutover`. Обычный публичный squash остаётся Test→Test; bootstrap
принимает Progress survivor с прежним Test result и фиксирует новый Test только
после полного Git readback. После него отдельно обязателен обычный Test→Await и
успешная сборка candidate.

При доказанном расхождении принятого локального `main` и опубликованного
`main` Release Manager может провести отдельный выбранный Test через
`hub_task_status_update`: `status=testing`, `expected_workflow_status=in_progress`,
точная ревизия Task, `selected_proof_bundle_path`, SHA-256 bundle и
`selected_proof_commit`. Первый `request_id` возвращает read-only
`previewHash`. Подтверждение с новым `request_id` передаёт исходный
`selected_preview_request_id` и `expected_selected_preview_hash`; оно связывает
актуальные Task/dev/publication/remote с проверенными родителями, конфликтными
blob и деревом композиции. Неизвестный исход восстанавливается только через
`hub_task_operation_reconcile` с исходным operation ID и теми же exact-полями.
Task-result остаётся отдельным от dev-композиции: кандидат выпуска проверяет
только выбранную дельту Task на опубликованной базе. Путь ограничен обычными
файлами и не даёт разрешения на произвольный merge, ручное изменение refs или
принятие новой удалённой вершины.

Для поглощённого результата Progress используется тот же selected Test.
Дополнительное `selected_absorption_handoff={requestId,text}` ссылается на
успешную аутентифицированную квитанцию исполнителя исходной Task: точное JSON
подтверждение saved/stopped связывает обе карточки, source revision/base/commit/tree
и ordered parents реального автоматического merge. Полные требования и
незавершённая нативная связь должны быть сохранены; обе own histories и текущий
исходник перепроверяются перед эффектом. См. ADR-0105 и REL-001.
При UNKNOWN передаются те же поля, либо
`--selected-absorption-handoff <json-file>` в существующий reconcile CLI.
Настоящий конфликт по-прежнему требует reviewed resolution; установка Hub
не заменяет эту проверку и не закрывает исходную карточку автоматически.

Для ручной настройки используйте `%LOCALAPPDATA%\AgentHub\config.json`. Путь к другому конфигу можно передать через `AGENT_HUB_CONFIG`, а токен — через `TELEGRAM_BOT_TOKEN`.

После активации workspace-команды `send-message.mjs` и `send-images.mjs` не читают Telegram-токен. Они передают только разрешённую операцию, аргументы и идентификатор вызывающей AI-сессии в локальный IPC живого runtime; уже доверенная release-копия выполняет отправку. Получатель повторно сверяется с allowlist, `cwd`, `--message-file` и изображения обязаны находиться внутри настроенных проектов, а окружение runtime очищается от чужих Codex/Claude session ID. Если sandbox запрещает named pipe, используется token-free файловая очередь в системном temp с теми же серверными проверками. `config.json` получает отдельный Windows ACL без доступа `CodexSandboxUsers`.

### Отправка сообщения из скрипта

Отдельный процесс может отправить владельцу сообщение через локальный IPC того же бота:

```powershell
node send-message.mjs "Обработка завершена"
```

То же через npm:

```powershell
npm run send -- "Обработка завершена"
```

Текст можно передать через stdin; для нескольких разрешённых чатов укажите `--chat-id <id>`. Параметр `--silent` отправляет уведомление без звука. Скрипт делит текст длиннее лимита Telegram на несколько сообщений и не выводит токен в командную строку или журнал.

Из Windows PowerShell 5.1, фонового watcher или `.ps1` с русским текстом безопаснее передавать сообщение через UTF-8-файл. Это не даёт PowerShell перекодировать кириллицу в аргументах запуска:

```powershell
Set-Content -LiteralPath notification.txt -Encoding UTF8 -Value "Обработка завершена"
node send-message.mjs --bind-current --category done --message-file notification.txt
```

`--message-file` взаимоисключаем с текстом в командной строке. Отправщик также отклоняет текст, похожий на повреждённый UTF-8 (`РўСЂ...`), вместо публикации битого уведомления.

Чтобы ответ на уведомление автоматически вернул бота к текущему потоку, отправьте его с привязкой:

```powershell
node send-message.mjs --bind-current --category action "Нужен ваш ответ"
```

`--bind-current` определяет вызывающую AI-сессию по точному идентификатору: `CODEX_THREAD_ID` для Codex или `CLAUDE_CODE_SESSION_ID` для Claude Code. Он не использует выбранный в боте поток как неявный fallback: если идентификатора вызывающей сессии нет, отправка завершается ошибкой до обращения к Telegram. Это исключает привязку уведомления из VS Code/CLI к чужому потоку, оставшемуся активным в `data/runtime.sqlite`.

Финальный ответ отдельно регистрировать не нужно. Для Codex Agent Hub получает полный финальный ответ, запрос, статус и usage из rollout точного `turnId`; для Claude те же поля читаются из локального JSONL-транскрипта, а денежная оценка нового управляемого хода — из итогового результата Claude CLI. Telegram работает в режиме ответа: прогресс, подтверждения и полный финал доставляются только для ввода, полученного самим ботом. Ходы, начатые через Desktop, Web, Mini App, Android или расширение VS Code, остаются видимыми в общем журнале и интерфейсах HUB, но автоматически в Telegram не дублируются. Явное `👀 Показать сообщение` подключает Telegram к выбранному живому ходу до его завершения. `send-message.mjs` сохраняется для намеренной ручной отправки отдельных уведомлений; отдельного автоматического end-of-turn API нет.

Фоновый terminal-аудит хранит в `runtime.sqlite` время последнего полностью завершённого обхода, байтовую позицию каждого append-only rollout и начавшиеся ходы без терминального события. После перезапуска он постранично читает все основные и дочерние треды, изменившиеся после сохранённой границы, и продолжает каждый файл с последней полной JSONL-строки. Если клиент остановил ход без записи `turn_aborted` или `task_complete`, аудит сверяет сохранённый точный `turnId` через `thread/read` и восстанавливает статус, usage и журнал. Статус `interrupted` отдельного App Server не считается завершением, пока lifecycle точного хода остаётся активным в rollout; это защищает длительные инструменты и автоматическое сжатие контекста от ложной остановки. Если ранее созданная предварительная terminal-запись противоречит возобновившейся активности того же `turnId`, аудит удаляет её из ledger и снимает отметку доставки до настоящего завершения. Расход субагента записывается по его точному `threadId + turnId`, по цепочке `parentThreadId` относится к корневой задаче и показывается отдельным ходом с префиксом `Субагент ·`; поэтому видимые ходы полностью объясняют итог задачи. Fork-rollout субагента содержит унаследованную историю родителя, но аудит отбрасывает ходы, чей UUIDv7 старше самого дочернего треда; ранее ошибочно записанная унаследованная история автоматически удаляется из ledger с сохранением в quarantine-файле. Фиксированного окна восстановления и лимита общего количества проверяемых тредов после первичной миграции нет; размер `thread/list` ограничивает только одну порцию. При обновлении со старой версии или при изменении правил учёта аудит один раз обнаруживает все обычные и дочерние rollout-файлы в активных `sessions` и `archived_sessions`, включая не возвращаемые App Server. Перед повторной сверкой создаётся проверенная SQLite-копия `journal.sqlite` в `data/migrations`. Каждый файл потоково разбирается один раз в отдельном worker thread; готовые данные всех его ходов возвращаются основному процессу без повторного чтения многогигабайтного rollout для каждого `turnId`. Версия алгоритма, очередь файлов и итог прогресса сохраняются после каждого шага, поэтому уже завершённая старая миграция не блокирует новую, текущая продолжается после рестарта, а обработка интерфейса не ждёт файлового сканирования. Изменившийся usage сохраняет прежний sync-`eventId`, но получает новый `observedAt`; поэтому уже установленный VDS принимает исправление как новую версию того же хода, а не как дополнительный расход. Неизменившийся повторный проход время версии не сдвигает. Для архивной цепочки родителей используется файловый `session_meta`; брошенный незавершённый ход старше 30 минут восстанавливается как отменённый. Повтор после сбоя безопасен благодаря дедупликации по `threadId + turnId`.

Компонент `components.codexContextCleanup` временно недоступен на всех
установках, пока механизм очистки переосмысливается. Runtime принудительно
нормализует старые значения `components.codexContextCleanup` и
`codexRolloutContext.enabled` в `false`; фоновый проход и очистка после свёртки
не запускаются. Настройка остаётся видимой, но недоступной в интерфейсе, чтобы
её назначение и временный статус не потерялись. Параметры прежнего механизма,
включая `codexRolloutContext.scanIntervalSeconds`, пока сохраняются для
совместимости. Ручная диагностика без изменения файла:
`node src/providers/codex/codex-rollout-context.mjs inspect <rollout.jsonl>`; ручное применение:
`node src/providers/codex/codex-rollout-context.mjs sanitize <rollout.jsonl>`.

Все настроенные проекты записываются в единую личную SQLite-базу `data/journal.sqlite`. В ней канонически хранятся журнальные записи ходов, каталог задач, сообщения, usage и история лимитов; HTML начальной страницы, старых дней и отдельных ходов является перестраиваемой проекцией в той же базе. Интерфейсы читают SQLite напрямую и не зависят от файла в открытом workspace. Codex rollout и Claude transcript остаются первичными источниками повторного восстановления истории. Redis, отдельный сервер БД и нативные npm-модули не требуются.

Журнал полностью принадлежит Agent Hub Server. Сервер находит задачу по `provider + threadId`, а ход — по точному `turnId`. В SQLite сохраняются название задачи, начало и завершение, пользовательский запрос, полный финальный ответ, diff, изменённые файлы, usage, модель и service tier. Запись и backfill выполняются транзакционно; журнальная HTML-проекция обновляется после изменения канонических строк. В компактный журнал и Mini App выводятся запрос, полный ответ и метрики; diff и список файлов остаются в канонической записи и подгружаются только по запросу. Заголовок хода получается детерминированно из финального ответа без дополнительного обращения к модели. Технические контейнеры IDE удаляются из отображаемого запроса; для `response-annotations` журнал показывает комментарии пользователя и отдельный текст `My request`, не служебную JSON/XML-обёртку. Ход фиксируется даже при временно недоступном usage; последующее событие дополняет ту же запись. Каждые пять минут сервер читает `account/rateLimits/read` для Codex и `/usage` для Claude и сохраняет полный ответ вместе с нормализованными рядами в индексированную таблицу `rate_limit_snapshots`. Старые `rate-limits-raw.jsonl` и `rate-limits.csv` однократно импортируются, архивируются и удаляются. Текущие остатки Codex, Spark и Claude показываются одной горизонтальной строкой сверху в настройках и статистике; компактная шапка интерфейса остаётся без лимитов. Для завершённого `imagegen` без отдельного image-usage сохраняются число генераций и исходная оценка `90 cr` на генерацию, но до калибровки реальной цены эта оценка не входит в учётный расход. Скрытые ходы для замера контекста не создаются. Существующая история и измеренный расход сохраняются; текст прежних маркеров обрабатывается как обычный текст. В дневном журнале все ходы любого Stream относятся непосредственно к Workspace и входят в его общий расход. Workspace и вложенные Stream раскрываются той же нативной механикой, что прежние группы Thread; ссылка заголовка Stream открывает его текущий Thread, а ссылка каждого хода адресует точные `threadId + turnId`. Название Stream также остаётся компактной меткой в заголовке каждого хода. Настройка `Сворачивать все потоки` массово закрывает только Stream; Workspace сохраняют собственное ручное раскрытие. Настройка подхватывает прежнее сохранённое значение, а новая оболочка преобразует старую серверную Workspace-разметку до перезапуска Runtime. Субагенты представлены рекурсивным деревом под породившим их ходом с префиксом `Субагент ·`; вложенные субагенты образуют следующие уровни, а их расход входит в итог Workspace. Кредиты масштабируются по SI (`cr`, `kcr`, `Mcr`, `Gcr`).

Карточки текущих лимитов и текстовый `/status` всегда показывают окно `primary`
для Codex и Spark. Окно `secondary` остаётся отдельной серией полного графика
истории и не подменяет значение в текущей карточке.

Для Claude стабильным `turnId` журнала служит UUID пользовательского сообщения из транскрипта, поэтому повторное чтение и исторический backfill не создают дубли.

Историю лимитов, предшествующую запуску пятиминутного опроса, можно восстановить из обычных и архивных rollout без обращения к модели: `npm run rate-limits:backfill` показывает план, а `npm run rate-limits:backfill -- --apply` дописывает отсутствующие пятиминутные интервалы в SQLite и перестраивает оба совместимых экспорта. Повторный запуск безопасен: уже существующие снимки пропускаются.

Для полной реконструкции старого журнала используйте `npm run work-log:backfill -- --through YYYY-MM-DD` сначала без `--apply`. Команда потоково читает активные `%USERPROFILE%\.codex\sessions` и архивные `%USERPROFILE%\.codex\archived_sessions`, объединяет дочерние ходы с корневой задачей и отбрасывает унаследованные дубли fork-rollout. Применение сохраняет не-Codex и более новые записи, транзакционно заменяет выбранную историю в `journal.sqlite` и предварительно создаёт резервную копию базы в `data/migrations/<timestamp>`.

После реконструкции команда `npm run work-log:title-backfill -- --through YYYY-MM-DD` пакетно заменяет только шаблонные заголовки `Ход завершён` и `Ход отменён` содержательными названиями по сохранённым запросам и ответам. По умолчанию используется `gpt-5.6-terra` с низким reasoning; модель, effort и размер пакета задаются параметрами `--model`, `--effort` и `--batch-size`. Результат каждого пакета атомарно сохраняется в `data/migrations/work-log-generated-titles.json`, поэтому прерванную генерацию можно продолжить той же командой. Сначала проверьте кэш без записи; `--apply` требует полный набор заголовков, создаёт резервную копию `journal.sqlite`, затем транзакционно обновляет записи и проекцию. Пустые или чисто служебные ходы сохраняют статусный заголовок.

Все завершённые ходы каждого изменившегося transcript Claude автоматически и одной пакетной операцией добавляются в SQLite при обновлении каталога задач; повторный аудит безопасен благодаря ключу `provider + sessionId + UUID пользовательского сообщения`. Для ручной проверки и восстановления остаётся команда `npm run work-log:claude-backfill`: без `--apply` она только показывает план, с `--apply` аддитивно переносит завершённые ходы из `%USERPROFILE%\.claude\projects`, дополняет ранее импортированные записи расчётными кредитами, использованными навыками и завершёнными MCP-вызовами и сначала сохраняет резервную копию базы в `data/migrations/claude-<timestamp>`. Когда в транскрипте нет итогового `total_cost_usd`, Agent Hub рассчитывает API-эквивалент по модели и сохранённым категориям токенов: обычному входу, cache write 5m/1h, cache read и выходу. Для управляемых ходов точная CLI-оценка по-прежнему имеет приоритет.

### Web App, Mini App и VS Code

Компонент `mini-app` включается через `--enable-component mini-app`, требует включённый Telegram и публичный HTTPS-адрес. Для него применимы оба описанных выше варианта: субдомен общего `darksanctuary.ru` либо собственный домен. В первом варианте доступ сейчас зависит от включённого домашнего компьютера владельца общего домена; после переноса шлюза на сервер зависимость исчезнет.

Agent Hub поднимает общий адаптивный интерфейс на loopback-адресе `127.0.0.1:8787`, когда включён `mini-app` или `android-app`: слева находятся задачи с активностью, временем и готовностью ответа, справа — история и живой чат, а журнал открывается отдельной вкладкой. Интерфейс не доступен по Wi‑Fi/LAN. Открывайте его командой `npm run open:web`: она один раз передаёт браузеру защищённый локальный ключ, обменивает его на HttpOnly/SameSite-сессию и сразу удаляет ключ из адресной строки. Прямое открытие URL без такой сессии не даёт читать задачи или выполнять команды. Композер поддерживает до восьми файлов по 20 МБ каждый, Ctrl+V, перетаскивание, несколько аннотаций и меню `/`; изображения показываются миниатюрами, остальные файлы — карточками с именем и типом. У каждой выбранной цитаты есть отдельный комментарий, а обычное поле ввода остаётся общим запросом ко всему набору. На desktop цитата добавляется правой кнопкой мыши, в Android — действием `Цитировать` в штатном меню выделения. Отправленные цитаты показываются отдельными карточками без служебной JSON/XML-обёртки. Ответы и reasoning безопасно отображаются как Markdown. Полнотекстовый поиск находит задачи, запросы, ответы, файлы и даты и открывает точный ход. Лента хода сохраняет порядок reasoning-блоков, а команды, изменения файлов, инструменты, поиск, субагентов, подтверждения и свёртку контекста собирает в один раскрываемый блок внизу хода.

Левый каталог Workspace поддерживает именованные папки; идея и постановка этой пользовательской группировки принадлежат [ZeroFakt](https://github.com/ZeroFakt). Кнопка папки рядом с `+` создаёт самостоятельную пустую папку и не перемещает активный Workspace; повторные нажатия добавляют новые папки. В форме нового Workspace можно сразу выбрать одну из папок либо оставить `Без папки — общий список`. Перемещение Workspace между папками и возврат в общий список выполняются через контекстное меню; drag-and-drop для Workspace отключён. Контекстное меню заголовка папки позволяет переименовать её одной атомарной операцией, включая размещённые в ней активные и архивные Workspace; имя существующей папки повторно использовать нельзя. Имя папки у размещённого Workspace хранится в его общих настройках и синхронизируется между Web App, Mini App и VS Code. Каталог пустых папок и их раскрытие остаются локальным предпочтением конкретного интерфейса.

Пользовательский Workspace удаляется через контекстное меню только после точного ввода его имени. Hub не копирует чаты и Streams: он помечает исходную строку Workspace двумя компактными SQLite-метками времени, исключает связанную иерархию и Dashboard Tasks из активных проекций и показывает её в архиве. В течение трёх дней Workspace восстанавливается с прежними Streams, Threads, настройками и задачами. По истечении срока каталог Workspace удаляется каскадом; проверка срока использует частичный индекс и выполняется вместе с обычным чтением каталога. System Workspace и Workspace с активным ходом архивировать нельзя.

Исходники этой общей оболочки находятся в `assets/web-app`, а имя компонента
`mini-app` сохранено только для совместимости конфигурации Telegram. Клиентская
логика сообщений находится в `assets/web-app/messages`, логика вложений — в
`assets/web-app/attachments`; общие контроллеры и темы не принадлежат Telegram.

Во время хода переключатель `В очередь` / `Изменить ход` либо сохраняет следующий ввод до завершения, либо вызывает Codex `turn/steer` с точным `expectedTurnId`. Для каждого исходящего сообщения UI показывает состояние `Подготовка` / `Отправляется` / `Принято` / `В очереди` / `Не подтверждено`. Пользовательские сообщения объединяются по официальному `clientUserMessageId → UserMessageThreadItem.clientId`, ответы — по точным `threadId + turnId + itemId`; текст идентификатором не считается. Подтверждённые сообщения удаляются из optimistic-слоя, а сохраняемые квитанции обеспечивают безопасный повтор того же UUID после потери ответа транспорта. Terminal-квитанция локальной управляющей команды удаляется только после ACK от HTTP- или IPC-клиента: до него повтор стабильного `commandId` возвращает сохранённый результат без второго эффекта. Время сообщения берётся из истории хода или квитанции приёма, а не вычисляется заново при каждом открытии чата. Загруженные вложения являются постоянной частью сообщения: изображения видны миниатюрами, документы и архивы — именными карточками для скачивания; вложения сохраняются у уже отправленного и отложенного ввода, переживают перезапуск Agent Hub и открываются из локального Web App, Android App, Mini App и расширения VS Code. Бинарные данные и `data:` URL не вставляются в запрос модели: Hub сохраняет файл в защищённом runtime-каталоге и передаёт агенту проверенный локальный путь. Ход, состоящий только из изображения, показывается с подписью `Изображение`, а состоящий только из другого файла — с подписью `Вложение`. Если отдельный Codex App Server после перезапуска временно возвращает отстающую историю, Hub объединяет её с долговечным кэшем и свежими ходами из локального rollout, поэтому уже полученный финал не исчезает. Индикатор контекста использует данные App Server и запускает `thread/compact/start`. Ручная и автоматическая свёртка отслеживаются по современным событиям `contextCompaction`: во время операции индикатор вращается, начало и завершение автосвёртки показываются уведомлениями, а после завершения выводится фактический новый процент из свежего `thread/tokenUsage/updated`. HUB не подставляет искусственные `0%`; пока App Server ещё не прислал новый объём, индикатор показывает `…`. Расширение VS Code показывает ту же веб-оболочку из активного неизменяемого runtime-релиза и вызывает backend через аутентифицированный named pipe, не передавая секрет в webview. Код и оформление из открытого workspace не получают полномочий управления Hub; отсутствие или повреждение runtime-ресурсов закрывает панель с диагностикой. После интерфейсного обновления достаточно переоткрыть панель или выбрать `Обновить Agent Hub`; перезагрузка окна VS Code нужна только при обновлении самого моста расширения.

Изображения, которые Codex возвращает через `generatedImage(...)` или `image(...)`
после `view_image`, прикрепляются к ответу агента. Hub связывает их с точным
`turnId`, сохраняет приватную копию под непрозрачным ID и не передаёт клиентам
исходный локальный путь либо data URL.

На третьей странице `Статистика` первый график показывает локальный расход завершённых ходов по ledger и переключается между суммой, календарной скоростью расхода в час и `Поглощением` — расходом на минуту фактического времени хода в выбранных единицах. Ходы без известной длительности в интенсивность не входят и считаются отдельно. Переключатель `Учитывать расход по времени хода` и дублирующий выбор единицы расхода расположены после карточек текущих лимитов. Второй график показывает историю лимитов API, а третий сопоставляет оба источника. Вид третьей диаграммы переключается слева непосредственно в её карточке между общим видом и раздельным анализом: двумя выровненными временными графиками в исходных единицах, точечной диаграммой с линией тренда и графиком подписанной нормированной разности `аккаунт − локально`. Для сопоставления локальный расход и положительные изменения лимитов разбиваются на общие интервалы и приводятся к собственному пику; исходные значения при этом сохраняются для раздельных временных графиков. Пропуски опроса восстанавливаются между соседними замерами одного аккаунта и цикла: неизменившийся процент даёт нулевой расход, а положительная разница равномерно распределяется по пропущенному времени. Сброс лимита и смена аккаунта остаются разрывами без выдуманного расхода. Третий график показывает ровно один выбранный лимит, по умолчанию `CODEX primary`; его выбор и режим отображения хранятся отдельно и не связаны с видимостью серий второго графика. Выбор лимита расположен первым в строке показателей и оформлен выпадающим списком, поэтому невыбранные серии не занимают место отдельными кнопками. Локальная выборка автоматически ограничивается провайдером выбранного лимита. Карточка показывает коэффициент корреляции Пирсона `r`, среднее знаковое отклонение `Δ` в направлении `аккаунт − локально`, отдельную пунктирную линию этого отклонения и скользящую цену лимита в процентных пунктах на 1 kcr. Положительные и отрицательные отклонения взаимно компенсируются в среднем. Изменение цены сравнивает агрегированный коэффициент первой и второй половин периода: положительное значение означает, что на тот же локальный расход стало уходить больше лимита. Все графики поддерживают диапазоны от 6 часов до всего доступного периода, включая отдельный диапазон `15 дней`: он начинается в полночь 14 суток назад и включает сегодняшний день. Выбранный диапазон каждого графика, видимые серии второго графика, а также единственный лимит и режим третьего сохраняются локально для текущего интерфейса и восстанавливаются после перезапуска. Фоновый запрос истории лимитов начинает работу с сохранённого диапазона, а запоздалый ответ для другого периода не меняет текущий выбор пользователя. Линии сохраняют все пятиминутные замеры, а видимые точки автоматически разрежаются по экранному расстоянию, поэтому длинные диапазоны не превращаются в сплошную полосу маркеров. Серии Claude показывают отдельные показатели session, week и доступные модельные лимиты.

Если ожидание полного интервала скорости отключено, график сразу показывает предварительную линию нового цикла, но сводная карточка остаётся в состоянии `Ожидание данных` первые 45 минут на коротких диапазонах и 23 часа на длинных. До накопления полного окна она не показывает рекомендацию по темпу.

Страница `Сервер` показывает состояние локального процесса Agent Hub, PID и время работы, активные ходы и ожидающий безопасный перезапуск, состав включённых компонентов и безопасную сводку эксплуатационных настроек. Основные параметры расположены строками в двух колонках; автосвёртка, авторотация и пока недоступная очистка контекста объединены в колонке `Оптимизация Codex`, а пороги свёртки и ротации появляются в строке своего переключателя. Редко меняемые эксплуатационные интервалы и лимиты собраны в свёрнутую трёхколоночную группу `Странные константы, трогать не рекомендую`. Остальные показанные параметры можно изменить прямо там. Hub принимает только закрытый список доступных полей, валидирует диапазоны и атомарно сохраняет конфигурацию; изменение отмечается до безопасного перезапуска, после которого начинает действовать. Токены, ключи, идентификаторы пользователей, публичные URL и абсолютные пути из конфигурации в интерфейс не передаются и этим маршрутом не изменяются. Раздел компонентов расположен перед доверенными устройствами. Там же находятся доверенные Android-устройства, переключатель автозапуска Windows и кнопка штатного перезапуска; отключение автозапуска удаляет только ярлык `Agent Hub.lnk`, не затрагивая ярлык VS Code.

В многоколонном чате очередь каждого Stream отображается в его собственной ленте после текущего ответа. Если пользователь прокрутил любую колонку выше, в ней появляется плавающая кнопка перехода к последнему сообщению; у самого низа кнопка скрывается.

Расширение VS Code и локальный Mini App читают один `journal.sqlite`, следят за его revision и получают изменения без ручной перезагрузки. Начальный ответ содержит пять последних дней целиком и только шапки более старых дней. При раскрытии старого дня отдельный SQL-запрос загружает задачи и шапки ходов, а запрос и полный ответ старого хода читаются только при раскрытии самого хода. Нажатие на название задачи открывает её чат; кнопка `↗` в шапке хода открывает точный ход, включая ход субагента. В группировке по задачам раскрытая карточка показывает радарный профиль масштаба задачи по ходам, кредитам, времени, касаниям файлов, строкам diff, доле ходов субагентов, уникальным использованным навыкам и завершённым MCP-вызовам относительно медианы видимых задач. Для MCP сохраняются только сервер, инструмент и статус без аргументов и результатов; навыки учитываются по явным маркерам `$skill-name` в запросе и по фактическому чтению соответствующего `SKILL.md`.

При публикации через Cloudflare Worker Telegram Mini App передаёт команды так: Telegram `initData` и allowlist защищают пользовательскую сторону, локальный Hub забирает команды исходящим HMAC-подписанным polling. UUID и отпечаток запроса проходят весь тракт Worker → publisher → Desktop router; долговечные квитанции с фазой до внешнего эффекта возвращают сохранённый результат при повторной доставке и не исполняют неизвестный исход повторно после аварии. Worker не получает локальные пути и не может произвольно выбирать проект. Изображения передаются как привязанные к пользователю opaque-ссылки с проверкой MIME, хеша и размера, квотами и TTL; локальный Hub повторно проверяет файл и только затем сохраняет его в разрешённый runtime-каталог. При прямом HTTPS-шлюзе тот же интерфейс обращается к домашнему Hub без промежуточного Worker, сохраняя проверку Telegram `initData`.

Тот же Worker обслуживает Android-клиент. Новый телефон добавляется только одноразовым 20-символьным кодом из настроек HUB. Выпустить код могут локальный Web, Desktop, панель VS Code и уже доверенный браузер; Telegram Mini App, Android-клиент, Shared Dashboard bot и неизвестный источник не могут делегировать доступ. Worker определяет источник по прошедшей аутентификацию сессии, а не доверяет полю команды. Компрометация доверенного браузера позволяет выпустить отдельное устройство, которое нужно отзывать отдельно, поэтому делегирование следует использовать только из контролируемого браузера. Приложение создаёт неэкспортируемый P-256 ключ в Android Keystore, подписывает короткий challenge вместе с origin того Hub, к которому обращается, и получает ограниченную 12-часовую сессию; подпись, сделанная для одного адреса, не принимается другим. Сессия передаётся клиенту HttpOnly-cookie и не попадает в JavaScript страницы. Локальный прямой HTTPS-шлюз и Worker сохраняют независимые сессии, но настройки показывают их единым списком. Код сначала создаётся в локальном реестре и затем тем же значением регистрируется в Worker; если Worker недоступен или исчерпал квоту, код остаётся рабочим через прямой шлюз без ожидания восстановления Cloudflare. В настройках показываются доверенные устройства и последний доступ; отзыв применяется локально сразу и считается выполненным, а недоступный в этот момент Worker догоняет отзыв при первом же восстановлении связи — незавершённая репликация переживает перезапуск Hub.

В VS Code кнопка Agent Hub в Activity Bar сразу открывает Hub в редакторе и
закрывает первичную боковую панель, чтобы интерфейс занимал всю ширину области
редактора.

Интерфейс имеет два профиля отображения при общей разметке и данных: Telegram на Android/iOS получает мобильную компоновку, а локальный браузер и VS Code — десктопную. Telegram Desktop и Telegram Web открываются в обычном максимально развёрнутом WebView без запроса fullscreen; точный размер окна выбирает клиент Telegram. При ширине WebView меньше `860px` используется мобильная компоновка без горизонтальной прокрутки. У выполняемых задач список показывает живую длительность от фактического начала хода; метки агента и runtime остаются контрастными и не сжимаются на узкой панели. Кнопка `Diff` добавляет к последнему ответу полноширинную раскрываемую страницу изменений с моноширинным текстом и отдельной вертикальной и горизонтальной прокруткой. Темы `Орбита`, `Туманность`, `Пульсар`, `Gothic`, `Dead Space`, `Чёрная дыра`, `Rain`, `Мегаполис`, `Storm`, `Магма`, `Луг`, `Озеро`, `Графит` и `Verdant` переключаются в единой панели `Настройки`; панель содержит общие настройки интерфейса, журнала, устройств и сервера, без дублирующего блока выбранной задачи. Выбор сохраняется локально для браузера или Telegram WebView. Там же выбирается общий эффект статуса Stream: спокойная отметка, бегущий импульс, сканирующий луч, набор энергии или полное отключение. Для каждого режима готовый ответ имеет отдельное завершённое состояние, а переключатель полноэкранной подсветки переносит тот же эффект с границы внутрь плашки. `Орбита` превращает весь экран в прозрачную картографическую консоль над ночной Землёй: чат занимает оставшееся после списка задач пространство, а координаты, трассы и спутниковые отметки продолжаются под интерфейсом. Единственная анимация темы — редкий световой захват цели, меняющий только `transform` и прозрачность. `Туманность` оформлена как строгий спектрограф над телескопическими снимками холодного газа: графитовые приборные панели, бирюзовая дымка и редкие медно-янтарные линии полностью заменяют прежнюю фиолетовую палитру. Единственный эффект — почти незаметное дыхание спектральной сетки через `transform` и прозрачность. `Чёрная дыра` превращает несколько открытых Stream в Focus Deck: активный чат становится широким центром композиции, а соседние потоки остаются узкими наблюдательными панелями по сторонам. В теме доступны три сцены — сингулярность, холодное фотонное кольцо и медный аккреционный поток; медленное линзирование меняет только `transform` и прозрачность. `Мегаполис` показывает ночной городской фон через WebGL-слой запотевшего стекла: конденсат размывает изображение, движущиеся капли преломляют свет и оставляют за собой прозрачные дорожки. При недоступном WebGL используется облегчённый CSS-вариант. `Storm` показывает живой ночной шторм: шейдер поднимает и опускает воду по маске горизонта, медленно ведёт облака и подсвечивает гребни, а в момент разряда кадр сменяется вторым снимком той же сцены, снятым при вспышке. Канал молнии ветвится, доходит до воды и гаснет вместе со вспышкой, разряды идут редко. Поверх сцены льёт ливень — тот же слой капель, что в `Rain`, но вдвое плотнее и быстрее. `Verdant` помещает интерфейс среди холодных зелёных техно-руин, где лес поглощает кольцевые башни связи; к штормовой сцене добавлены солнечная долина и тёмное машинное святилище. На широком экране список задач и чат расходятся в две отдельные полевые консоли, оставляя справа открытую сцену; сообщения агента лежат прямо на стекле, а ответы пользователя остаются компактными терминальными пластинами. Редкий сканирующий импульс движется только через compositor-friendly `transform`, а карточки длинного чата обходятся без отдельных blur-слоёв. `Озеро` показывает лесное мелководье после летнего дождя: знакомые шпиц и колли идут навстречу через отражения и круги на воде, а прозрачные зелёные панели обрамлены тонкими растительными завитками. Медленный солнечный блик и расходящиеся кольца у активной задачи меняют только `transform` и прозрачность; прежние акварельный и масляный кадры остаются дополнительными фонами. Сцена за интерфейсом выбирается отдельно от палитры списком `Фон`, который показывает только кадры текущей темы: у `Verdant` три техно-природные сцены, у «Чёрной дыры» — три космические сцены, у «Озера» — дождливое мелководье, акварель и масло, у `Gothic` — десять ночных сцен: склеп, крипта, две башни, гавань, часовня, крепость, монастырь, замок Миненталя и логово Финкрегха, у `Dead Space` — шахтёрская палуба, у остальных тем — по два кадра. `Мегаполис` показывает стекло с каплями только над родной сценой: над другим кадром за конденсатом не читаются огни, поэтому там идёт обычный дождь. У каждого кадра своё затемнение для десктопа и телефона и свой источник живого света: над башней, крепостью, монастырём и замком тянется туман, в логове Финкрегха холодная дымка скользит по льду, свечи часовни горят неровно, над гаванью идёт дождь, а в склепе дышит факел. `Gothic` оформляет общий интерфейс как рабочую поверхность храма Спящего: почти чёрный графит, фактурное старое железо, прямые границы, выцветший текст и редкие ржаво-красные метки. Кованая шапка повторяет пропорции игрового референса: логотип и пергаментные подписи `AGENT HUB`/`CHAT` находятся в отдельной плашке с заклёпками, а компактное меню продолжает её справа. Крупные панели, Streams, сообщения и композер собраны матовой nine-slice рамой; флаг, срединные украшения рам и яркие засветы отсутствуют. В однопоточном режиме кованая консоль прижата влево и открывает справа фотореалистичную Башню Ксардаса среди ночного леса и тумана; несколько Streams снова занимают доступную ширину. Все девять прежних сцен и их источники живого света сохранены.

`Dead Space` переносит Hub на заброшенную шахтёрскую палубу оригинального
глубококосмического корабля: тёмный поцарапанный металл, прямые технические
панели, холодная бирюзовая индикация и редкие янтарные аварийные сигналы
оставляют переписку читаемой, а справа открывают длинный коридор и расколотую
планету за обзорным окном. Активные Workspace и Streams отмечаются тонким
голографическим контуром, сообщения агента получают скошенный технический угол,
а ответы пользователя — сдержанную аварийную подсветку. Фон и интерфейс
используют оригинальные ресурсы без игровых логотипов, персонажей и готовых
ассетов.

На desktop невидимые границы левой панели Workspace и правой панели Streams
можно перетаскивать как границы окна. Обе ширины сохраняются локально для
текущего браузера или WebView во всех темах; двойной клик по границе удаляет
пользовательскую ширину этой панели и возвращает значение активной темы.
Настройка `Переносить задачи в отдельную колонку` включена по умолчанию: правая
панель автоматически делится на задачи и потоки с собственным разделителем,
только когда их содержимое не помещается в одну вертикальную колонку. При её
включении появляется настройка `Задачи всегда в отдельной колонке`, которая
принудительно сохраняет двухколоночный режим независимо от свободной высоты.
Когда автоматический режим объединяет содержимое, панель занимает сохранённую
ширину большей из двух колонок, а не их прежнюю суммарную ширину.
Сворачивание одной колонки сохраняет ширину оставшейся, а сворачивание обеих
оставляет минимальную шапку. Границу панели можно перетаскивать и при одной
видимой колонке; её размер пересчитывается в базовую ширину панели и сохраняется
для обратного разворачивания. Если включён `Прозрачный фон переписки`, полностью
свёрнутая панель также теряет заливку, сохраняя кнопки и рамку.
Если кнопки
`Задачи (X)` и `Потоки (Y)` не помещаются рядом, они автоматически располагаются
друг под другом.

На desktop кнопка `Фокус` доступна во всех темах и находится перед компактной
кнопкой настроек без текстовой подписи. Она включает общую геометрию шапки, Stream и правой панели;
выбор сохраняется локально. На мобильной компоновке кнопка скрыта, потому что
интерфейс уже использует компактные размеры.

Актуальная компоновка `Gothic` убирает знамя Старого лагеря, но сохраняет полноценные кованые рамки вокруг Workspace, Stream и чата. Для крупных поверхностей используется матовая версия рамки без центральных крестообразных накладок и ярких засветов, поэтому соседние панели больше не образуют ряд повторяющихся орнаментов.

`Rain` превращает рабочее пространство в тёмное лесное убежище: дождь идёт поверх трёх ночных сцен, а прямые дымчатые панели читаются как сухие участки за мокрым стеклом. В теме доступны окно убежища, лесной коридор и поляна с одиноким фонарём; дополнительная лунная дымка медленно движется только через `transform` и прозрачность. Это отдельное исключение из приведённого выше общего правила о двух кадрах у остальных тем.

`Магма` оформлена как холодная обсидиановая кузница: сине-чёрные железные таблички, тонкие одинаковые рамки, тёмные заклёпки и дозированный красно-оранжевый акцент вместо прежней коричневой лавовой заливки. Центральная сцена просвечивает под чатом; доступны лавовый колодец, вертикальный разлом и сердце горна. Прежние кадры с лавовой коркой и потоком удалены.

Отдельная вкладка `Фон` пока намеренно не содержит элементов. В `Настройки →
Обратная связь → Сообщить о баге.` можно ввести описание и приложить до восьми
скриншотов PNG, JPEG, WebP, GIF или BMP размером до 20 МБ каждый. Hub создаёт
`AgentHub/Bugs/bug-<UUID>/report.md`, копирует туда изображения и публикует один
commit только с этой папкой. Перед публикацией локальная `main` должна совпадать
с upstream; уже staged и незакоммиченные пользовательские изменения не
добавляются к отчёту. Changelog gate разрешает без отдельной записи только один
отчёт строгого формата и блокирует смешанный commit.

Темы оформлены как самодостаточные пакеты в [`assets/web-app/themes`](assets/web-app/themes): каждая папка содержит манифест, CSS, необязательные скрипты/разметку и все свои изображения. Mini App, Worker и VS Code используют один автоматически найденный каталог, поэтому новая тема или её фон не требуют регистрации в остальных файлах Hub. Worker публикует CSS и изображения темы с hash содержимого в имени файла и переписывает внутренние `url(...)`. Для фоновых сцен браузер сначала использует прямой `home`-origin, вычисленный из Worker-route; если он недоступен, небольшой JSON-манифест и base64-части не больше 20 КБ с ограниченными повторами полного чтения ответа собираются локально в `blob:`. Публикация повторяет временно упавший Wrangler deploy, затем скачивает с живого домена каждый manifest и проверяет доступный транспорт по SHA-256; невосстановимый ответ останавливает релиз. Полный контракт `theme.json`, минимальный пример и команды проверки приведены в [инструкции по созданию темы](assets/web-app/themes/README.md).

Журнал открывается в режиме `Воркспейсы`: одна строка соответствует текущей задаче (`provider + threadId`), а её Stream показывается рядом с названием. Единый реестр выводит количество ходов, расход, длительность и `Пробелы`; последняя колонка считает только ходы без данных о расходе кредитов. Быстрый переключатель в шапке поддерживает `Воркспейсы`, `День`, рабочие недели с понедельника по воскресенье и календарные месяцы; дублирующий список группировки из общей панели удалён. В режиме дня раскрытая строка показывает список задач слева и ходы выбранной задачи справа; режимы недели и месяца используют ту же строковую компоновку и агрегируют соответствующий период. Раскрытая строка воркспейса показывает радарный профиль масштаба по ходам, кредитам, времени, касаниям файлов, строкам diff, доле ходов субагентов, уникальным использованным навыкам и завершённым MCP-вызовам относительно медианы видимых задач того же провайдера. Настройки журнала и дублирующий выбор единицы расхода находятся на самой странице журнала. Опция `Группировать задачи Claude в Work` объединяет Claude-ходы в одну задачу `Work` внутри выбранного периода, а в режиме воркспейсов — во всём журнале. Глобальная настройка `Учитывать расход Claude` сохраняется в runtime Agent Hub и одинакова для Mini App, панели VS Code и Desktop: при отключении Claude-ходы остаются видны, но их API-эквивалент исключается из итогов журнала и графика расхода. Выбранный режим группировки сохраняется отдельно в браузере или Telegram WebView; геометрия и контраст журнала общие для всех тем, а цвета берутся из токенов активной темы.

График локального расхода сохраняет выбранный период отдельно для каждого браузера или WebView. Скорость рассчитывается по времени задач: расход тарифицированных ходов с известной длительностью делится на их суммарную длительность. Ходы без длительности исключаются из скорости и показываются отдельным счётчиком. Диапазоны `7 дней`, `15 дней` и `30 дней` агрегируются по тем же локальным календарным дням, что и дневная группировка журнала; пропущенные дни показываются с нулевым расходом, а дата подписывается под каждым днём. На узком экране длинная дневная ось прокручивается горизонтально без прореживания дат.

Компоненты задаются в `components`, а параметры `miniApp.host` и `miniApp.port` — в `config.json`. Для локального сервера разрешены только loopback-адреса `127.0.0.1`, `localhost` и `::1`.

При белом домашнем IP Agent Hub может публиковать тот же loopback-сервер напрямую через Caddy, не пропуская трафик приложения через Cloudflare. Установщик скачивает закреплённый официальный Caddy `2.11.3`, проверяет SHA-256 архива и создаёт внешний `gateway.json` в runtime-каталоге:

```powershell
npm run gateway:install -- --url https://hub.example.com
```

После перезапуска Hub сам запускает Caddy, получает и обновляет TLS-сертификат и направляет HTTPS на `127.0.0.1:8787`. В роутере должны быть проброшены TCP 80 и 443 на компьютер, а DNS-запись hostname — указывать прямо на белый IP без HTTP-прокси. API по-прежнему требует Telegram `initData` либо локальную сессию доверенного устройства; наружу не публикуется незащищённый LAN-listener. Прямой шлюз всегда проверяет локальный реестр и не обращается к Worker за challenge или сессией, поэтому исчерпание Cloudflare Durable Objects не блокирует `home`.

Один Caddy может публиковать несколько Agent Hub из одной домашней сети через
разные hostname и единственный проброс TCP 80/443. Дополнительные частные
upstream задаются в `gateway.json`; установщик Caddy сохраняет их при повторном
запуске:

```json
{
  "enabled": true,
  "publicUrl": "https://home.example.com",
  "routes": [
    {
      "publicUrl": "https://second.example.com",
      "upstreamUrl": "http://upstream.example.invalid:8787"
    }
  ]
}
```

Дополнительный Hub должен слушать закреплённый частный адрес, а его firewall —
принимать этот порт только от компьютера с Caddy. Публичные upstream запрещены,
повторяющиеся hostname отклоняются при запуске.

Параметр `miniApp.quickTunnel.enabled` запускает HTTPS-туннель и обновляет через `setChatMenuButton` общую кнопку меню бота и явную кнопку каждого чата из `allowedUserIds`. В режиме `mode: "quick"` поддержаны временные адреса Pinggy через системный OpenSSH на порту 443 и Cloudflare Quick Tunnel через внешний `cloudflared`. Бесплатные адреса меняются после перезапуска; Hub автоматически записывает новый адрес в кнопку при каждом успешном запуске.

Для постоянного Cloudflare Named Tunnel укажите `provider: "cloudflare"`, `mode: "named"`, стабильный `publicUrl` и путь `tokenFile`, относительный к внешнему `config.json`. Файл должен содержать только tunnel token и не должен попадать в Git:

```json
{
  "miniApp": {
    "enabled": true,
    "host": "127.0.0.1",
    "port": 8787,
    "quickTunnel": {
      "enabled": true,
      "provider": "cloudflare",
      "mode": "named",
      "executable": "cloudflared",
      "publicUrl": "https://hub.example.com",
      "tokenFile": "cloudflare-tunnel.token",
      "edgeBindAddress": "192.0.2.10",
      "menuText": "Журнал",
      "publicPort": 8788,
      "controlPort": 4300
    }
  }
}
```

Маршрут опубликованного hostname в Cloudflare должен вести на `http://127.0.0.1:<publicPort>`. Необязательный `edgeBindAddress` закрепляет исходящее соединение `cloudflared` за конкретным локальным IP; это полезно, когда системный VPN перехватывает порт Cloudflare Tunnel `7844`. В named-режиме Hub публикует стабильную Telegram-кнопку после фактической регистрации соединения с Cloudflare и не ждёт распространения публичного DNS. Туннель в обоих режимах направляется на отдельный локальный listener, который требует корректную подпись Telegram Mini App и пользователя из `allowedUserIds`; обычный локальный просмотр на основном порту остаётся доступным без Telegram. Внутри Telegram журнал обновляется опросом раз в пять секунд.

Предпочтительный постоянный режим — Cloudflare Worker из `cloudflare-worker`. Статические CSS, JS, изображения и шрифты обслуживает Cloudflare Assets напрямую; Worker запускается только для API и других путей, которым действительно нужна серверная логика. Это не расходует Durable Objects на загрузку интерфейса и не пропускает крупные изображения через повторно обёрнутый Worker-stream. Защищённое Telegram API остаётся в Worker, а локальный Hub отправляет актуальный снимок журнала исходящим HTTPS-запросом. Входящий порт и постоянно работающий `cloudflared` не нужны. Снимок хранится в SQLite-backed Durable Object со строгой согласованностью; публикация подписывается отдельным HMAC-секретом, а чтение требует корректный Telegram `initData` и пользователя из `allowedUserIds`.

Сборка и развёртывание:

```powershell
npm run worker:build
npx wrangler login
npx wrangler secret put TELEGRAM_BOT_TOKEN --config cloudflare-worker/wrangler.jsonc
npx wrangler secret put SYNC_SECRET --config cloudflare-worker/wrangler.jsonc
npx wrangler secret put ALLOWED_USER_IDS --config cloudflare-worker/wrangler.jsonc
npx wrangler secret put DASHBOARD_BOT_WEBHOOK_SECRET --config cloudflare-worker/wrangler.jsonc
npx wrangler secret put DASHBOARD_BOT_TOKEN --config cloudflare-worker/wrangler.jsonc
npx wrangler secret put DASHBOARD_BOT_HUB_REGISTRY --config cloudflare-worker/wrangler.jsonc
npm run worker:deploy
npm run worker:verify
```

`worker:deploy` только собирает и развёртывает Worker, а `worker:verify` отдельно
проверяет опубликованный index и изменённые manifest/chunks. Поэтому временная
несогласованность байтов index повторно проверяется в пределах шести попыток и
общего окна 60 секунд с тем же checkpoint и без нового deploy. Это окно относится
только к index и его частям: последующие проверки сохраняют прежний бюджет
пять минут на логический запрос; устойчивое несовпадение
завершает этап ошибкой с hash/length без вывода HTML. Сетевые, policy и auth
ошибки автоматически не повторяются. Один логический
сетевой запрос проверки ограничен пятью минутами и пишет начало, повтор и
завершение в журнал публикации.

Список ресурсов оболочки выводится из одного `index.html` через общий
`client-assets.cjs`: локальный HTTP-сервер, VS Code WebView и Worker-сборка не
поддерживают отдельные ручные перечни. Выборочная публикация запускает общий
контракт поверхностей и останавливается до deploy, если любой ресурс отсутствует,
не упакован, не читается локально либо не переписывается для VS Code.

Для общего Dashboard-бота владелец один раз создаёт отдельного бота через
`@BotFather`, сохраняет его token и случайный webhook secret длиной не менее 32
символов в закрытых локальных файлах, записывает webhook secret и token в
Cloudflare командами выше и регистрирует webhook:

```powershell
npm run dashboard-bot:webhook -- --url https://hub.example.com --token-file C:\private\dashboard-bot.token --webhook-secret-file C:\private\dashboard-bot-webhook.secret
```

BotFather token хранится только как закрытый Cloudflare secret центрального
Worker и в административном локальном файле; в Hub участников он не передаётся.
До включения защищённой регистрации каждый существующий Hub формирует безопасную
запись enrolment без исходного секрета и локального пути:

```powershell
npm run dashboard-bot:pair -- --enrollment
```

Владелец объединяет полученные `hubId` и `verifier` в один JSON вида
`{"version":1,"hubs":{"<hubId>":"sha256:<hex>"}}`, записывает его в Cloudflare
secret `DASHBOARD_BOT_HUB_REGISTRY` и только затем развёртывает Worker. Локальные
`config.json` и `shared-dashboard-bot.secret` не меняются. Для нового Hub порядок
тот же: установка создаёт локальный ID и секрет, владелец добавляет verifier в
registry, после чего пользователь выполняет обычный `npm run dashboard-bot:pair`.
Защита не удаляет записи Durable Object, созданные до её включения: при
подозрении на прежнюю публичную регистрацию владелец отдельно очищает такие
непривязанные записи либо заменяет Durable Object до открытия маршрута.

Token нужен Worker для кнопок пачки и защищённой загрузки изображений. Worker
проверяет Telegram secret header, хранит
привязку Telegram user ID к одному Hub ID и ставит карточку только в отдельную
Durable Object очередь этого Hub. Каждый локальный Hub имеет собственный
случайный секрет в защищённом runtime-каталоге; секреты разных участников не
совпадают. Локальный Hub забирает очередь коротким запросом с `waitMs: 0` и
ограничивает зависший pull десятью секундами: если карточек нет или Worker
временно не ответил, он ждёт `sharedDashboardBot.retrySeconds` (по умолчанию 5
секунд) до следующей попытки. Авторизация pull/result хранится рядом с очередью
конкретного Hub, поэтому публикация большого журнала и snapshots в общем Durable
Object больше не блокирует доставку задач; существующая привязка переносится туда
автоматически при первом запросе. Привязки Telegram и незавершённые пачки также
живут в отдельном router-объекте и автоматически переносятся из прежнего общего
хранилища. После каждого нового элемента карточка пачки переносится к последнему
сообщению, поэтому обновление не остаётся незаметным выше по истории; запросы к
Telegram ограничены по времени, а недоступную для редактирования старую карточку
бот заменяет новой. Telegram сначала честно показывает постановку в очередь, а
подтверждает создание карточки отдельным сообщением только после успешного
результата локального Hub. Уже зарегистрированный Hub может безопасно
обновить регистрацию по своему прежнему секрету даже при временно отсутствующем
registry-secret; неизвестные Hub без registry по-прежнему отклоняются.
Telegram Bot API позволяет боту скачать через `getFile` не более 20 МБ. Если
один файл превышает этот предел или не скачивается, Worker явно перечисляет его
как не приложенный, но всё равно ставит в очередь текст и остальные исправные
вложения той же пачки; один недоступный файл не удерживает последующие картинки.
Durable Object поэтому может переходить в спящий режим между запросами вместо
непрерывного 25-секундного ожидания, а обычная задержка доставки остаётся в
диапазоне 0–5 секунд.

В `cloudflare-worker/wrangler.jsonc` задаётся публичный маршрут Worker. Значения `TELEGRAM_BOT_TOKEN`, `SYNC_SECRET`, `ALLOWED_USER_IDS`, `DASHBOARD_BOT_WEBHOOK_SECRET`, `DASHBOARD_BOT_TOKEN` и `DASHBOARD_BOT_HUB_REGISTRY` хранятся как Cloudflare secrets и не попадают в Git. Локальная копия `SYNC_SECRET` хранится рядом с внешним `config.json`; Worker включается так:

```json
{
  "miniApp": {
    "worker": {
      "enabled": true,
      "publicUrl": "https://hub.example.com",
      "syncSecretFile": "cloudflare-worker-sync.secret",
      "menuText": "Журнал",
      "retrySeconds": 15,
      "refreshSeconds": 60
    }
  }
}
```

Publisher сжимает SQLite-снимок журнала через gzip, подписывает и отправляет его порциями при изменении revision, повторяет неудачные запросы и периодически сверяет состояние. Worker атомарно переключает опубликованный журнал только после получения всех порций, поэтому рост истории не обрывает обновление и незавершённая публикация не заменяет рабочий снимок. Telegram-кнопка переключается на Worker только после первой успешной публикации.

Если требуется осознанно привязать сообщение именно к задаче, выбранной сейчас в Telegram-боте, используйте отдельный параметр:

```powershell
node send-message.mjs --bind-active --category info "Сообщение для активной задачи бота"
```

Привязанное уведомление отправляется как тонкая медиа-карточка фиксированного размера: PNG-баннер показывает категорию, а подпись — жирное название текущей задачи с одним `🧵` слева и текст. Кнопка `👀 Показать сообщение` прикреплена к этой же карточке: она выбирает привязанный thread и показывает текущий ход либо последний полный ответ. Исходники и воспроизводимый генератор баннеров находятся в `assets/notification-cards`. Поддерживаются категории:

- `action` — `ТРЕБУЕТСЯ ДЕЙСТВИЕ`;
- `done` — `ЗАДАЧА ВЫПОЛНЕНА`;
- `intermediate` — `ПРОМЕЖУТОЧНЫЙ РЕЗУЛЬТАТ`;
- `progress` — `ЗАДАЧА ВЫПОЛНЯЕТСЯ`;
- `warning` — `ВНИМАНИЕ`;
- `info` — `ИНФОРМАЦИЯ` (по умолчанию).

Если Telegram временно не принимает PNG, `send-message.mjs` автоматически отправляет прежнее текстовое оформление, поэтому важное уведомление не теряется.

`done` используется только после полного завершения всей задачи, когда больше не осталось работы и агент заканчивает ход. `action` означает, что дальнейшая безопасная работа действительно невозможна без ответа или действия пользователя. Для существенного готового этапа, после которого работа продолжается, используется `intermediate`; для обычного текущего состояния — `progress`; для риска или отклонения, ещё не требующего вмешательства, — `warning`. Нейтральные сообщения, не подходящие ни под одну специальную категорию, отправляются как `info`.

Например, отдельный промежуточный результат отправляется командой `node send-message.mjs --bind-current --category intermediate "Проверка завершена"`. Обычный финал отдельно не отправляется: Agent Hub читает его из rollout. Переключение выполняется при Telegram-действии «Ответить» или по кнопке показа. Простое новое сообщение и ответ на уведомление, отправленное без `--bind-current` или `--bind-active`, текущую задачу не меняют. Если другая задача выполняется, бот не прерывает её автоматически. При фактической смене бот присылает заголовок `Текущая задача изменена`. Если `showProjectButton` включён, ниже выводятся жирное имя проекта и курсивное название задачи; если выключен — только жирное название задачи. Служебное сообщение прогресса и итоговый ответ, отправленные самим ботом, тоже получают привязку к породившей их задаче.

### Скриншоты кода

Для переписки с телефона фрагмент исходника можно отрендерить в читаемые PNG. Длинный диапазон автоматически разбивается на несколько изображений:

```powershell
python render-code-images.py `
  "C:\Projects\App\Module.bsl" `
  "C:\Projects\App\WIP\code-images" `
  --start 190 --end 260 `
  --title "Копирование коллекций"
```

Готовые PNG отправляются одним изображением или Telegram-альбомом. Привязка работает так же, как у `send-message.mjs`, поэтому ответ на картинку возвращается в правильную задачу:

```powershell
node send-images.mjs --bind-current --caption "Код после правки" `
  "C:\Projects\App\WIP\code-images\Module-190-234.png" `
  "C:\Projects\App\WIP\code-images\Module-235-260.png"
```

Поддерживается до десяти PNG в одном альбоме. `--bind-active` намеренно привязывает изображения к выбранной в боте задаче, `--silent` отключает уведомление. Для рендеринга используется Pillow из `requirements.txt`.

Кнопка `Показать сообщение` не создаёт новый ход. Она перерисовывает компактное представление выбранного Stream: удаляет доступные боту сообщения этого Stream из Telegram, сверху создаёт навигацию истории, затем показывает последнюю пару `👤 Вы` → `🤖 агент` и создаёт новую живую progress-карточку последней в чате. Старый ID progress-сообщения одновременно отсоединяется от run, поэтому обновления не продолжают уходить в карточку выше истории. Для начатого в Telegram хода используется тот же run. Для Codex бот читает текущий turn через App Server, а для Claude — локальный transcript соответствующего `session_id`; сообщение продолжает обновляться до завершения. Ходы, начатые другими клиентами HUB либо внешним VS Code/CLI, отслеживаются в фоне только для общего состояния и журнала: Telegram не получает progress-карточку, подтверждение или финал, пока пользователь явно не нажмёт `Показать сообщение`. Нажатие включает Telegram-представление именно этого хода до его завершения. Если активного хода нет, кнопка показывает полный последний ответ. Если ни хода, ни ответа найти нельзя, бот сообщает об этом и не подставляет данные другого Stream.

Кнопка `👀 Показать ещё` расположена в первом сообщении компактного представления, то есть визуально выше показанной переписки. Каждое нажатие добавляет ровно одну пару: `1 → 2 → 3 → 4…`. Telegram не позволяет вставлять новые сообщения задним числом, поэтому при догрузке бот удаляет текущее представление и строит его заново с большим числом пар в хронологическом порядке. Источником истории остаются локальные треды Codex и transcript Claude; удаление Telegram-сообщений историю агента не затрагивает.

В личном чате бот может удалять как исходящие, так и входящие пользовательские сообщения моложе 48 часов. Новые входящие тексты, изображения и голосовые сообщения привязываются к задаче, чтобы при следующем открытии убрать оригинал и показать его как `👤 Вы`. Сообщения старше ограничения Telegram и старые пользовательские сообщения, ID которых бот ещё не сохранял, автоматически удалить нельзя. Незакрытые запросы разрешения с кнопками сохраняются.

## Что изменено в текущей версии

### Потоковый ход выполнения

- Codex обрабатывает `agentMessage`, доступное резюме анализа, `plan`, команды, изменения файлов и вызовы MCP по мере поступления событий App Server.
- Claude Code запускается с `stream-json --verbose --include-partial-messages`; текст, инструменты, повторные API-запросы и `session_id` доступны до завершения процесса.
- Для задачи дольше трёх секунд бот создаёт одно служебное сообщение и редактирует его не чаще одного раза в 1,5 секунды. В первой строке компактного заголовка указаны агент, модель и reasoning; проект добавляется только при включённой кнопке проекта. Во второй строке указано название задачи, отдельной строкой — владелец выполнения: `VSCode App Server`, `Agent Hub Server`, `Codex Desktop App`, `Codex CLI` или безопасный `External Codex`, если текущий внешний клиент определить нельзя. В коротких кнопках списка используются соответственно `VSC`, `HUB`, `APP`, `CLI` и `EXT`. Короткие ответы приходят сразу одним итоговым сообщением без лишнего «Задача принята».
- Heartbeat различает доступность потока и реальную работу: зелёный статус показывается только при свежих событиях, а после двух минут без новых событий появляется оранжевое предупреждение с длительностью простоя. Успешный `thread/read` сам по себе больше не изображает продвижение задачи.
- После завершения служебное сообщение сворачивается до краткого статуса, а полный ответ отправляется отдельно. Бот берёт `final_answer` либо отдельный итоговый `plan` завершённого Codex-turn, а если итог ещё не появился в снимке — повторно перечитывает turn перед доставкой; промежуточные commentary не подменяют итоговый ответ. В Plan mode ответы формы уточнений отправляются из всей карточки запроса, поэтому выбранные и собственные варианты не теряются.

### Несколько задач одновременно

- Выбранная задача — только адрес для следующего обычного сообщения. Она не является глобальной блокировкой бота.
- Пока один поток выполняется локально, через `/streams`, `/projects`, `/agent` или ответ на привязанное сообщение можно выбрать другой и запустить его. Работа первого продолжится в фоне.
- Реестр запуска хранит отдельно для каждого `проект + агент + thread/session`: процесс или turn, прогресс, ответ, временные файлы и последний diff.
- Перед запуском управляемого хода бот определяет фактический корень Git-репозитория и сохраняет синтетическое дерево текущих файлов, не меняя рабочий index. Поэтому кнопка `Изменения` под каждым итоговым ответом показывает diff именно этой задачи, даже если сейчас выбрана другая; команда `/diff` остаётся способом открыть изменения выбранной задачи. Учитываются staged- и новые untracked-файлы, но исключается уже существовавшая грязь. Большой diff ограничивается 64 КиБ и дополняется перечнем затронутых файлов; последние сто результатов хранятся отдельно от часто перезаписываемого state и переживают рестарт бота. Для внешнего хода, обнаруженного после старта, снимок охватывает изменения с момента подключения.
- Исполнитель у каждого хода только один. Если turn уже выполняется через `VSCode App Server`, Telegram подключает наблюдение и сохраняет новое сообщение для выбора действия или очереди, но не запускает параллельный turn. Ход, начатый Telegram, помечается `Agent Hub Server`. Штатная панель VSCode не читает lock бота, поэтому жёсткая блокировка гарантируется со стороны Telegram; обнаруженный встречный VSCode-ход всё равно сразу попадает в локальный реестр и становится наблюдаемым.
- `/streams` строится заново из локального каталога Codex и файлов сессий Claude, поэтому показывает потоки обоих агентов во всех разрешённых папках, а не только уже открывавшиеся через бота. Индекс названий Codex читается один раз на обновление каталога, увеличившиеся rollout-файлы и transcript Claude разбираются только с последней подтверждённой байтовой позиции. Первичный полный разбор большого transcript и бухгалтерский перескан выполняются последовательно вне главного потока. Список разбит на страницы; выполняющиеся через Agent Hub Server потоки отмечены `⚡`, остальные выполняющиеся — `⏳`, Claude-потоки с неопределённой живостью — `❔`. Команда `/rename <название>` переименовывает и закрепляет текущий поток по его `provider + threadId`; последующие автоматически сгенерированные заголовки Codex не меняют это имя в боте.
- `/status` отправляется как прямоугольная карточка 3:1 с логотипом выбранного агента. Для каждого показа случайно выбирается одна из семи синих шапок Codex или семи терракотовых шапок Claude; если одновременно активны задачи обоих агентов, используется одна из трёх совместных шапок. Первая строка показывает агента, модель и reasoning, вторая — режим и состояние. Каталог выводится только при включённой кнопке проекта. Число выполняющихся задач находится в заголовке `🧵НЕДАВНИЕ ЗАДАЧИ (N)🧵`; отдельная строка счётчика не выводится. Под заголовком находятся четыре кнопки: сначала выполняющиеся задачи, затем свободные места занимают последние по активности завершённые задачи. Ходы Agent Hub отмечены `⚡`, остальные активные — `🧵`, недавние — `🕘`, Claude-задачи с неопределённой живостью — `❔`, выбранная — `✅ ТЕКУЩАЯ`; у выбранной активной HUB-задачи `⚡` остаётся рядом с меткой `HUB`. Нажатие сразу выбирает агент, проект и thread/session. Запуски самого сервера определяются точно; для внешнего Codex сервер сопоставляет lifecycle-события свежего rollout (`task_started`/`task_complete`/`turn_aborted`) по `turn_id`, а VSC сначала определяет по `client_id` пользовательского сообщения именно этого turn. Если per-turn метки недостаточно, Windows Restart Manager показывает процессы, которые сейчас держат rollout: процесс Agent Hub исключается, а оставшийся клиент определяется по живому дереву процессов как `VSC`, `APP` или `CLI`. Несколько разных внешних клиентов либо неизвестное дерево дают безопасный `EXT`. Исторические `originator` и `source` сессии при выборе владельца не используются. Для внешнего Claude незакрытый transcript считается выполняющимся, пока обновлялся в последние 30 минут. После более долгой тишины состояние становится `активность неизвестна`: наблюдение снимается без ложного финала, а новый ход в той же сессии требует явного подтверждения. Для Claude, запущенного самим сервером, используется PID и такого таймаута нет. После подтверждённой отмены управляемого Claude-процесса сервер запоминает снимок его transcript и не воскрешает незавершённый хвост как внешний ход; новая реальная активность или следующий запуск в этой сессии снимают отметку.
- `/cancel` останавливает только выбранную задачу. Для подключённого внешнего хода бот отключает observer и запоминает это состояние, поэтому наблюдение не подключается повторно само. Пока внешний ход действительно выполняется, новый запрос в тот же thread/session всё равно не запускается; повторное подключение доступно через `Показать сообщение`. Другие запуски продолжаются.
- Разные задачи могут одновременно работать внутри одного workspace и одного Git-репозитория: это штатный режим для `VSC_Tyrael`, и бот не показывает предупреждение о пересечении репозиториев. Перед обычным сообщением бот по-прежнему повторно проверяет выбранный thread/session и не запускает в нём второй параллельный ход.
- Если выбранный поток уже выполняется, новый текст, голосовая расшифровка или изображение не теряются и не подменяются текущим прогрессом. Бот сохраняет вход и предлагает отправить его в новый поток, поставить в очередь исходного, показать текущий ход или отменить. Предупреждающая кнопка явного запуска остаётся только для неопределённой живости внешнего Claude-процесса. Очередь запускается автоматически после освобождения своего потока; сохранённые и поставленные в очередь входы переживают перезапуск бота. Старые сохранённые сообщения, остановленные прежней проверкой Git-корня, при обновлении автоматически переводятся в очередь.
- Все привязанные уведомления и сообщения о смене задачи используют единый контракт кнопки `👀 Показать сообщение`: она выбирает именно привязанный `проект + агент + thread/session`, подключает его текущий живой ход и показывает актуальный прогресс. Новые кнопки просмотра и догрузки истории несут `provider + threadId` непосредственно в callback, поэтому продолжают работать после компактации или удаления ограниченного хранилища привязок; проект и название восстанавливаются из каталога задач. Если ход уже завершён, показывается его последний полный ответ. Старые callbacks `show-message`, `show-last-message` и `history-more` поддерживаются для ранее отправленных Telegram-сообщений и при утраченном контексте возвращают явный безопасный отказ. Переключение представления не останавливает фоновые задачи и не запускает дополнительный ход. Если переключение выполнено самой кнопкой показа, новое уведомление о переключении отправляется без кнопки, чтобы не создавать рекурсивную цепочку.

### Workspace, Stream, Thread и Turn

Agent Hub хранит пользовательскую работу как `Workspace → Stream → Thread → Turn`.
Workspace имеет постоянный ID и изменяемое имя. Stream — независимая линия
работы внутри Workspace; один Stream последовательно объединяет несколько Codex
Threads или Claude sessions. Turn остаётся отдельным пользовательским ходом.
Все команды и клиенты адресуют Stream через `streamId`, а provider thread/session
ID используется как заменяемая внешняя ссылка.

Каждый ещё не распределённый корневой Thread автоматически получает собственный
Workspace с текущим названием Thread и один безымянный Stream. Поэтому обновление
старой установки сохраняет привычный список: прежнее название задачи становится
названием Workspace, а единственный Stream не получает лишний номер. Старые
автоматические привязки в `Other` переводятся в этот формат при следующей
синхронизации; явно заданная раскладка и пользовательские переименования не
изменяются. `Other` остаётся системным Workspace для явного размещения
тестовых и неопознанных запусков. Субагенты остаются дочерними ходами и не
создают верхнеуровневые Streams. Общая Web/VS Code/Android/Mini App оболочка
по умолчанию переключает один Stream обычным кликом, а Ctrl+click показывает до
четырёх Streams одновременно на desktop; mobile всегда показывает один. Общий
порядок Streams меняется перетаскиванием, сохраняется в серверном SQLite-каталоге
и синхронизируется между всеми устройствами. Композер адресует подсвеченную
целиком активную колонку.

Каталог Workspace поддерживает именованные сворачиваемые папки по идее
[ZeroFakt](https://github.com/ZeroFakt). Пустая папка создаётся отдельной кнопкой
и не забирает активный Workspace автоматически. При создании Workspace папку
можно выбрать под полем `Наименование`; пустое значение оставляет его в общем
списке. Перемещение выполняется через контекстное меню Workspace, а папка
переименовывается через собственное контекстное меню. Drag-and-drop Workspace
не используется. Назначение папки хранится в SQLite вместе с настройками
Workspace, а список пустых папок и их свёрнутое состояние — локально для каждой
поверхности интерфейса.

Компактная непрозрачная кнопка слева на полосе Streams переключает сортировку
по последней активности и ручной порядок; значок часов обозначает активность,
а вертикальные стрелки — ручную перестановку. Автоматический режим всегда ставит
самые свежие потоки в начало ленты. Протягивание мышью прокручивает полосу по
горизонтали. В ручном режиме drag-and-drop меняет и локально сохраняет порядок.
Правая панель продолжает показывать недавно использованные Stream в пределах
настроенного периода, но счётчик `Активно: X` учитывает только Stream с текущим
ходом или непрочитанным готовым ответом.
Параметр `Период отображения активных задач` хранится в состоянии Agent Hub Server
и синхронизируется между Desktop, VS Code, Mini App и браузером.
Журнал и статистика агрегируются по Workspace и сохраняют детализацию по Stream.
Контекстное меню Stream (`ПКМ` либо `Shift+F10`) позволяет переименовать его,
перенести в существующий Workspace или создать новый Workspace сразу из этого
Stream. Перенос выполняется одной SQLite-транзакцией; опустевший пользовательский
Workspace удаляется, а системный `Other` сохраняется. Workspace с активным
ходом отмечается той же тематической бегущей рамкой, что и работающий Stream.

Первичная раскладка выполняется повторяемой командой с обязательным dry-run:

`npm run workspace:migrate -- --manifest <manifest.json>`

После проверки применяется `--apply`; перед транзакцией создаётся согласованная
копия `journal.sqlite`, а повторный запуск с тем же манифестом ничего не меняет.
Манифест нужен только для заранее подготовленной общей раскладки: обычное
обновление самостоятельно создаёт безопасный Workspace для каждого старого
корневого Thread.

### Сохранение и восстановление задач

- Активный запуск сохраняется в `data/runtime.sqlite`: агент, проект, `threadId`/`session_id`, `turnId`, время запуска, ID служебного Telegram-сообщения и уже полученная часть ответа.
- SQLite read-model в `data/journal.sqlite` синхронизирует между независимыми интерфейсами каталог, историю, фактический статус, `turnId`, владельца App Server, последний этап и текст выбранной задачи. Задачи, ходы и сообщения лежат в отдельных таблицах; обновления выполняются параметризованными запросами в транзакциях. При первом запуске старый `data/task-sync.json` импортируется, каждая запись сверяется с SQLite, и только после успешной проверки исходный JSON удаляется. Для Codex источником истины остаются локальные thread/rollout-файлы, для Claude — transcript. Пока внешний VSC-ход выполняется, его текущий пользовательский запрос и последующие уточнения берутся из append-only rollout по точному `client_id` и сразу добавляются в чат; после обновления официальной истории они сливаются по тому же идентификатору без дублей. Read-model является восстанавливаемым кэшем: если отдельный App Server временно недоступен, кнопка просмотра берёт историю только соответствующего `provider + threadId`; статус `running` автоматически устаревает через десять минут и не создаёт вечную фантомную задачу. Хранилище ограничено тысячей задач; при переполнении удаляются самые старые завершённые записи, активные не вытесняются.
- Неизменившийся снимок потока не создаёт запись в SQLite. События собственного `Agent Hub Server` остаются основным мгновенным каналом обновления, а `thread/read` используется раз в пять секунд только как страховка от потерянного события. Внешний `VSCode App Server` проверяется чаще, чтобы новый ход быстро появлялся в статусе. Одновременные чтения одного треда и повторные открытия `/streams` в коротком интервале объединяются; индекс названий Codex перечитывается только после изменения файла.
- При разрыве Codex App Server бот автоматически запускает его снова, возобновляет поток и читает сохранённую задачу через `thread/read`. Для продолжающегося хода восстанавливается наблюдение; для завершённого — найденный ответ доставляется в Telegram.
- Если `thread/resume` временно ошибается при запуске бота, но для этого же треда сохранён активный run, бот не создаёт новый выбранный тред. Он сохраняет прежнюю привязку и передаёт ход процедуре восстановления, исключая две параллельные задачи из одного пользовательского продолжения.
- Если управляемый Telegram-ход после переподключения остался в `waitingOnApproval`, но сам JSON-RPC-запрос погиб вместе со старым App Server, в режиме автоподтверждения бот откатывает только незавершённый turn и продолжает задачу новым turn с требованием проверить уже сделанные файлы и не повторять завершённые действия.
- Запросы дополнительных разрешений App Server (`item/permissions/requestApproval`) показываются в Telegram так же, как подтверждения команд и файлов. Запросы MCP (`mcpServer/elicitation/request`) обрабатываются отдельно: безопасная форма-разрешение с булевыми полями, утвердительными вариантами или готовыми значениями принимается в режиме автоподтверждения; форма, для которой пришлось бы выдумывать текст, пароль или неоднозначный выбор, всегда показывается пользователю. Неизвестный MCP-запрос больше не остаётся без JSON-RPC-ответа и не зависает скрыто. Техническое сообщение `Бот запущен` при фоновом рестарте не отправляется.
- Ошибка доставки финального ответа в Telegram не оставляет завершённый ход в реестре активных задач. Ответ сначала сохраняется локально для последующего просмотра кнопкой с глазами, а запуск освобождается независимо от состояния сети; состояние `finishing` после аварийного рестарта также перечитывается и завершается.
- Observer запоминает текст ответа на момент подключения, но при фактическом завершении наблюдаемого хода всегда доставляет его итог отдельно. Это закрывает гонку, когда внешний ход успел завершиться между обнаружением и первым опросом: старый ответ не подменяет текущий, а уже готовый текущий финал не теряется.
- Claude сообщает `session_id` первым событием и бот сохраняет его сразу, а не только после успешного завершения.
- Запущенный ботом ход Claude переживает перезапуск бота. CLI стартует отдельным процессом, а его `stream-json` пишется в файл хода `data/claude-runs/<turnId>.jsonl`, который бот читает хвостом с потоковым UTF-8-декодером. Русский текст и эмодзи сохраняются, даже если опрос пришёлся на середину многобайтного символа. После перезапуска ход подключается заново по сохранённому PID и файлу вывода: живой процесс продолжает вести ту же progress-карточку, а завершившийся отдаёт финальный ответ из файла. Прерванным ход помечается, только если процесса уже нет и результата в файле тоже. По той же причине `/restart` не ждёт завершения ходов Claude, а `/cancel` останавливает ход и после перезапуска — по сохранённому PID.
- При запуске удаляются файлы `data/claude-runs`, которые не принадлежат ни одному восстановленному активному ходу. `/cancel` в Windows останавливает всё дерево Claude через `taskkill /T /F` с резервной остановкой корневого процесса; в Unix сигнал получает detached-группа процессов.
- Оперативное состояние сериализуется через очередь в `runtime.sqlite` с WAL и `synchronous=FULL`. В той же базе сохраняются граница terminal-аудита Codex, байтовые позиции rollout и Telegram-привязки; транзакции исключают обрезанный JSON и потерю конкурентной записи. Старые `state.json`, резервная копия и журналы привязок однократно импортируются, архивируются в `data/migrations/runtime-sqlite` и больше не используются. Хранилище текстов озвучки остаётся отдельным ограниченным JSON-кэшем.

### Надёжность процесса

Активная свёртка блокирует смену модели и Reasoning, а также считается работой,
которую обязан дождаться безопасный рестарт Agent Hub. После завершения или
таймаута свёртки отложенный рестарт продолжается автоматически. При остановке
незагруженного треда Hub сначала возобновляет его в своём App Server и повторяет
`turn/interrupt`; ход другого окна Codex получает понятное сообщение без сырой
ошибки `thread not found`.

- Эксклюзивность процесса обеспечивается локальным системным каналом, уникальным для `dataDir`, поэтому две копии не могут одновременно читать `getUpdates` и дублировать ответы даже при гонке за устаревший файл. `data/bot.lock` хранит PID, случайный token, время запуска, имя канала и признак `ready`; PID, переиспользованный Windows после аварии, не создаёт вечную блокировку. Штатный `/restart` не обрывает управляемые Agent Hub ходы и не бросает уже принятую фоновую загрузку, распознавание или озвучивание: при необходимости перезапуск откладывается до безопасной передачи работы ходу Codex, чей App Server перезапускается вместе с Agent Hub. Старая копия сначала прекращает polling и фоновые таймеры, завершает всё дерево Codex App Server/MCP и локальный TTS-worker, освобождает системный lock, затем запускает замену. Новая копия выставляет `ready` только после инициализации provider, восстановления запусков/очередей и регистрации команд; живого PID без `ready` недостаточно. Если WMI-launch не дал готового процесса, запуск повторяется и используется прямой скрытый `wscript` fallback; если все попытки неуспешны, прежняя копия повторно захватывает lock и восстанавливает свои сервисы. Соседний Telegram update из уже полученного пакета остаётся для новой копии и обрабатывается ровно один раз. Ходы Claude перезапуск не задерживают, потому что подключаются заново. Внешние наблюдаемые задачи после запуска подключаются снова по сохранённому thread/session и заново определяют владельца текущего turn (`VSC`, `APP`, `CLI` либо безопасный `EXT`), не наследуя среду создания треда. Сообщение `Перезапускаю Agent Hub…` редактируется в итоговую карточку `AGENT HUB ПЕРЕЗАПУЩЕН`; технический статус `interrupted` при таком восстановлении пользователю не отправляется.
- Фоновое наблюдение повторно сверяет выбранные `provider + project + threadId` после каждого асинхронного чтения snapshot и ещё раз проверяет реестр запусков. Переключение задачи или старт Telegram-хода во время чтения не могут подключить observer к старой задаче либо создать второй запуск поверх нового.
- Codex App Server автоматически переподключается с повторными попытками, а пользователь видит состояние соединения в служебном сообщении.
- Каждый Codex JSON-RPC вызов ограничен `codexRpcTimeoutSeconds` (по умолчанию 30 секунд). Ошибка запуска App Server, закрытие stdin или зависший RPC завершают конкретное ожидание ошибкой вместо бесконечной блокировки Telegram polling.
- Перед запуском `Agent Hub Server` проверяет только локальные HTTP MCP из пользовательского `config.toml`. Недоступные порты отключаются аргументами лишь для запускаемого им экземпляра Codex App Server, поэтому не создают повторяющиеся fatal-записи и не меняют глобальную конфигурацию. На следующем безопасном перезапуске проверка выполняется заново, и уже запущенные MCP снова подключаются.
- При обрыве Telegram polling бот продолжает работу локальных ходов и повторяет `getUpdates` с ограниченной задержкой `3 → 6 → 12 → 24 → 30` секунд. После первого успешного запроса задержка сбрасывается; при долгом обрыве одинаковые ошибки журналируются разреженно.
- Служебный `answerCallbackQuery` выполняется в фоне с коротким таймаутом: временная потеря сети не отменяет уже выбранное действие и не выдаётся за ошибку переключения задачи. Если `/status` не может отправить графическую шапку, бот повторяет ответ обычным текстовым сообщением.
- `telegramApiBaseUrl` применяется ко всем JSON- и multipart-запросам, загрузке файлов, изображениям и голосу — локальный Bot API server или прокси не обходится прямыми обращениями к `api.telegram.org`.
- Если новое состояние прогресса пришло во время уже выполняющегося `editMessageText`, оно помечается ожидающим и отправляется сразу после текущей правки, а не теряется до следующего события.
- Сессия Claude хранит свой фактический `cwd` отдельно от корня разрешённого проекта. При `--resume` Agent Hub повторно читает каталог из transcript, проверяет, что он остаётся внутри проекта, и запускает CLI именно там; поэтому задачи из вложенных папок не теряются после выбора в общем каталоге. Ошибки Claude разбираются одновременно из финального JSON, stream-событий и сохранённого `stderr`, даже при ненулевом коде процесса. Для `rate_limit_event` бот показывает настоящую причину и время сброса вместо общего сообщения «завершился с кодом 1».
- Telegram offset сохраняется после обработки конкретного update. Если обработчик завершился ошибкой, полный update и причина сначала атомарно сохраняются в `data/failed-updates/`; только затем offset продвигается и пользователю отправляется диагностика. Если сохранить запись не удалось, offset не подтверждается. Штатный `/restart` запускает замену лишь после записи offset и runtime-state, поэтому новая копия не обрабатывает повторно саму команду рестарта.
- Пока управляемый Telegram-ход выполняется, бот обновляет отдельную progress-карточку. После терминального события точный `threadId + turnId` атомарно сохраняется в ledger журнала, а затем ставятся в durable outbox Markdown-проекция и, только для Telegram-хода, обычный полный финальный ответ. Ledger имеет резервную копию, восстанавливается после повреждения основного JSON и хранит `projectRoot`, поэтому один проект не может попасть в журнал другого. Ошибка Markdown-проекции не теряет ход: проекция повторяется при следующем запуске. Если внешний ход остановился во время остановленного Hub, потоковый terminal-аудит дочитывает событие с сохранённой позиции и уточняет ту же запись поздним настоящим terminal-событием. Только после надёжного сохранения финала progress-карточка удаляется.
- Ключ каждого ручного подтверждения — неповторимый UUID, привязанный к точному Telegram chat/message и активному run. Кнопки до рестарта честно протухают и не могут разрешить уже другую операцию. Меню, меняющие текущую задачу, проект, агента, модель или режим, содержат отпечаток контекста; старая кнопка не архивирует и не перенастраивает задачу, выбранную позднее.
- Привязки Telegram-сообщений хранятся в индексированной таблице `runtime.sqlite`. Параллельные `agent-hub-main.mjs`, `send-message.mjs` и `send-images.mjs` используют транзакционные upsert/delete, а WAL и `busy_timeout` обеспечивают межпроцессную запись без каталога событий. Хранилище ограничено 500 привязками и 30 днями.
- При штатной остановке очищаются индикатор набора, таймеры очереди, прогресса и наблюдения; незавершённые очереди и запуски остаются в состоянии для восстановления после старта. Отложенные сообщения одной задачи всегда запускаются по `createdAt`: более новое сообщение не обходит ни старую очередь, ни старую запись, требующую решения. На время фактической передачи запись получает состояние `dispatching`, исчезает из блока ожидания и после создания точного run переводит сохранённую квитанцию в `accepted`; временный обрыв Codex App Server повторяет тот же первый элемент с задержкой, а не запускает следующий.
- Изображения, голосовые и запросы озвучивания до фиксации Telegram offset атомарно сохраняются отдельными работами в `data/background-jobs/`. Ограниченные FIFO-очереди восстанавливаются после аварийного завершения процесса, сохраняют исходную задачу, модель и режим и удаляют запись после обработки. Отложенные пользовательские сообщения имеют TTL `deferredInputTtlHours` (по умолчанию 168 часов); после него временные файлы и старая кнопка очищаются предсказуемо. Внешние API не имеют общего ключа идемпотентности, поэтому гарантия — at-least-once: потеря принятой работы закрыта, но при падении точно между внешним действием и локальной отметкой его завершения редкий повтор теоретически возможен.
- Потенциально медленные команды просмотра `/status`, `/streams`, перелистывание списка и `/diff` выполняются в отдельной ограниченной очереди с параллелизмом два. Они не задерживают приём следующей команды, в частности `/cancel`; изменяющие поток callbacks остаются в основном последовательном контуре, чтобы сохранить порядок мутаций состояния.
- Каждый финальный ответ до закрытия run сначала сохраняется отдельными атомарными файлами в `data/delivery-outbox/`; уведомления из `send-message.mjs` попадают туда при временной сетевой ошибке. Для медиа-карточки при ошибке загрузки используется текстовый fallback. Очередь безопасно принимает сообщения от параллельных процессов Codex/Claude, переживает рестарт, сохраняет порядок частей одного ответа, заменяет устаревший недоставленный progress и повторяет доставку с экспоненциальной задержкой, учитывая Telegram `Retry-After`. Отложенная или временно ошибочная группа не блокирует готовые сообщения других задач, повреждённый файл изолируется с суффиксом `.invalid-*`, а окончательно отвергнутый Telegram-запрос сохраняется как `.failed-*` для диагностики вместо удаления ответа. Служебные действия (`typing`, callback-ответы и редактирование старого прогресса) намеренно не ставятся в очередь. При сетевом таймауте Telegram не поддерживает ключ идемпотентности, поэтому редкий повтор уже принятого сервером сообщения технически возможен.
- `agent-hub.log` и `agent-hub-error.log` ротируются внутри процесса. По умолчанию каждый файл ограничен 5 МБ и хранится до пяти архивов; лимиты задаются через `logMaxBytes` и `logMaxFiles`.

### Sentry-диагностика

Sentry по умолчанию отключён. Для включения достаточно задать локальную переменную
`SENTRY_DSN`; альтернативно можно заполнить `diagnostics.sentry.dsn` и поставить
`diagnostics.sentry.enabled: true` в `config.json`. `SENTRY_ENVIRONMENT` и
`SENTRY_RELEASE` переопределяют соответствующие значения конфигурации.

Hub отправляет необработанные ошибки Node и глобальные ошибки Web/VS Code,
системные сбои lifecycle/restart, пофазного startup и SQLite recovery, терминальные
сбои фоновых задач, внутренние ошибки Runtime Command spool и Hub MCP, неожиданные
программные ошибки HTTP/Desktop IPC и необработанные исключения нативного
Desktop-host через локальный runtime.
Обычные ошибки валидации, авторизации, отмены и потери связи не отправляются.
Текст чата, история, вложения, параметры запросов,
произвольные breadcrumbs и идентификатор пользователя не передаются. Перед отправкой из
сообщений и stack trace удаляются пользовательские абсолютные пути, секреты и
query/hash URL; поток ограничен `diagnostics.sentry.maxEventsPerMinute`.

Каждое событие содержит безопасную категорию причины (`not-a-function`,
`unknown-icon`, `network`, `timeout` и другие), поверхность клиента, компонент,
действие и имя JS-ассета без origin/query/hash. Web-клиент прикладывает состояние
`online`/visibility/readyState и до 20 служебных breadcrumbs о подключении
диагностики, потере/восстановлении связи Hub, online/offline, видимости страницы
и типе глобальной ошибки. Это
кольцевой буфер в памяти: он не отправляется отдельно и сериализуется только при
ошибке. Исходный текст исключения, `console`, пользовательский ввод и сетевые
payload по-прежнему не передаются. Отправка асинхронная, ограничена таймаутом и
общим rate limit, поэтому при нормальной работе сетевых запросов к Sentry нет.

Для read-only проверки всех Agent Hub issues запрос к Sentry API не должен
содержать параметр `environment`, пока `SENTRY_ENVIRONMENT` не задан явно:

```text
GET /api/0/projects/$SENTRY_ORG/$SENTRY_PROJECT/issues/?statsPeriod=14d&query=is%3Aunresolved
```

Это соответствует `All Envs` в интерфейсе Sentry. Параметр
`environment=<name>` добавляется только для намеренной фильтрации одного
окружения; значение `prod` нельзя подставлять по умолчанию, иначе события без
такого тега будут ошибочно выглядеть отсутствующими.

### Озвучка

- Последние 100 текстов, связанных с кнопками `🔊 Озвучить`, сохраняются в `data/speech-texts.json`. Кнопки новых сообщений продолжают работать после рестарта бота.
- Silero TTS использует один worker последовательно до `ttsIdleTimeoutSeconds`, поэтому модель не загружается заново при каждом нажатии. Python обрабатывает stdin в основном потоке без фонового reader-потока, конфликтующего на Windows с `torch.package`; idle-timeout контролирует Node-клиент. Таймаут или повреждение канала останавливают всё дерево worker; следующий запрос запускает чистый процесс. Старые кнопки, созданные до появления постоянного хранилища, восстановить невозможно.

### Настройки интерфейса и доступа

Панель быстрых действий отправляется как постоянная `ReplyKeyboardMarkup`. Обычные ответы без собственных inline-кнопок повторно прикрепляют её, чтобы Telegram Desktop восстанавливал панель после локального скрытия. Если клиент всё же не показывает значок клавиатуры, синяя системная кнопка `Меню` содержит первой команду `⌨️ Показать кнопки` (`/menu`); она заново отправляет панель. Это обход клиентского ограничения Telegram: `is_persistent` является запросом к приложению, а не принудительной блокировкой скрытия.

- `showTaskProject` управляет префиксом проекта в `/streams`, когда включена кнопка проекта; если `showProjectButton` или `showTaskProject` равен `false`, список остаётся компактным.
- `guardConcurrentRepositoryWrites` по умолчанию равен `false`: разные задачи могут параллельно изменять один Git-репозиторий. Значение `true` включает предупреждение и требует явного подтверждения перед запуском второй задачи в том же Git-корне.
- `autoApproveOnStart` включает автоматические подтверждения после каждого запуска. Для Codex автоматически принимаются запросы команд, файловых изменений, дополнительных разрешений и безопасно заполняемые MCP-формы разрешений; произвольные формы ввода не автозаполняются. Для Claude используется `bypassPermissions`. В публичном примере значение оставлено `false`.
- `codexRpcTimeoutSeconds` ограничивает ожидание ответа локального Codex App Server; значение по умолчанию — 30 секунд.
- `codexExecutableAutoUpdate` по умолчанию включён на Windows. Обычный запуск берёт сохранённый проверенный Codex; перед созданием процесса сверяет официальный canonical path и один SHA-256, без поиска всех версий, повторной проверки подписи и `--version`. Раз в минуту после завершения запуска фоновая проверка ищет установленные официальные версии из OpenAI Desktop и VS Code extension: неизменившиеся байты используют сохранённые результаты, новые проходят Authenticode/SHA-256 и изолированный bounded canary при отсутствии активных Codex runs. Подготовленная версия применяется только при следующем безопасном запуске провайдера, без принудительного рестарта; ошибка фоновой проверки не ломает работающий Codex. Только первая настройка без проверенной версии или новый pin без подходящей сохранённой версии требуют синхронной проверки. Отзыв сертификата для неизменившихся байтов повторно не проверяется. Hub ничего не скачивает. Состояние, подготовленная версия и отдельный результат фоновой проверки доступны в runtime health как `codexExecutableUpdate` и сохраняются в `data/codex-executable-state.json` без auth-данных.
- `codexExecutableVersionPin` задаёт точную установленную версию (например, `0.152.1`), `codexExecutableAutoUpdate: false` отключает автоматическое принятие версий, а существующий `codexExecutable` остаётся самым сильным ручным pin пути. Эквивалентные переменные окружения: `CODEX_EXECUTABLE_VERSION_PIN`, `CODEX_EXECUTABLE_AUTO_UPDATE` и `CODEX_EXECUTABLE`.
- `contextAutomation` управляет обслуживанием контекста после терминального события хода. При включённой авто-свёртке Hub запускает её только после завершения хода и только выше заданного процента; при включённой авто-ротации готовый результат этой же свёртки передаётся в новый Thread без повторной свёртки. Если Codex сам свернул контекст посреди пользовательского хода, Hub даёт ходу завершиться и при превышении порога ротации переносит в новый Thread результат свёртки вместе со всеми сырыми элементами завершившегося хода; команды при этом повторно не запускаются. После свёртки используется предварительная оценка провайдера для той же свёртки и хода: время наблюдения должно быть не раньше границы свёртки, а интерфейс явно помечает значение как оценочное. При отсутствии такого наблюдения значение остаётся неизвестным. Ротация не запускает дополнительный ход для измерения: новый Thread создаётся, получает контекст и проходит свежее чтение с проверкой точного ID и статуса idle до переключения Stream и очереди. Принятый провайдером ход сохраняет точную identity из ответа RPC, даже если проекция Thread ещё отстаёт; задержка проекции не разрешает повторную отправку. Неизвестный результат восстанавливается по исходной квитанции без создания второго хода. Пока операция не закончена, Stream остаётся занятым, а очередь после ротации перенаправляется в новый Thread. Оба переключателя по умолчанию выключены; пороги по умолчанию — 75% и 20%.
- Выбранные проект, агент, задача, модели, Reasoning и режим Plan/Work сохраняются между перезапусками.
- В итоговой статистике Codex действует единый версионированный реестр цен. До `2026-09-08T00:00:00Z` сохраняются прежние цены за 1M входных / кэшированных входных / выходных токенов: `GPT-5.6 Sol` — `$5 / $0,50 / $30`, `GPT-5.6 Terra` — `$2,50 / $0,25 / $15`, `GPT-5.6 Luna` — `$1 / $0,10 / $6`. Начиная с этой границы используются подтверждённые цены: `GPT-6 Astra` — `$10 / $1 / $50`, `GPT-5.6 Sol` — `$4 / $0,40 / $20`, `GPT-5.6 Terra` — `$2 / $0,20 / $12`, `GPT-5.6 Luna` — `$0,20 / $0,02 / $1,20`. Точный момент изменения официальный источник не публикует, поэтому это первая проверенная календарная граница. Тариф выбирается по `completedAt`; при отсутствующем или повреждённом времени выбирается самая старая сохранённая версия, чтобы legacy-история не дорожала при открытии.
- Журнал, Статистика, итог хода, ПТЭ и денежные представления используют один и тот же `turnCreditBreakdown`; повторный backfill, restart или reprojection не меняет цену старого хода. Reasoning входит в output. Fast умножает расход `GPT-5.6` и `GPT-5.5` на `2,5`, `GPT-5.4` — на `2`; Spark по принятому локальному правилу учитывается как `0 cr`. Для каждой категории выводится её доля от точной общей суммы; округлённые доли всегда складываются ровно в 100%.
- `cr` — общая межпровайдерная единица расчётного расхода: `1 cr = $0,04` API-эквивалента. Для Claude итоговый `total_cost_usd`, который Claude CLI рассчитывает по всему ходу вместе с субагентами, умножается на `25`; если общего итога нет, Agent Hub суммирует доступный `modelUsage[*].costUSD`, а для внешних и исторических транскриптов рассчитывает стоимость по официальным API-тарифам модели и категориям токенов. Учитываются cache write 5m (`1,25×`), cache write 1h (`2×`), cache read (`0,1×`), Fast и US-only inference; для Sonnet 5 применяется вводная цена `$2/$10` за MTok до 31 августа 2026 и `$3/$15` после. Это API-эквивалент, а не фактический счёт подписки Anthropic. Старые несопоставимые `кТЭ` не используются; неизвестная модель остаётся без выдуманной оценки.
- Единица расхода переключается глобально между `ПТЭ`, `cr`, `$` и `₽`; синхронизированные кнопки доступны на страницах `Журнал` и `Статистика`, стоят в этом порядке, а формулы вынесены в свёрнутую справку журнала. `ПТЭ` — приведённые токен-эквиваленты, приведённые к входному токену GPT-5.4 / GPT-5.6-Terra: `1 cr = 16 000 ПТЭ`; коэффициенты модели и Fast уже входят в credits. Доллары и рубли не сокращаются до `k/M`: до одной денежной единицы показываются два знака после запятой, начиная с одной — один, разряды разделяются пробелами. Рубли рассчитываются через долларовый API-эквивалент (`25 cr = $1`) и официальный курс USD/RUB Банка России. Agent Hub обновляет курс при запуске без блокировки запуска сервера и сохраняет последнее успешное значение в `data/exchange-rates.json`; при временной недоступности источника используется кэш.

### Codex models

`/model` switches the Codex model used for the next `turn/start` request. `/reasoning` selects the reasoning effort, and `/mode` selects `Work` (`default`) or `Plan` (`plan`). The Reasoning and Plan/Work buttons are in the second menu row. The selected values are saved in `data/runtime.sqlite` and sent explicitly with every Codex turn, including turns in resumed tasks. Defaults are configured in `config.json`:

On Windows, Agent Hub discovers already installed official Codex binaries from OpenAI Desktop and the official OpenAI VS Code extension, verifies their publisher and exact bytes, and compares executable-reported versions instead of directory timestamps. A newly seen identity must pass the isolated App Server compatibility canary before activation; the previous last-known-good remains available for one bounded startup rollback.

For Claude Code, `/model` still switches `sonnet`, `opus`, or `haiku`.

### Claude Code (опционально)

Codex остаётся провайдером по умолчанию. Чтобы использовать Claude Code, сначала установите и авторизуйте CLI, затем укажите:

```json
{
  "provider": "claude",
  "claudeExecutable": "claude",
  "claudeModel": "sonnet",
  "claudePermissionMode": "acceptEdits"
}
```

Либо запустите установщик с `python install.py --provider claude`. Провайдер также переопределяется переменной `AI_PROVIDER`, путь к CLI — `CLAUDE_EXECUTABLE`, модель — `CLAUDE_MODEL`. При стандартном значении `claude` в Windows Agent Hub на каждом старте выбирает самый новый установленный native binary из расширений Claude Code для VSCode и глобального npm-пакета; поэтому обновление расширения автоматически выравнивает версию. Явный путь или `claudeExecutableArgs` всегда отключает автопоиск и используется без подмены. Если Claude CLI не установлен и его лимиты не нужны, задайте `"claudeRateLimitPolling": false`, чтобы отключить фоновый опрос `/usage`; ручные команды и поддержка Claude при этом остаются доступны.

Claude запускается в headless-режиме с `stream-json` и сохраняет `session_id` сразу после события инициализации; продолжение доступно через `/resume <ID>`. Поскольку CLI не предоставляет отдельный машиночитаемый реестр сессий, `/streams` безопасно индексирует локальные transcript-файлы `~/.claude/projects`, отбрасывает subagent-сессии и служебные command-only сессии (`/usage` и подобные), затем оставляет только потоки из разрешённых папок. Для названий HUB сначала использует пользовательский `custom-title` из `/rename`, затем автоматически сгенерированный `ai-title`, а пользовательский запрос служит запасным вариантом. Возобновление запускается из исходного корня сессии, даже если последние действия Claude выполнялись во вложенном каталоге. `/status` получает актуальные лимиты через встроенную команду Claude Code `/usage`, не обращаясь к модели. Режим `acceptEdits` разрешает правки в рабочей папке, но не произвольные команды. Telegram-кнопка автоподтверждения включает `bypassPermissions` и должна использоваться лишь в доверенной рабочей папке. По умолчанию автоматический режим сбрасывается после перезапуска; постоянное включение задаётся локальным параметром `"autoApproveOnStart": true`.

### Несколько рабочих папок

Добавьте разрешённые папки в `projects`. Значение `projectRoot` задаёт папку по умолчанию и должно совпадать с одним из путей:

```json
{
  "projectRoot": "C:\\Projects\\Main",
  "projects": [
    { "name": "Основной", "path": "C:\\Projects\\Main" },
    { "name": "Сайт", "path": "C:\\Projects\\Website" }
  ]
}
```

Если `projects` отсутствует, бот продолжает работать с единственным `projectRoot`. В Telegram используйте `/projects` или кнопку «📁 Проект». Кнопка показывается по умолчанию; чтобы скрыть её, установите `"showProjectButton": false` — команда `/projects` продолжит работать. Имя проекта перед названием потока в `/streams` показывается только вместе с кнопкой проекта; `"showTaskProject": false` позволяет отдельно скрыть этот префикс. При переключении проекта создаётся новый выбранный поток, а уже запущенные потоки в других проектах продолжают выполняться.

## Безопасность

- Доступ проверяется одновременно по `allowedUserIds` и `allowedChatIds`.
- По умолчанию принимаются сообщения только из приватных чатов.
- Codex работает с `workspaceWrite`, без сетевого доступа для команд агента.
- Claude Code использует собственную систему разрешений; рекомендуемый режим — `acceptEdits`.
- Подтверждения команд, изменений файлов и дополнительных профилей разрешений отправляются владельцу в Telegram.
- Автоподтверждение после запуска определяется локальной настройкой `autoApproveOnStart`; безопасное значение в примере — `false`.
- Не публикуйте внешний `config.json`, каталоги runtime-`data`, окружения моделей и логи.

Бот предоставляет удалённый доступ к Codex и папкам из `projects` (либо к `projectRoot` в однопроектной конфигурации). Не добавляйте недоверенных пользователей в разрешённый список. Текущая версия не предназначена для совместного использования одного процесса несколькими людьми: состояние Codex и активная задача общие.

```powershell
npm run check
npm test
npm run test:e2e
npm run test:all
npm run doctor

```

Для обычной функциональной проверки используйте `npm test`.
`npm run test:visual` отдельно проверяет геометрию карточек и матрицу тем
аккаунтов журнала; эти две браузерные матрицы не входят в unit-набор.
Focused-публикация UI-изменений включает их автоматически.
`npm run test:all` обнаруживает все
unit/architecture-тесты в зеркальном дереве `tests`, visual-набор ровно один раз,
process E2E, installer и проверки VS Code. После подготовки зависимостей и syntax
preflight независимые файлы всех групп допускаются по измеренной нагрузке всего
дерева процессов: целевой бюджет 40% мощности CPU и 40% физической RAM, с учётом
свободного ресурса машины. Git и браузеры входят в измерение. Фиксированного
максимума файлов нет; общий изменяемый ресурс сериализует только его владельцев.
Резерв ресурса сохраняется до завершения файла, включая ожидания I/O. На Windows
тот же Job, который ведёт учёт дерева, ограничивает его CPU-квотой 40%; закрытие
снимает и проверяет эту квоту, а ошибка закрытия остаётся ошибкой проверки. На
POSIX допуск остаётся кооперативным. Живые тесты не убиваются и не повторяются
из-за нагрузки. Квота Windows относится к циклам планирования, а не к каждому
короткому замеру CPU. Итог содержит peak CPU/RSS, число
превышений в замерах и ожидание допуска. Каждый файл получает собственный
temp/home/state root. Неизвестные входы запрещают кэш, а не параллельность.
Все тестовые группы выполняются даже при падении
одной из них, после чего команда возвращает единый список проблем. Поддерживать отдельный список файлов или дополнительно запускать
каждую группу вручную не нужно.

`npm run test:e2e` выполняет полностью локальную CLI-приёмку настоящего `agent-hub-main.mjs` и composition root `agent-hub-server.mjs` через fake Telegram Bot API, Codex App Server и Claude CLI. Рабочий бот, токен, задачи и `data` не затрагиваются. Полное покрытие сценариев перечислено в [E2E_TEST_MATRIX.md](E2E_TEST_MATRIX.md). `telegramApiBaseUrl`, `codexExecutableArgs`, `claudeExecutableArgs` и `progressStartDelayMs` служат безопасными точками подмены для стенда; производственные значения по умолчанию остаются прежними. На Windows процессные ожидания автоматически получают двукратный запас для нестабильного времени запуска дочерних процессов; это не меняет проверяемые лимиты отзывчивости. Для диагностики медленной машины множитель можно переопределить через `TELEGRAM_E2E_TIMEOUT_MULTIPLIER`.

Telegram сразу показывает `typing`, а содержательная progress-карточка по умолчанию появляется через 500 мс после безопасной проверки активности и Git-снимка. Проверка внешней активности и конфликта репозитория выполняется параллельно; лишний `thread/resume` перед каждым ходом удалён, а восстановление незагруженного треда остаётся в retry-маршруте `turn/start`. `/status` получает каталог и лимиты параллельно, держит лимиты в минутном кэше и после первой загрузки каждого баннера повторно использует Telegram `file_id`. Обработка update дольше двух секунд записывает в лог отдельные времена handler/state и возраст доставки, чтобы задержку Telegram не путать с задержкой приложения. Итоговый ответ сначала сохраняется в durable-outbox и отправляется немедленным flush; заменяемая progress-карточка остаётся видимой до подтверждённой доставки последней части финала.

`npm run check` одним процессом синтаксически разбирает все `.mjs` модули без их исполнения. `npm test` автоматически находит и проверяет модули функционально, а `npm run test:e2e` — жизненный цикл отдельного процесса Agent Hub.

Текущий план выделения компонентов из исторически выросшего `agent-hub-server.mjs`, границы этапов и критерий завершения описаны в [AGENT_HUB_MODULES.md](AGENT_HUB_MODULES.md). Стабилизационные исправления и архитектурная декомпозиция учитываются раздельно в [STABILIZATION_CHECKLIST.md](STABILIZATION_CHECKLIST.md).

## Совместимость после переименования

Исходники и пользовательские названия используют `Agent Hub`, `Agent Hub Server`, каталог `AgentHub`, исполняемую точку входа `agent-hub-main.mjs` и composition root `agent-hub-server.mjs`. Сокращённый владелец хода в карточках — `HUB`.

Внешний runtime Agent Hub находится в `%LOCALAPPDATA%\AgentHub`. Управляющие named pipe, переменные окружения и точки запуска используют единый префикс `Agent Hub`.

Основная декомпозиция выполнена. Исполняемый bootstrap находится в `agent-hub-main.mjs`: он устанавливает process-level handlers и вызывает idempotent start/shutdown API composition root. Внутренний orchestrator собирается четырьмя явными фазами: provider/application, client/runtime, interaction shell и execution/bootstrap; Telegram runtime и startup/shutdown имеют одного финального владельца. Telegram Bot API обслуживают `TelegramClient` и `TelegramPollingController`; команды и callback-группы settings/task/input принадлежат отдельным application services. Desktop/Mini App разделены на snapshot/history, application router, message, attachment, settings и deferred-input services. Жизненный цикл хода проходит через общий `RunCoordinator`, а `AgentProviderRegistry` связывает самостоятельные Codex/Claude catalog/task/turn/event/snapshot/completion/recovery services. Restart и shutdown используют единый `RuntimeResourceRegistry` с фазами `flush → suspend → finalize`; `AgentHubStartupCoordinator` задаёт порядок control plane, восстановления провайдеров и readiness, `RunProgressPresentation` формирует клиентскую карточку, `TaskObservationService` владеет observed lifecycle, `ProviderTaskActivityService` — определением внешней активности Codex/Claude, `SelectedTaskWatchService` — безопасным подключением к выбранному внешнему ходу, `RateLimitTelemetryService` — безопасным чтением и периодическим сохранением лимитов, `TaskMetadataStore` — bounded-состоянием названий и настроек задач, `RunJournalService` — общей journal projection и bounded last-message state, `TurnEndDeliveryService` — terminal projection/retry, `CodexRunFinalizer` — финальным учётом управляемых Codex-ходов, `CodexTerminalReconciliationService` — восстановлением и коррекцией завершившихся Codex-ходов, `CodexUsageTracker` — bounded token/context state, `CodexContextMaintenanceService` — обслуживанием свёртки и периодической санацией rollout, а `RuntimeTimerCoordinator` — именованными таймерами процесса. Claude transcript discovery/parsing/cache находится у Claude provider, Codex answer policy — у Codex provider и application history. SQLite-журнал не зависит от web-интерфейса: persistence хранит read model, application-сервис строит lazy projection, web лишь публикует её. Журнал не блокирует запуск control pipe и polling и штатно закрывает SQLite. `ApplicationCommandBus` требует явную task-цель и `clientId`, а task-lane, observer и provider ports сохраняют будущий `streamId`, не закрепляя логическую задачу за одним ThreadID/session ID. Внутренние модули распределены по слоям [`src`](src/README.md), тогда как стабильные entrypoint и CLI остаются в корне. `agent-hub-server.mjs` остаётся стабильным composition facade и больше не запускает процесс при импорте. Целевая схема описана в [ARCHITECTURE_V2.md](ARCHITECTURE_V2.md), текущие границы — в [AGENT_HUB_MODULES.md](AGENT_HUB_MODULES.md).

Низкоуровневый Codex App Server transport вынесен в `src/providers/codex/codex-app-server-transport.mjs`: модуль владеет дочерним процессом, JSON-RPC request/response, таймаутами, разбором событий, остановкой дерева и коротким ограниченным кэшем `thread/read`. Прикладные события, live snapshot, запуск, завершение и восстановление Codex обрабатывают отдельные provider services; composition root только связывает их с transport, run registry и delivery.

Lifecycle Claude CLI вынесен в `claude-run-controller.mjs`: контроллер запускает detached-процесс, ведёт файлы потока, читает `stream-json` с сохранённого офсета, завершает или отменяет дерево и подключается к ходу после рестарта. Смысловая реакция на события, progress и доставка ответа остаются в композиции бота.

Lifecycle progress-карточки вынесен в `task-progress-controller.mjs`: модуль владеет отложенным созданием, последовательными edit, heartbeat-активностью, повтором временных ошибок, удалением старых bindings и финальным закрытием карточки. Формат текста принадлежит `run-progress-presentation.mjs`, а фактический Telegram transport передаётся контроллеру как зависимость.

Polling уже подключённого внешнего или восстанавливаемого хода разделён между `task-observer-controller.mjs` и `task-observation-service.mjs`. Контроллер управляет таймером и переходами `active/completed/unknown/error`, сервис — созданием, обновлением, завершением и синхронизацией наблюдаемого run. После каждого асинхронного чтения повторно проверяется актуальность run; поздний snapshot не применяется к завершённой или переключённой задаче. При создании observer сохраняется логический `streamId`, если он уже известен.

`npm run doctor` не ограничивается поиском файлов: он проверяет Telegram Bot API через `getMe`, запускает изолированный Codex App Server и выполняет `initialize + thread/list`, а также проверяет авторизованную сессию Claude через `/usage`. Все live-probes имеют таймаут и не создают новых задач.

В Windows для ручного запуска из workspace остаётся `start.ps1`. После активации он направляет запуск в `AgentHub.RuntimeHost.exe`; штатный автозапуск и безопасный рестарт работают напрямую через Runtime Host, а сам сервер — в Node.js.

На экране запуска доступны текст ошибки, «Повторить упавшие этапы» и
«Перезапустить Хаб». Повтор доступен после завершения первичного запуска и
повторяет только восстанавливаемые неудачные этапы, не проигрывая заново
завершённые операции. Для оставшихся инфраструктурных ошибок нужен перезапуск.
Обе команды используют обычный авторизованный транспорт. Если процесс полностью
остановлен, браузер не может запустить его: используйте установленный
`%LOCALAPPDATA%\AgentHub\AgentHub.RuntimeHost.exe` или ярлык на него.

Команды: `/agent`, `/model`, `/reasoning`, `/mode`, `/projects`, `/new`, `/streams`, `/resume`, `/rename`, `/archive`, `/current`, `/thread`, `/status`, `/approvals`, `/restart`, `/diff`, `/cancel`, `/help`. Старые `/tasks` и `/engine` сохранены как совместимые псевдонимы. Кнопка `📥 Задача` и `/task` убраны из публичных меню, но сама команда и старый текст кнопки остаются доступными для совместимости и работы с настоящими Dashboard Task.

`/archive` архивирует текущий поток Codex и автоматически выбирает первый оставшийся поток из списка. Та же команда доступна кнопкой `❌ Архивировать текущий поток` в конце `/streams`. При архивации через кнопку исходное меню обновляется на месте: архивированный поток исчезает, а автоматически выбранный помечается как текущий.

При обычном выборе потока Codex или Claude через `/streams` бот сразу переключает локальный адрес агента, проекта и thread/session, а дорогое `thread/resume` выполняет только перед фактическим обращением к Codex. Удаление списка и отправка уведомления выполняются параллельно. Если выбран другой поток, бот присылает то же форматированное уведомление `Текущий поток изменён`, что и при переходе по ответу на привязанное сообщение. Повторный выбор текущего потока через список, карточку статуса или `/resume <ID>` присылает уведомление `Текущий поток уже выбран` с кнопкой показа последнего сообщения.

`/thread` показывает ID выбранного потока. Откройте активную папку в Codex App или VS Code и выберите этот поток в истории; из CLI его можно продолжить командой `codex resume <ID>`. Telegram сам не запускает второй turn в занятом потоке. Если VS Code всё же создаёт несколько параллельных turns одного треда, локальный rollout-индекс хранит их тексты раздельно по настоящему `turn_id`; карточка остаётся закреплена за наблюдаемым turn, показывает общее число активных turns и не закрывается при завершении соседнего.

## Голосовые сообщения

Голос распознаётся локально через `faster-whisper`. По умолчанию используется `large-v3-turbo` на NVIDIA GPU (`whisperDevice: "cuda"`, FP16); Windows-установка голосового компонента ставит закреплённые CUDA 12 cuBLAS/cuDNN runtime-пакеты в отдельное Python-окружение, а процесс распознавания подключает их DLL непосредственно из этого окружения. Модель занимает видеопамять только на время отдельного процесса распознавания, после чего процесс завершается и освобождает VRAM. Если CUDA недоступна или её запуск завершается ошибкой, тот же файл автоматически обрабатывается на CPU в INT8. Модель и устройство выбираются параметрами `whisperModel` и `whisperDevice`; файлы модели и временные аудиофайлы не попадают в Git.

Для каждого непустого итогового ответа бот по умолчанию показывает кнопку `🔊 Озвучить`. Синтез выполняется локально через Silero TTS, а результат отправляется как Telegram voice message в OGG Opus. Запросы выполняются последовательно через ограниченную и сохраняемую на диск очередь максимум из десяти работ: повторные нажатия не создают неограниченное число одновременных синтезов, а принятый запрос переживает рестарт процесса. Один worker обслуживает последовательные запросы и держит модель загруженной до `ttsIdleTimeoutSeconds`; после штатного idle-exit следующий запрос создаёт новый процесс. Worker сообщает о принятии запроса, загрузке модели, начале и завершении каждого фрагмента и кодировании результата. Если текущий этап не даёт прогресса дольше `ttsRequestTimeoutSeconds` (по умолчанию 60 секунд), всё дерево зависшего worker принудительно останавливается; следующий запрос получает чистый процесс. Поэтому длинное исправно обрабатываемое сообщение не обрывается через 60 секунд от начала синтеза. Последние 100 текстов кнопок сохраняются в `data/speech-texts.json`, поэтому новые кнопки переживают рестарт. Модель, голос, idle timeout, минимальная длина обычного ответа и максимальный объём озвучиваемого текста задаются параметрами `ttsModel`, `ttsSpeaker`, `ttsIdleTimeoutSeconds`, `ttsButtonMinChars` и `ttsMaxChars`; значение `ttsButtonMinChars` по умолчанию равно `1`. При первом озвучивании Silero скачивает модель во внешний runtime-кэш `data/models/silero`.

Команда `npm run tts:smoke` проходит тот же Node → Python → Silero → OGG тракт без отправки в Telegram, проверяет непустой результат и удаляет диагностический файл.

Процессный E2E отдельно проверяет пользовательский путь от callback кнопки до multipart-вызова `sendVoice`, освобождение очереди после зависшего worker и однократную доставку принятой озвучки после аварийного рестарта бота.

Если пользователь отвечает на сообщение Telegram через «Ответить», бот добавляет текст или подпись цитируемого сообщения в запрос как отдельную цитату. Команды `/...` при этом продолжают распознаваться по самому новому сообщению.

### Пакеты пересланных сообщений

Первая пересылка — текст, фотография, изображение-документ или альбом — не запускает ход немедленно, а открывает сохраняемый черновик для выбранной в этот момент задачи. Следующие пересылки, изображения и обычные сообщения пользователя добавляются в ту же пачку; одна компактная карточка показывает количество реплик и изображений и предлагает `✅ Отправить пачку`, `↩️ Убрать последнее` или `🗑 Отменить`. Telegram передаёт альбом как несколько обновлений с общим `media_group_id`; Agent Hub сохраняет их отдельными упорядоченными элементами одной пачки. Таймер автоматической отправки намеренно не используется: Telegram не сообщает боту, что пользователь закончил пересылать переписку или дописывать собственный комментарий.

При отправке Agent Hub формирует один запрос в исходном порядке. Пересланные реплики помечаются как `Переслано · <автор>`, а собственные дополнения — как `Вы`. Для современного `forward_origin` и совместимых legacy-полей сохраняются доступные Telegram имя пользователя, скрытое имя, канал или чат; если источник не раскрыт, явно указывается `источник скрыт`. Текст, скопированный вручную вместо функции Telegram «Переслать», технической отметки источника не имеет и считается собственным сообщением пользователя.

Черновик закреплён за исходной задачей, моделью и режимом, сохраняется в `runtime.sqlite` и переживает рестарт Agent Hub. Изображения загружаются долговечной фоновой очередью, не блокируют обработку Telegram-команд и передаются агенту только вместе с пачкой. До завершения загрузки кнопка отправки не запускает ход; при ошибке следующее нажатие повторяет загрузку. `Убрать последнее`, отмена и истечение срока черновика удаляют уже загруженные временные файлы. Если к моменту отправки задача уже занята, вся пачка вместе со всеми изображениями становится одним сохранённым входом с обычным выбором очереди, а не набором независимых сообщений.

## Изображения

Бот принимает Telegram-фотографии и файлы с MIME-типом `image/*`. Одиночное непересланное изображение вне открытой пачки по-прежнему запускает самостоятельный запрос: подпись используется как запрос, а без подписи Codex анализирует картинку с учётом предыдущей переписки. Пересланные изображения и любые изображения при уже открытой пачке обрабатываются по правилам раздела выше. Загрузка изображений и распознавание голоса выполняются вне последовательного цикла Telegram-обновлений: долгий файл не блокирует команды и переключение, а будущий ход остаётся закреплён за задачей, моделью и режимом, выбранными в момент получения. Общая сохраняемая FIFO-очередь обрабатывает один медиафайл за раз и принимает максимум 20 работ, поэтому серия голосовых не запускает параллельно несколько тяжёлых Whisper-процессов и не теряется при аварийном рестарте бота. Временная ошибка получает до трёх попыток с ограниченной экспоненциальной задержкой; состояние следующей попытки сохраняется и восстанавливается после аварийного рестарта. Временный файл удаляется после завершения задачи.


### Восстановление старой истории

При открытии страницы истории Хаб проверяет до 20 показанных завершённых ходов
тем же механизмом восстановления, который используется при запуске. Поэтому
старые диалоги вне стартового окна из 200 завершений тоже получают исправление
потерянных идентификаторов и дублей. Замена возможна только по точному совпадению
сохранённого завершения и журнала команд; текст сообщений не используется для
сопоставления. Исправляется только открытая страница, без повторной отправки
провайдеру и без полной пересборки истории. При отсутствии подтверждений история
остаётся без изменений.

### Единые замеры задержек

`data/command-traces.sqlite` — общий журнал замеров команд, интерфейса, запуска,
обработки завершений и числовых показателей runtime/SQLite. Запись идёт через
существующий отдельный worker; переполнение отбрасывает диагностику, не команды.
Начало и завершение ожидания связаны `operationSpanId`, команды — исходным ID,
серверные записи — экземпляром и релизом. Тексты сообщений, DOM, URL и тела
запросов в новые клиентские замеры не попадают.

Хранение: до 7 дней и максимум 250 000 записей; очистка работает и без новых
событий. Лимит количества может сокращать фактическую глубину истории. SQLite
повторно использует освободившиеся страницы; размер файла не обязан сразу
уменьшаться после удаления старых строк.

Отчёт без изменения рабочей БД:

```powershell
npm run trace:report -- "$env:LOCALAPPDATA/AgentHub/data/command-traces.sqlite" --hours 24 --limit 25
```

JSON содержит размеры файлов и диапазон данных, p50/p95/p99 по этапу/действию,
медленные операции и незакрытые диагностические маркеры. Последние не доказывают
зависший ход: конец мог быть потерян при остановке или очистке. Runtime-health
показывает уже существующие накопительные метрики процесса отдельно от задержки
конкретного запроса. Детальные UI-замеры доступны после загрузки новых клиентских
файлов; Long Tasks зависит от поддержки браузера.

Полное обновление каталога и данных стоимости после старта выполняется в фоне.
Готовность приложения по-прежнему ждёт обязательного восстановления владельцев
активных ходов и завершений, но не этого дополнительного обновления.

### Reobserving legacy checkpoint annotations

A later primary synchronization proof does not prevent startup when the imported
checkpoint remains evidence-only and all original evidence matches exactly.
The original operation stays waiting and cannot resume or publish automatically.
The current checkpoint and the first imported snapshot are both preserved.

Для узкого регрессионного прогона перезапуска: `node --test tests/runtime/restart-lock-handoff.test.mjs tests/runtime/runtime-host-owned-compat.test.mjs`. Второй тест в Windows собирает настоящий RuntimeHost с изолированным локальным Node fixture; провайдеры и рабочий runtime не запускаются. Повторный запуск после доказанного terminal failure проходит штатным restart; неизвестный исход не повторяется. Доставка подтверждается только совпадением expected release, ready instance lock и process identity authenticated control. Продолжение агента разрешено после этого подтверждения, а не обычным queued сообщением перед cutover.

Focused launcher lifetime and message terminal/reload checks: `node --test tests/runtime/runtime-host-parent-lifetime.test.mjs tests/runtime/runtime-host-owned-compat.test.mjs tests/composition/message-command-terminal-visibility.test.mjs tests/providers/codex/codex-event-service.test.mjs`. Cold `AgentHub.RuntimeHost.exe --spawn-independent` returns native detached creation outcome, not readiness; denied job breakaway fails visibly. Controlled restart owns a separate direct detached host until exact lock/ready proof. Payload-free host lifetime evidence is in runtime `data/runtime-host-lifetime.jsonl`.

Focused real Stop outcome regression: `node --test tests/composition/codex-stop-terminal.test.mjs`. Live-run versus stale-catalog precedence: `node --test --test-name-pattern 'authoritative live run clears stale catalog unknown' tests/interfaces/desktop/desktop-snapshot.test.mjs`. These isolated checks send no provider input or Stop.

Cancelled agent history cards display «Остановлен» from the canonical cancellation
projection, including when an existing card updates or history reloads. This label
does not infer cancellation from a Stop acknowledgement or alter message content.
Focused rendering check: `node --test --test-name-pattern 'cancelled agent card'
tests/public/message-view-controller.test.mjs`.
