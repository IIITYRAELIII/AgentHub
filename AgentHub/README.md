# Agent Hub Server

Локальный сервер задач и личного журнала Codex App Server и Claude Code CLI. Каждый участник запускает собственный экземпляр со своим AI-аккаунтом, локальными rollout и разрешёнными рабочими папками. Telegram и Mini App подключаются только в профилях, где они нужны.

Telegram, [Windows-клиент](DesktopApp/README.md) и [Android-клиент](AndroidApp/README.md) видят общий каталог, локальную историю, выбранную задачу, настройки и живые ходы; второй процесс Codex/Claude не запускается. Desktop-клиент использует отдельный аутентифицированный named pipe. Android-клиент переиспользует опубликованный интерфейс Mini App, но авторизуется ключом доверенного устройства из Android Keystore, а не через Telegram.

Текущее состояние работ по надёжности и оставшиеся задачи ведутся в [STABILIZATION_CHECKLIST.md](STABILIZATION_CHECKLIST.md).

## Требования

- Node.js со встроенным `node:sqlite`: 22.5 или новее, рекомендуется 24+;
- установленный и авторизованный Codex CLI либо Claude Code CLI;
- Python 3.10 или новее — только для распознавания и синтеза голосовых сообщений.
- Для сборки необязательного Android-клиента: JDK 17, Android SDK API 36 и Gradle 8.13. Обычная установка HUB их не требует.

## Установка

У Agent Hub три переключаемых профиля:

- `full` — Telegram, Mini App и локальный журнал;
- `telegram` — Telegram и локальный журнал без Mini App и домена;
- `journal` — только личный локальный журнал и расширение VS Code, без Telegram, домена и Cloudflare.

Для участника команды, которому нужен только журнал, выполните из корня workspace:

```powershell
python Utilities/AgentHub/install.py --profile journal
```

Токен, Telegram ID и домен не запрашиваются. Установщик создаёт личный runtime, устанавливает Codex hooks и общее расширение VS Code, восстанавливает `WORK_LOG.md` из локальных `%USERPROFILE%\.codex\sessions` и `archived_sessions`, добавляет Agent Hub в автозапуск и запускает его. После первого запуска подтвердите оба hook в Codex через `/hooks` и выполните `Developer: Reload Window` в VS Code. Подробная памятка для участника и его Codex: [JOURNAL_SETUP.md](JOURNAL_SETUP.md).

Для Telegram без Mini App:

```powershell
python Utilities/AgentHub/install.py --profile telegram
```

Для полной версии сначала создайте бота через `@BotFather`, узнайте числовой Telegram user ID, затем выполните:

```powershell
python Utilities/AgentHub/install.py --profile full
```

Установщик создаёт изолированный runtime в `%LOCALAPPDATA%\AgentHub` (в Linux — `$XDG_STATE_HOME/agent-hub`). Там хранятся личная конфигурация, ledger, история лимитов и версионные копии исполняемого сервера; в Git остаются только общие исходники и тесты. Повторный запуск сохраняет Telegram- и Mini App-настройки и после обновления запрашивает штатный безопасный перезапуск существующего Agent Hub. Активная работа при необходимости откладывает переключение до безопасного момента. Для развёртывания release без запроса перезапуска используйте `--skip-restart`. Для голосовых сообщений используйте:

```powershell
python Utilities/AgentHub/install.py --install-voice
```

Для миграции существующей установки или публикации новой версии выполните:

```powershell
npm run runtime:deploy
npm run runtime:activate
npm run doctor
```

Для сопровождающего полная публикация всех поверхностей выполняется одной
командой из `Utilities/AgentHub`:

```powershell
npm run publish:all
```

Команда сама выполняет полный набор проверок исходников, unit-тестов, процессных
E2E и тестов расширения VS Code — отдельно запускать их перед публикацией не
нужно. Перед `npm run publish:all` не запускайте вручную `npm run check`,
`npm test`, `npm run test:e2e` или тесты расширения: это только повторит уже
встроенный прогон. Затем команда публикует Cloudflare Worker, создаёт и активирует
runtime-релиз, устанавливает локальное расширение VS Code и через защищённый
локальный control channel запрашивает штатный перезапуск Agent Hub.
Если выполняются активные задачи, сервер сам откладывает перезапуск до
безопасного момента. Для локальной отладки доступны параметры `--skip-tests`,
`--skip-worker` и `--skip-restart`; обычная публикация использует полный набор.
Git commit и push намеренно остаются отдельными: скрипт не придумывает сообщение
коммита и не публикует случайные изменения рабочего дерева.

`runtime:deploy` создаёт новый неизменяемый release и атомарно переключает `current.json`, сохраняя предыдущую версию для `npm run runtime:rollback`. CLI сравнивает физические пути точки входа, поэтому эти команды и `send-message.mjs`/`send-images.mjs` корректно запускаются также из workspace, открытого через Windows junction. Команда `runtime:activate` один раз переносит конфигурацию, данные и модели из рабочей папки во внешний runtime, создаёт маркер активации и удаляет старый workspace-`config.json`. Выполняйте её только при остановленном старом боте; для живой установки сначала дождитесь завершения ходов.

Текущий runtime можно проверить через `npm run runtime:status`. После активации `/restart` запускает release, указанный в `current.json`, поэтому новая публикация начинает действовать при следующем штатном рестарте. Автозапуск Windows также указывает на внешний launcher. В Windows фоновый запуск проходит через GUI-хост `wscript.exe` и `launch.vbs`, поэтому бот не создаёт окно PowerShell или вкладку Windows Terminal. Для совместимости с прежними служебными updater-скриптами рядом устанавливается эквивалентный alias `runtime-launch.vbs`; штатной точкой входа остаётся `launch.vbs`.

После `runtime:deploy` установите пользовательские `UserPromptSubmit`- и `Stop`-hooks командой `npm run hook:install` и проверьте `npm run hook:status`. Статус показывает не только конфигурацию и доступность стабильного launcher, но и последние фактически принятые start/stop-вызовы. Первый hook до начала модели сразу сохраняет точный запрос, а затем дополняет ту же запись Git-baseline; повторная фаза объединяется с первой и не может стереть уже сохранённые данные. Если клиент Codex не вызывает hook, постоянно работающий terminal-аудит замечает активный ход по rollout и сам создаёт Git-baseline; `apply_patch` дополнительно сохраняется как резервный diff. Второй hook в конце передаёт статус, usage и данные rollout; ошибка чтения rollout обозначается как `unknown`, пока terminal-аудит не уточнит результат. Установщик аккуратно объединяет `%USERPROFILE%\.codex\hooks.json` с существующими hooks и ссылается на стабильный launcher runtime. Codex требует отдельно просмотреть и доверить новые hooks через `/hooks`; доверие привязано к их точному содержимому. После обновления runtime перезапустите Agent Hub Server, а открытые до установки клиенты Codex — переоткройте.

Для ручной настройки используйте `%LOCALAPPDATA%\AgentHub\config.json`. Путь к другому конфигу можно передать через `AGENT_HUB_CONFIG`, а токен — через `TELEGRAM_BOT_TOKEN`.

После активации workspace-команды `send-message.mjs` и `send-images.mjs` не читают Telegram-токен. Они передают только разрешённую операцию, аргументы и идентификатор вызывающей AI-сессии в локальный IPC живого runtime; уже доверенная release-копия выполняет отправку. Получатель повторно сверяется с allowlist, `cwd`, `--message-file` и изображения обязаны находиться внутри настроенных проектов, а окружение runtime очищается от чужих Codex/Claude session ID. Если sandbox запрещает named pipe, используется token-free файловая очередь в системном temp с теми же серверными проверками. `config.json` получает отдельный Windows ACL без доступа `CodexSandboxUsers`.

### Отправка сообщения из скрипта

Отдельный процесс может отправить владельцу сообщение через локальный IPC того же бота:

```powershell
node send-message.mjs "Обработка завершена"
```

То же через npm:

```powershell
npm run send -- "Обработка завершена"
```

Текст можно передать через stdin; для нескольких разрешённых чатов укажите `--chat-id <id>`. Параметр `--silent` отправляет уведомление без звука. Скрипт делит текст длиннее лимита Telegram на несколько сообщений и не выводит токен в командную строку или журнал.

Из Windows PowerShell 5.1, фонового watcher или `.ps1` с русским текстом безопаснее передавать сообщение через UTF-8-файл. Это не даёт PowerShell перекодировать кириллицу в аргументах запуска:

```powershell
Set-Content -LiteralPath notification.txt -Encoding UTF8 -Value "Обработка завершена"
node send-message.mjs --bind-current --category done --message-file notification.txt
```

`--message-file` взаимоисключаем с текстом в командной строке. Отправщик также отклоняет текст, похожий на повреждённый UTF-8 (`РўСЂ...`), вместо публикации битого уведомления.

Чтобы ответ на уведомление автоматически вернул бота к текущей задаче, отправьте его с привязкой:

```powershell
node send-message.mjs --bind-current --category action "Нужен ваш ответ"
```

`--bind-current` определяет вызывающую AI-сессию по точному идентификатору: `CODEX_THREAD_ID` для Codex или `CLAUDE_CODE_SESSION_ID` для Claude Code. Он не использует выбранную в боте задачу как неявный fallback: если идентификатора вызывающей сессии нет, отправка завершается ошибкой до обращения к Telegram. Это исключает привязку уведомления из VS Code/CLI к чужой задаче, оставшейся активной в `data/state.json`.

Финальный ответ отдельно регистрировать не нужно. Для Codex Agent Hub получает полный финальный ответ, запрос, статус и usage из rollout точного `turnId`; для Claude те же поля читаются из локального JSONL-транскрипта, а денежная оценка нового управляемого хода — из итогового результата Claude CLI. Для хода, запущенного самим Telegram-ботом, обычный полный финал доставляется в Telegram. Внешние ходы Codex и Claude записываются в журнал без отдельной Telegram-карточки. `send-message.mjs` предназначен только для явных промежуточных уведомлений; отдельного end-of-turn API больше нет.

Фоновый terminal-аудит хранит в `state.json` время последнего полностью завершённого обхода, байтовую позицию каждого append-only rollout и начавшиеся ходы без терминального события. После перезапуска он постранично читает все основные и дочерние треды, изменившиеся после сохранённой границы, и продолжает каждый файл с последней полной JSONL-строки. Если клиент остановил ход без записи `turn_aborted` или `task_complete`, аудит сверяет сохранённый точный `turnId` через `thread/read` и восстанавливает статус, usage и журнал. Статус `interrupted` отдельного App Server не считается завершением, пока lifecycle точного хода остаётся активным в rollout; это защищает длительные инструменты и автоматическое сжатие контекста от ложной остановки. Если ранее созданная предварительная terminal-запись противоречит возобновившейся активности того же `turnId`, аудит удаляет её из ledger и снимает отметку доставки до настоящего завершения. Расход субагента записывается по его точному `threadId + turnId`, по цепочке `parentThreadId` относится к корневой задаче и показывается отдельным ходом с префиксом `Субагент ·`; поэтому видимые ходы полностью объясняют итог задачи. Fork-rollout субагента содержит унаследованную историю родителя, но аудит отбрасывает ходы, чей UUIDv7 старше самого дочернего треда; ранее ошибочно записанная унаследованная история автоматически удаляется из ledger с сохранением в quarantine-файле. Фиксированного окна восстановления и лимита общего количества проверяемых тредов после первичной миграции нет; размер `thread/list` ограничивает только одну порцию. При обновлении со старой версии аудит один раз обнаруживает все обычные и дочерние rollout-файлы в активных `sessions` и `archived_sessions`, включая не возвращаемые App Server, и потоково дочитывает их порциями по 32 МБ. Очередь, точный байтовый офсет и незавершённые между порциями `turnId` сохраняются после каждого шага, поэтому миграция не блокирует HUB и продолжается после рестарта. Для архивной цепочки родителей используется файловый `session_meta`; брошенный незавершённый ход старше 30 минут восстанавливается как отменённый. Курсор продвигается только после успешной обработки всей порции; повтор после сбоя безопасен благодаря дедупликации по `threadId + turnId`.

Необязательная функция «очистка дубликатов изображений в rollout» не меняет
порог штатного Codex-сжатия. При явном `codexRolloutContext.enabled: true` она
до запуска своего App Server и затем с интервалом
`codexRolloutContext.scanIntervalSeconds` (по умолчанию 900 секунд, то есть
15 минут) очищает точные дубликаты старых `input_image` только из
`compacted.payload.replacement_history`: исходные сообщения rollout остаются
без изменений, а в каждом snapshot сохраняются последние четыре изображения.
Отсутствующее значение `enabled` трактуется как `false`. Перед анализом и перед
атомарной заменой файла проверяются завершённость хода и отсутствие процессов,
держащих rollout открытым. Поэтому активный в VS Code, Codex Desktop или другом
клиенте тред только откладывается до следующей автоматической попытки. Ручная диагностика:
`node codex-rollout-context.mjs inspect <rollout.jsonl>`; ручное применение:
`node codex-rollout-context.mjs sanitize <rollout.jsonl>`.

Все настроенные проекты записываются в общий личный ledger и проецируются в единственный `WORK_LOG.md` корневого проекта. Для интерфейсов Agent Hub строит встроенный SQLite read-store `data/journal.sqlite`: начальная страница, старые дни и отдельные ходы читаются из него без повторного разбора всего Markdown. `WORK_LOG.md` остаётся переносимым человекочитаемым экспортом и источником безопасной перестройки индекса; Redis, отдельный сервер БД и нативные npm-модули не требуются. Отдельные проектные журналы Agent Hub не обновляет.

Журнал полностью принадлежит Agent Hub Server. Агент не ищет строку, не создаёт UUID и не редактирует `WORK_LOG.md`: сервер находит или создаёт строку по `provider + threadId + локальная дата`, а ход — по точному `turnId`. В личном ledger сохраняются название задачи, начало и завершение, пользовательский запрос, полный финальный ответ, diff, доступные изменённые файлы, usage, модель и service tier. В компактный `WORK_LOG.md` и Mini App выводятся запрос, полный ответ и метрики; diff и список файлов остаются только в ledger, поэтому опубликованный журнал не разрастается ими. Заголовок хода получается детерминированно из финального ответа без дополнительного обращения к модели. Технические контейнеры IDE удаляются из отображаемого запроса; для `response-annotations` журнал показывает комментарии пользователя и отдельный текст `My request`, не служебную JSON/XML-обёртку. Ход фиксируется даже при временно недоступном usage; последующее событие дополняет ту же запись. Каждые пять минут сервер читает `account/rateLimits/read` для Codex и `/usage` для Claude, сохраняет оба снимка отдельными строками в `data/rate-limits-raw.jsonl` и добавляет нормализованные строки в `data/rate-limits.csv`. Текущие остатки Codex, Spark и Claude показываются одной горизонтальной строкой сверху в настройках и статистике; компактная шапка интерфейса остаётся без лимитов. Каждый завершённый `imagegen`, для которого rollout не содержит отдельного image-usage, добавляет к обычному расходу Codex фиксированную оценку `90 cr`. Таблица дня состоит из колонок `Задача | Ходы`; задачи отсортированы по убыванию времени последнего хода, сами ходы — также по убыванию времени. Субагенты представлены отдельными ходами с префиксом `Субагент ·`, а их расход входит в итог задачи. Кредиты масштабируются по SI (`cr`, `kcr`, `Mcr`, `Gcr`) и показываются с одним знаком после запятой после перехода к следующему порядку.

Для Claude стабильным `turnId` журнала служит UUID пользовательского сообщения из транскрипта, поэтому повторное чтение и исторический backfill не создают дубли.

Историю лимитов, предшествующую запуску пятиминутного опроса, можно восстановить из обычных и архивных rollout без обращения к модели: `npm run rate-limits:backfill` показывает план, а `npm run rate-limits:backfill -- --apply` дописывает отсутствующие пятиминутные интервалы в оба локальных файла истории. Повторный запуск безопасен: уже существующие интервалы для того же лимита пропускаются.

Для одноразовой полной реконструкции старого журнала используйте `npm run work-log:backfill -- --through YYYY-MM-DD` сначала без `--apply`. Команда потоково читает и активные `%USERPROFILE%\.codex\sessions`, и архивные `%USERPROFILE%\.codex\archived_sessions`, объединяет дочерние ходы с корневой задачей и отбрасывает унаследованные дубли fork-rollout. Применение через `--apply` сохраняет неизменёнными все не-Codex записи и более новые Codex-записи, заменяет историю Codex до указанной локальной даты, строит `WORK_LOG.md` с чистого шаблона и предварительно копирует исходные ledger и журнал в `data/migrations/<timestamp>`. На время применения Agent Hub Server должен быть остановлен, чтобы параллельная проекция не перезаписала миграцию.

После реконструкции команда `npm run work-log:title-backfill -- --through YYYY-MM-DD` пакетно заменяет только шаблонные заголовки `Ход завершён` и `Ход отменён` содержательными названиями по сохранённым запросам и ответам. По умолчанию используется `gpt-5.6-terra` с низким reasoning; модель, effort и размер пакета задаются параметрами `--model`, `--effort` и `--batch-size`. Результат каждого пакета атомарно сохраняется в `data/migrations/work-log-generated-titles.json`, поэтому прерванную генерацию можно продолжить той же командой. Сначала проверьте кэш без записи; `--apply` требует полный набор заголовков, создаёт отдельную резервную копию ledger и `WORK_LOG.md`, затем перестраивает журнал. Пустые или чисто служебные ходы честно сохраняют статусный заголовок.

Все завершённые ходы каждого изменившегося transcript Claude автоматически и одной пакетной операцией добавляются в ledger при обновлении каталога задач; повторный аудит безопасен благодаря ключу `provider + sessionId + UUID пользовательского сообщения`. Для ручной проверки и восстановления остаётся команда `npm run work-log:claude-backfill`: без `--apply` она только показывает план, с `--apply` аддитивно переносит завершённые ходы из `%USERPROFILE%\.claude\projects`, дополняет ранее импортированные записи расчётными кредитами, использованными навыками и завершёнными MCP-вызовами и сначала сохраняет ledger, incremental delta и `WORK_LOG.md` в `data/migrations/claude-<timestamp>`. Когда в транскрипте нет итогового `total_cost_usd`, Agent Hub рассчитывает API-эквивалент по модели и сохранённым категориям токенов: обычному входу, cache write 5m/1h, cache read и выходу. Для управляемых ходов точная CLI-оценка по-прежнему имеет приоритет.

### Mini App и VS Code

Agent Hub поднимает общий адаптивный интерфейс на loopback-адресе `127.0.0.1:8787`: слева находятся задачи с активностью, временем и готовностью ответа, справа — история и живой чат, а журнал открывается отдельной вкладкой. Интерфейс не доступен по Wi‑Fi/LAN. Открывайте его командой `npm run open:web`: она один раз передаёт браузеру защищённый локальный ключ, обменивает его на HttpOnly/SameSite-сессию и сразу удаляет ключ из адресной строки. Прямое открытие URL без такой сессии не даёт читать задачи или выполнять команды. Композер поддерживает изображения, Ctrl+V, аннотации и меню `/`; ответы и reasoning безопасно отображаются как Markdown. Полнотекстовый поиск находит задачи, запросы, ответы, файлы и даты и открывает точный ход. Лента хода показывает команды, изменения файлов, инструменты, поиск, субагентов, подтверждения и свёртку контекста.

Во время хода переключатель `В очередь` / `Изменить ход` либо сохраняет следующий ввод до завершения, либо вызывает Codex `turn/steer` с точным `expectedTurnId`. Для каждого исходящего сообщения UI показывает состояние `Подготовка` / `Отправляется` / `Принято` / `В очереди` / `Не подтверждено`. Пользовательские сообщения объединяются по официальному `clientUserMessageId → UserMessageThreadItem.clientId`, ответы — по точным `threadId + turnId + itemId`; текст идентификатором не считается. Подтверждённые сообщения удаляются из optimistic-слоя, а сохраняемые квитанции обеспечивают безопасный повтор того же UUID после потери ответа транспорта. Время сообщения берётся из истории хода или квитанции приёма, а не вычисляется заново при каждом открытии чата. Загруженные изображения являются постоянной частью сообщения: их миниатюры видны как у уже отправленного, так и у отложенного ввода, переживают перезапуск Agent Hub и открываются нажатием в локальном веб-интерфейсе и расширении VS Code. Индикатор контекста использует данные App Server и запускает `thread/compact/start`. Ручная и автоматическая свёртка отслеживаются по современным событиям `contextCompaction`: во время операции индикатор вращается, начало и завершение автосвёртки показываются уведомлениями, а после завершения выводится фактический новый процент из свежего `thread/tokenUsage/updated`. HUB не подставляет искусственные `0%`; пока App Server ещё не прислал новый объём, индикатор показывает `…`. Расширение VS Code показывает ту же оболочку и вызывает backend через аутентифицированный named pipe, не передавая секрет в webview.

На третьей странице `Статистика` верхний график показывает локальный расход завершённых ходов по ledger, а нижний — историю лимитов API. Оба поддерживают диапазоны от 6 часов до всего доступного периода. Нажатие на элемент легенды графика лимитов скрывает или возвращает соответствующую серию. Выбор сохраняется локально для текущего интерфейса и восстанавливается после перезапуска; новые серии по умолчанию остаются видимыми. Линии сохраняют все пятиминутные замеры, а видимые точки автоматически разрежаются по экранному расстоянию, поэтому длинные диапазоны не превращаются в сплошную полосу маркеров. Серии Claude показывают отдельные показатели session, week и доступные модельные лимиты.

Журнал отслеживает тот же `WORK_LOG.md`, атомарно обновляет SQLite read-store, сохраняет раскрытые секции и получает изменения без ручной перезагрузки. Холодная перестройка выполняет линейную сборку фрагментов вместо многократного копирования всего дня. Начальный ответ содержит пять последних дней целиком и только шапки более старых дней. При раскрытии старого дня отдельный SQL-запрос загружает задачи и шапки ходов, а запрос и полный ответ старого хода читаются только при раскрытии самого хода. Нажатие на название задачи открывает её чат; кнопка `↗` в шапке хода открывает точный ход, включая ход субагента. В группировке по задачам раскрытая карточка показывает радарный профиль масштаба задачи по ходам, кредитам, времени, касаниям файлов, строкам diff, доле ходов субагентов, уникальным использованным навыкам и завершённым MCP-вызовам относительно медианы видимых задач. Для MCP ledger сохраняет только сервер, инструмент и статус без аргументов и результатов; навыки учитываются по явным маркерам `$skill-name` в запросе и по фактическому чтению соответствующего `SKILL.md`. Старые ходы без этих данных показывают `нет данных`, а rollout-backfill заполняет метрики там, где они присутствуют в истории Codex.

Опубликованная Telegram Mini App передаёт команды через Cloudflare Worker: Telegram `initData` и allowlist защищают пользовательскую сторону, локальный Hub забирает команды исходящим HMAC-подписанным polling, а UUID обеспечивает идемпотентность. Worker не получает локальные пути и не может произвольно выбирать проект. Изображения передаются как привязанные к пользователю opaque-ссылки с проверкой MIME, хеша и размера, квотами и TTL; локальный Hub повторно проверяет файл и только затем сохраняет его в разрешённый runtime-каталог.

Тот же Worker обслуживает Android-клиент. Новый телефон добавляется только одноразовым 20-символьным кодом из настроек HUB. Приложение создаёт неэкспортируемый P-256 ключ в Android Keystore, подписывает короткий challenge и получает ограниченную 12-часовую сессию. В настройках показываются доверенные устройства и последний доступ; отзыв удаляет все активные сессии телефона. Telegram-токен и Worker sync secret на устройство не передаются.

Интерфейс имеет два профиля отображения при общей разметке и данных: Telegram на Android/iOS получает мобильную компоновку, а локальный браузер и VS Code — десктопную. Telegram Desktop и Telegram Web открываются в обычном максимально развёрнутом WebView без запроса fullscreen; точный размер окна выбирает клиент Telegram. При ширине WebView меньше `860px` используется мобильная компоновка без горизонтальной прокрутки. У выполняемых задач список показывает живую длительность от фактического начала хода; метки агента и runtime остаются контрастными и не сжимаются на узкой панели. Темы `Орбита`, `Туманность`, `Пульсар`, `Gothic`, `Чёрная дыра`, `Rain`, `Мегаполис`, `Storm`, `Магма`, `Гроза`, `Луг` и `Графит` переключаются в единой панели `Настройки`; эта же панель содержит параметры журнала и выбранной задачи, а кнопка в чате остаётся вторым входом в неё. Выбор сохраняется локально для браузера или Telegram WebView. `Мегаполис` показывает ночной городской фон через WebGL-слой запотевшего стекла: конденсат размывает изображение, движущиеся капли преломляют свет и оставляют за собой прозрачные дорожки. При недоступном WebGL используется облегчённый CSS-вариант. `Storm` показывает живой ночной шторм: шейдер поднимает и опускает воду по маске горизонта, медленно ведёт облака и подсвечивает гребни, а в момент разряда кадр сменяется вторым снимком той же сцены, снятым при вспышке. Канал молнии ветвится и гаснет книзу.

Переключатель `Группировка` поддерживает дни, рабочие недели с понедельника по воскресенье, календарные месяцы и задачи. В режиме по дням после даты показывается двухбуквенный день недели. В режиме задач каждая карточка объединяет ходы одного `provider + threadId`, показывает их количество, суммарный расход и длительность; ходы без данных о стоимости или времени отмечаются отдельно. Опция `Группировать задачи Claude в Work` объединяет Claude-ходы в одну задачу `Work` внутри выбранного периода, а в режиме по задачам — во всём журнале. Глобальная настройка `Учитывать расход Claude` сохраняется в runtime Agent Hub и одинакова для Mini App, панели VS Code и Desktop: при отключении Claude-ходы остаются видны, но их API-эквивалент исключается из итогов журнала и графика расхода. Выбранный режим группировки сохраняется отдельно в браузере или Telegram WebView.

График локального расхода сохраняет выбранный период отдельно для каждого браузера или WebView. Диапазоны `7 дней` и `30 дней` агрегируются по тем же локальным календарным дням, что и дневная группировка журнала; пропущенные дни показываются с нулевым расходом, а дата подписывается под каждым днём. На узком экране длинная дневная ось прокручивается горизонтально без прореживания дат.

Параметры `miniApp.enabled`, `miniApp.host` и `miniApp.port` задаются в `config.json`. Для локального сервера разрешены только loopback-адреса `127.0.0.1`, `localhost` и `::1`.

При белом домашнем IP Agent Hub может публиковать тот же loopback-сервер напрямую через Caddy, не пропуская трафик приложения через Cloudflare. Установщик скачивает закреплённый официальный Caddy `2.11.3`, проверяет SHA-256 архива и создаёт внешний `gateway.json` в runtime-каталоге:

```powershell
npm run gateway:install -- --url https://hub.example.com
```

После перезапуска Hub сам запускает Caddy, получает и обновляет TLS-сертификат и направляет HTTPS на `127.0.0.1:8787`. В роутере должны быть проброшены TCP 80 и 443 на компьютер, а DNS-запись hostname — указывать прямо на белый IP без HTTP-прокси. API по-прежнему требует Telegram `initData` либо сессию доверенного телефона; наружу не публикуется незащищённый LAN-listener. Android-устройство после перехода нужно один раз сопрячь заново, потому что ключи Worker намеренно не экспортируются.

Параметр `miniApp.quickTunnel.enabled` запускает HTTPS-туннель и обновляет через `setChatMenuButton` общую кнопку меню бота и явную кнопку каждого чата из `allowedUserIds`. В режиме `mode: "quick"` поддержаны временные адреса Pinggy через системный OpenSSH на порту 443 и Cloudflare Quick Tunnel через внешний `cloudflared`. Бесплатные адреса меняются после перезапуска; Hub автоматически записывает новый адрес в кнопку при каждом успешном запуске.

Для постоянного Cloudflare Named Tunnel укажите `provider: "cloudflare"`, `mode: "named"`, стабильный `publicUrl` и путь `tokenFile`, относительный к внешнему `config.json`. Файл должен содержать только tunnel token и не должен попадать в Git:

```json
{
  "miniApp": {
    "enabled": true,
    "host": "127.0.0.1",
    "port": 8787,
    "quickTunnel": {
      "enabled": true,
      "provider": "cloudflare",
      "mode": "named",
      "executable": "cloudflared",
      "publicUrl": "https://hub.example.com",
      "tokenFile": "cloudflare-tunnel.token",
      "edgeBindAddress": "192.0.2.10",
      "menuText": "Журнал",
      "publicPort": 8788,
      "controlPort": 4300
    }
  }
}
```

Маршрут опубликованного hostname в Cloudflare должен вести на `http://127.0.0.1:<publicPort>`. Необязательный `edgeBindAddress` закрепляет исходящее соединение `cloudflared` за конкретным локальным IP; это полезно, когда системный VPN перехватывает порт Cloudflare Tunnel `7844`. В named-режиме Hub публикует стабильную Telegram-кнопку после фактической регистрации соединения с Cloudflare и не ждёт распространения публичного DNS. Туннель в обоих режимах направляется на отдельный локальный listener, который требует корректную подпись Telegram Mini App и пользователя из `allowedUserIds`; обычный локальный просмотр на основном порту остаётся доступным без Telegram. Внутри Telegram журнал обновляется опросом раз в пять секунд.

Предпочтительный постоянный режим — Cloudflare Worker из `cloudflare-worker`. В нём статика и защищённое Telegram API работают на Cloudflare, а локальный Hub отправляет актуальный снимок журнала исходящим HTTPS-запросом. Входящий порт и постоянно работающий `cloudflared` не нужны. Снимок хранится в SQLite-backed Durable Object со строгой согласованностью; публикация подписывается отдельным HMAC-секретом, а чтение требует корректный Telegram `initData` и пользователя из `allowedUserIds`.

Сборка и развёртывание:

```powershell
npm run worker:build
npx wrangler login
npx wrangler secret put TELEGRAM_BOT_TOKEN --config cloudflare-worker/wrangler.jsonc
npx wrangler secret put SYNC_SECRET --config cloudflare-worker/wrangler.jsonc
npx wrangler secret put ALLOWED_USER_IDS --config cloudflare-worker/wrangler.jsonc
npm run worker:deploy
```

В `cloudflare-worker/wrangler.jsonc` задаётся публичный маршрут Worker. Значения `TELEGRAM_BOT_TOKEN`, `SYNC_SECRET` и `ALLOWED_USER_IDS` хранятся как Cloudflare secrets и не попадают в Git. Локальная копия `SYNC_SECRET` хранится рядом с внешним `config.json`; Worker включается так:

```json
{
  "miniApp": {
    "worker": {
      "enabled": true,
      "publicUrl": "https://hub.example.com",
      "syncSecretFile": "cloudflare-worker-sync.secret",
      "menuText": "Журнал",
      "retrySeconds": 15,
      "refreshSeconds": 60
    }
  }
}
```

Publisher сжимает снимок `WORK_LOG.md` через gzip, подписывает и отправляет его порциями при изменении файла, повторяет неудачные запросы и периодически сверяет состояние. Worker атомарно переключает опубликованный журнал только после получения всех порций, поэтому рост истории не обрывает обновление и незавершённая публикация не заменяет рабочий снимок. Telegram-кнопка переключается на Worker только после первой успешной публикации.

Если требуется осознанно привязать сообщение именно к задаче, выбранной сейчас в Telegram-боте, используйте отдельный параметр:

```powershell
node send-message.mjs --bind-active --category info "Сообщение для активной задачи бота"
```

Привязанное уведомление отправляется как тонкая медиа-карточка фиксированного размера: PNG-баннер показывает категорию, а подпись — жирное название текущей задачи с одним `🧵` слева и текст. Кнопка `👀 Показать сообщение` прикреплена к этой же карточке: она выбирает привязанный thread и показывает текущий ход либо последний полный ответ. Исходники и воспроизводимый генератор баннеров находятся в `assets/notification-cards`. Поддерживаются категории:

- `action` — `ТРЕБУЕТСЯ ДЕЙСТВИЕ`;
- `done` — `ЗАДАЧА ВЫПОЛНЕНА`;
- `intermediate` — `ПРОМЕЖУТОЧНЫЙ РЕЗУЛЬТАТ`;
- `progress` — `ЗАДАЧА ВЫПОЛНЯЕТСЯ`;
- `warning` — `ВНИМАНИЕ`;
- `info` — `ИНФОРМАЦИЯ` (по умолчанию).

Если Telegram временно не принимает PNG, `send-message.mjs` автоматически отправляет прежнее текстовое оформление, поэтому важное уведомление не теряется.

`done` используется только после полного завершения всей задачи, когда больше не осталось работы и агент заканчивает ход. `action` означает, что дальнейшая безопасная работа действительно невозможна без ответа или действия пользователя. Для существенного готового этапа, после которого работа продолжается, используется `intermediate`; для обычного текущего состояния — `progress`; для риска или отклонения, ещё не требующего вмешательства, — `warning`. Нейтральные сообщения, не подходящие ни под одну специальную категорию, отправляются как `info`.

Например, отдельный промежуточный результат отправляется командой `node send-message.mjs --bind-current --category intermediate "Проверка завершена"`. Обычный финал отдельно не отправляется: Agent Hub читает его из rollout. Переключение выполняется при Telegram-действии «Ответить» или по кнопке показа. Простое новое сообщение и ответ на уведомление, отправленное без `--bind-current` или `--bind-active`, текущую задачу не меняют. Если другая задача выполняется, бот не прерывает её автоматически. При фактической смене бот присылает заголовок `Текущая задача изменена`. Если `showProjectButton` включён, ниже выводятся жирное имя проекта и курсивное название задачи; если выключен — только жирное название задачи. Служебное сообщение прогресса и итоговый ответ, отправленные самим ботом, тоже получают привязку к породившей их задаче.

### Скриншоты кода

Для переписки с телефона фрагмент исходника можно отрендерить в читаемые PNG. Длинный диапазон автоматически разбивается на несколько изображений:

```powershell
python render-code-images.py `
  "C:\Projects\App\Module.bsl" `
  "C:\Projects\App\WIP\code-images" `
  --start 190 --end 260 `
  --title "Копирование коллекций"
```

Готовые PNG отправляются одним изображением или Telegram-альбомом. Привязка работает так же, как у `send-message.mjs`, поэтому ответ на картинку возвращается в правильную задачу:

```powershell
node send-images.mjs --bind-current --caption "Код после правки" `
  "C:\Projects\App\WIP\code-images\Module-190-234.png" `
  "C:\Projects\App\WIP\code-images\Module-235-260.png"
```

Поддерживается до десяти PNG в одном альбоме. `--bind-active` намеренно привязывает изображения к выбранной в боте задаче, `--silent` отключает уведомление. Для рендеринга используется Pillow из `requirements.txt`.

Кнопка `Показать сообщение` не создаёт новый ход. Она перерисовывает компактное представление выбранной задачи: удаляет доступные боту сообщения этой задачи из Telegram, сверху создаёт навигацию истории, затем показывает последнюю пару `👤 Вы` → `🤖 агент` и создаёт новую живую progress-карточку последней в чате. Старый ID progress-сообщения одновременно отсоединяется от run, поэтому обновления не продолжают уходить в карточку выше истории. Для запущенной ботом задачи используется тот же run. Для внешнего Codex бот читает текущий turn через App Server, а для внешнего Claude — локальный transcript соответствующего `session_id`; сообщение продолжает обновляться до завершения. Выбранная задача дополнительно проверяется автоматически: если ход запущен из VSCode/CLI, бот молча подключает observer, обновляет локальный статус и блокирует параллельный turn, но не отправляет progress-карточку или полный финальный ответ без запроса. Живое представление и последующая доставка полного финала появляются только после `Показать сообщение`; отдельного автоматического end-of-turn-уведомления нет. Если активного хода нет, кнопка показывает полный последний ответ. Если ни хода, ни ответа найти нельзя, бот сообщает об этом и не подставляет данные другой задачи.

Кнопка `👀 Показать ещё` расположена в первом сообщении компактного представления, то есть визуально выше показанной переписки. Каждое нажатие добавляет ровно одну пару: `1 → 2 → 3 → 4…`. Telegram не позволяет вставлять новые сообщения задним числом, поэтому при догрузке бот удаляет текущее представление и строит его заново с большим числом пар в хронологическом порядке. Источником истории остаются локальные треды Codex и transcript Claude; удаление Telegram-сообщений историю агента не затрагивает.

В личном чате бот может удалять как исходящие, так и входящие пользовательские сообщения моложе 48 часов. Новые входящие тексты, изображения и голосовые сообщения привязываются к задаче, чтобы при следующем открытии убрать оригинал и показать его как `👤 Вы`. Сообщения старше ограничения Telegram и старые пользовательские сообщения, ID которых бот ещё не сохранял, автоматически удалить нельзя. Незакрытые запросы разрешения с кнопками сохраняются.

## Что изменено в текущей версии

### Потоковый ход выполнения

- Codex обрабатывает `agentMessage`, доступное резюме анализа, план, команды, изменения файлов и вызовы MCP по мере поступления событий App Server.
- Claude Code запускается с `stream-json --verbose --include-partial-messages`; текст, инструменты, повторные API-запросы и `session_id` доступны до завершения процесса.
- Для задачи дольше трёх секунд бот создаёт одно служебное сообщение и редактирует его не чаще одного раза в 1,5 секунды. В первой строке компактного заголовка указаны агент, модель и reasoning; проект добавляется только при включённой кнопке проекта. Во второй строке указано название задачи, отдельной строкой — владелец выполнения: `VSCode App Server`, `Agent Hub Server`, `Codex Desktop App`, `Codex CLI` или безопасный `External Codex`, если текущий внешний клиент определить нельзя. В коротких кнопках списка используются соответственно `VSC`, `HUB`, `APP`, `CLI` и `EXT`. Короткие ответы приходят сразу одним итоговым сообщением без лишнего «Задача принята».
- Heartbeat различает доступность потока и реальную работу: зелёный статус показывается только при свежих событиях, а после двух минут без новых событий появляется оранжевое предупреждение с длительностью простоя. Успешный `thread/read` сам по себе больше не изображает продвижение задачи.
- После завершения служебное сообщение сворачивается до краткого статуса, а полный ответ отправляется отдельно. Бот берёт именно `final_answer` завершённого Codex-turn, а если итог ещё не появился в снимке — повторно перечитывает turn перед доставкой; промежуточные commentary не подменяют итоговый ответ.

### Несколько задач одновременно

- Выбранная задача — только адрес для следующего обычного сообщения. Она не является глобальной блокировкой бота.
- Пока одна задача выполняется локально, через `/tasks`, `/projects`, `/agent` или ответ на привязанное сообщение можно выбрать другую и запустить её. Работа первой продолжится в фоне.
- Реестр запуска хранит отдельно для каждого `проект + агент + thread/session`: процесс или turn, прогресс, ответ, временные файлы и последний diff.
- Перед запуском управляемого хода бот определяет фактический корень Git-репозитория и сохраняет синтетическое дерево текущих файлов, не меняя рабочий index. Поэтому кнопка `Изменения` под каждым итоговым ответом показывает diff именно этой задачи, даже если сейчас выбрана другая; команда `/diff` остаётся способом открыть изменения выбранной задачи. Учитываются staged- и новые untracked-файлы, но исключается уже существовавшая грязь. Большой diff ограничивается 64 КиБ и дополняется перечнем затронутых файлов; последние сто результатов хранятся отдельно от часто перезаписываемого state и переживают рестарт бота. Для внешнего хода, обнаруженного после старта, снимок охватывает изменения с момента подключения.
- Исполнитель у каждого хода только один. Если turn уже выполняется через `VSCode App Server`, Telegram подключает наблюдение и сохраняет новое сообщение для выбора действия или очереди, но не запускает параллельный turn. Ход, начатый Telegram, помечается `Agent Hub Server`. Штатная панель VSCode не читает lock бота, поэтому жёсткая блокировка гарантируется со стороны Telegram; обнаруженный встречный VSCode-ход всё равно сразу попадает в локальный реестр и становится наблюдаемым.
- `/tasks` строится заново из локального каталога Codex и файлов сессий Claude, поэтому показывает задачи обоих агентов во всех разрешённых папках, а не только уже открывавшиеся через бота. Индекс названий Codex читается один раз на обновление каталога, увеличившиеся rollout-файлы разбираются только с последней сохранённой позиции, а transcript Claude перечитывается только после изменения его `mtime` или размера. Список разбит на страницы; выполняющиеся через Agent Hub Server задачи отмечены `⚡`, остальные выполняющиеся — `⏳`, Claude-задачи с неопределённой живостью — `❔`. Команда `/rename <название>` переименовывает и закрепляет текущую задачу по её `provider + threadId`; последующие автоматически сгенерированные заголовки Codex не меняют это имя в боте.
- `/status` отправляется как прямоугольная карточка 3:1 с логотипом выбранного агента. Для каждого показа случайно выбирается одна из семи синих шапок Codex или семи терракотовых шапок Claude; если одновременно активны задачи обоих агентов, используется одна из трёх совместных шапок. Первая строка показывает агента, модель и reasoning, вторая — режим и состояние. Каталог выводится только при включённой кнопке проекта. Число выполняющихся задач находится в заголовке `🧵НЕДАВНИЕ ЗАДАЧИ (N)🧵`; отдельная строка счётчика не выводится. Под заголовком находятся четыре кнопки: сначала выполняющиеся задачи, затем свободные места занимают последние по активности завершённые задачи. Ходы Agent Hub отмечены `⚡`, остальные активные — `🧵`, недавние — `🕘`, Claude-задачи с неопределённой живостью — `❔`, выбранная — `✅ ТЕКУЩАЯ`; у выбранной активной HUB-задачи `⚡` остаётся рядом с меткой `HUB`. Нажатие сразу выбирает агент, проект и thread/session. Запуски самого сервера определяются точно; для внешнего Codex сервер сопоставляет lifecycle-события свежего rollout (`task_started`/`task_complete`/`turn_aborted`) по `turn_id`, а VSC сначала определяет по `client_id` пользовательского сообщения именно этого turn. Если per-turn метки недостаточно, Windows Restart Manager показывает процессы, которые сейчас держат rollout: процесс Agent Hub исключается, а оставшийся клиент определяется по живому дереву процессов как `VSC`, `APP` или `CLI`. Несколько разных внешних клиентов либо неизвестное дерево дают безопасный `EXT`. Исторические `originator` и `source` сессии при выборе владельца не используются. Для внешнего Claude незакрытый transcript считается выполняющимся, пока обновлялся в последние 30 минут. После более долгой тишины состояние становится `активность неизвестна`: наблюдение снимается без ложного финала, а новый ход в той же сессии требует явного подтверждения. Для Claude, запущенного самим сервером, используется PID и такого таймаута нет. После подтверждённой отмены управляемого Claude-процесса сервер запоминает снимок его transcript и не воскрешает незавершённый хвост как внешний ход; новая реальная активность или следующий запуск в этой сессии снимают отметку.
- `/cancel` останавливает только выбранную задачу. Для подключённого внешнего хода бот отключает observer и запоминает это состояние, поэтому наблюдение не подключается повторно само. Пока внешний ход действительно выполняется, новый запрос в тот же thread/session всё равно не запускается; повторное подключение доступно через `Показать сообщение`. Другие запуски продолжаются.
- Разные задачи могут одновременно работать внутри одного workspace и одного Git-репозитория: это штатный режим для `VSC_Tyrael`, и бот не показывает предупреждение о пересечении репозиториев. Перед обычным сообщением бот по-прежнему повторно проверяет выбранный thread/session и не запускает в нём второй параллельный ход.
- Если выбранная задача уже выполняется, новый текст, голосовая расшифровка или изображение не теряются и не подменяются текущим прогрессом. Бот сохраняет вход и предлагает отправить его в новую задачу, поставить в очередь исходной, показать текущий ход или отменить. Предупреждающая кнопка явного запуска остаётся только для неопределённой живости внешнего Claude-процесса. Очередь запускается автоматически после освобождения своей задачи; сохранённые и поставленные в очередь входы переживают перезапуск бота. Старые сохранённые сообщения, остановленные прежней проверкой Git-корня, при обновлении автоматически переводятся в очередь.
- Все привязанные уведомления и сообщения о смене задачи используют единый контракт кнопки `👀 Показать сообщение`: она выбирает именно привязанный `проект + агент + thread/session`, подключает его текущий живой ход и показывает актуальный прогресс. Новые кнопки просмотра и догрузки истории несут `provider + threadId` непосредственно в callback, поэтому продолжают работать после компактации или удаления ограниченного хранилища привязок; проект и название восстанавливаются из каталога задач. Если ход уже завершён, показывается его последний полный ответ. Старые callbacks `show-message`, `show-last-message` и `history-more` поддерживаются для ранее отправленных Telegram-сообщений и при утраченном контексте возвращают явный безопасный отказ. Переключение представления не останавливает фоновые задачи и не запускает дополнительный ход. Если переключение выполнено самой кнопкой показа, новое уведомление о переключении отправляется без кнопки, чтобы не создавать рекурсивную цепочку.

### Сохранение и восстановление задач

- Активный запуск сохраняется в `data/state.json`: агент, проект, `threadId`/`session_id`, `turnId`, время запуска, ID служебного Telegram-сообщения и уже полученная часть ответа.
- Общий локальный индекс `data/task-sync.json` синхронизирует между независимыми интерфейсами каталог, историю, фактический статус, `turnId`, владельца App Server, последний этап и текст выбранной задачи. Для Codex источником истины остаются локальные thread/rollout-файлы, для Claude — transcript. Пока внешний VSC-ход выполняется, его текущий пользовательский запрос и последующие уточнения берутся из append-only rollout по точному `client_id` и сразу добавляются в чат; после обновления официальной истории они сливаются по тому же идентификатору без дублей. Индекс является безопасным кэшем: если отдельный App Server временно недоступен, кнопка просмотра берёт историю только соответствующего `provider + threadId`; статус `running` из кэша автоматически устаревает через десять минут и не создаёт вечную фантомную задачу. Кэш ограничен тысячей задач; при переполнении удаляются самые старые завершённые записи, активные не вытесняются.
- Неизменившийся снимок задачи не перезаписывает `task-sync.json`. События собственного `Agent Hub Server` остаются основным мгновенным каналом обновления, а `thread/read` используется раз в пять секунд только как страховка от потерянного события. Внешний `VSCode App Server` проверяется чаще, чтобы новый ход быстро появлялся в статусе. Одновременные чтения одного треда и повторные открытия `/tasks` в коротком интервале объединяются; индекс названий Codex перечитывается только после изменения файла.
- При разрыве Codex App Server бот автоматически запускает его снова, возобновляет поток и читает сохранённую задачу через `thread/read`. Для продолжающегося хода восстанавливается наблюдение; для завершённого — найденный ответ доставляется в Telegram.
- Если `thread/resume` временно ошибается при запуске бота, но для этого же треда сохранён активный run, бот не создаёт новый выбранный тред. Он сохраняет прежнюю привязку и передаёт ход процедуре восстановления, исключая две параллельные задачи из одного пользовательского продолжения.
- Если управляемый Telegram-ход после переподключения остался в `waitingOnApproval`, но сам JSON-RPC-запрос погиб вместе со старым App Server, в режиме автоподтверждения бот откатывает только незавершённый turn и продолжает задачу новым turn с требованием проверить уже сделанные файлы и не повторять завершённые действия.
- Запросы дополнительных разрешений App Server (`item/permissions/requestApproval`) показываются в Telegram так же, как подтверждения команд и файлов. Запросы MCP (`mcpServer/elicitation/request`) обрабатываются отдельно: безопасная форма-разрешение с булевыми полями, утвердительными вариантами или готовыми значениями принимается в режиме автоподтверждения; форма, для которой пришлось бы выдумывать текст, пароль или неоднозначный выбор, всегда показывается пользователю. Неизвестный MCP-запрос больше не остаётся без JSON-RPC-ответа и не зависает скрыто. Техническое сообщение `Бот запущен` при фоновом рестарте не отправляется.
- Ошибка доставки финального ответа в Telegram не оставляет завершённый ход в реестре активных задач. Ответ сначала сохраняется локально для последующего просмотра кнопкой с глазами, а запуск освобождается независимо от состояния сети; состояние `finishing` после аварийного рестарта также перечитывается и завершается.
- Observer запоминает текст ответа на момент подключения, но при фактическом завершении наблюдаемого хода всегда доставляет его итог отдельно. Это закрывает гонку, когда внешний ход успел завершиться между обнаружением и первым опросом: старый ответ не подменяет текущий, а уже готовый текущий финал не теряется.
- Claude сообщает `session_id` первым событием и бот сохраняет его сразу, а не только после успешного завершения.
- Запущенный ботом ход Claude переживает перезапуск бота. CLI стартует отдельным процессом, а его `stream-json` пишется в файл хода `data/claude-runs/<turnId>.jsonl`, который бот читает хвостом с потоковым UTF-8-декодером. Русский текст и эмодзи сохраняются, даже если опрос пришёлся на середину многобайтного символа. После перезапуска ход подключается заново по сохранённому PID и файлу вывода: живой процесс продолжает вести ту же progress-карточку, а завершившийся отдаёт финальный ответ из файла. Прерванным ход помечается, только если процесса уже нет и результата в файле тоже. По той же причине `/restart` не ждёт завершения ходов Claude, а `/cancel` останавливает ход и после перезапуска — по сохранённому PID.
- При запуске удаляются файлы `data/claude-runs`, которые не принадлежат ни одному восстановленному активному ходу. `/cancel` в Windows останавливает всё дерево Claude через `taskkill /T /F` с резервной остановкой корневого процесса; в Unix сигнал получает detached-группа процессов.
- Записи состояния сериализуются через очередь и атомарно заменяют `state.json`, поэтому параллельные события и авария во время записи не оставляют обрезанный JSON. В том же состоянии сохраняются граница terminal-аудита Codex и байтовые позиции rollout, поэтому длительность простоя Agent Hub не ограничивает последующее восстановление завершившихся ходов. Не реже одного раза в 30 секунд сохраняется `state.json.bak`; при повреждении основного файла бот восстанавливается из резервной копии и не удаляет output потенциально живых detached-процессов. Хранилище текстов озвучки использует тот же атомарный механизм.

### Надёжность процесса

- Эксклюзивность процесса обеспечивается локальным системным каналом, уникальным для `dataDir`, поэтому две копии не могут одновременно читать `getUpdates` и дублировать ответы даже при гонке за устаревший файл. `data/bot.lock` хранит PID, случайный token, время запуска, имя канала и признак `ready`; PID, переиспользованный Windows после аварии, не создаёт вечную блокировку. Штатный `/restart` не обрывает управляемые Agent Hub ходы и не бросает уже принятую фоновую загрузку, распознавание или озвучивание: при необходимости перезапуск откладывается до безопасной передачи работы ходу Codex, чей App Server перезапускается вместе с Agent Hub. Старая копия сначала прекращает polling и фоновые таймеры, завершает всё дерево Codex App Server/MCP и локальный TTS-worker, освобождает системный lock, затем запускает замену. Новая копия выставляет `ready` только после инициализации provider, восстановления запусков/очередей и регистрации команд; живого PID без `ready` недостаточно. Если WMI-launch не дал готового процесса, запуск повторяется и используется прямой скрытый `wscript` fallback; если все попытки неуспешны, прежняя копия повторно захватывает lock и восстанавливает свои сервисы. Соседний Telegram update из уже полученного пакета остаётся для новой копии и обрабатывается ровно один раз. Ходы Claude перезапуск не задерживают, потому что подключаются заново. Внешние наблюдаемые задачи после запуска подключаются снова по сохранённому thread/session и заново определяют владельца текущего turn (`VSC`, `APP`, `CLI` либо безопасный `EXT`), не наследуя среду создания треда. Сообщение `Перезапускаю Agent Hub…` редактируется в итоговую карточку `AGENT HUB ПЕРЕЗАПУЩЕН`; технический статус `interrupted` при таком восстановлении пользователю не отправляется.
- Фоновое наблюдение повторно сверяет выбранные `provider + project + threadId` после каждого асинхронного чтения snapshot и ещё раз проверяет реестр запусков. Переключение задачи или старт Telegram-хода во время чтения не могут подключить observer к старой задаче либо создать второй запуск поверх нового.
- Codex App Server автоматически переподключается с повторными попытками, а пользователь видит состояние соединения в служебном сообщении.
- Каждый Codex JSON-RPC вызов ограничен `codexRpcTimeoutSeconds` (по умолчанию 30 секунд). Ошибка запуска App Server, закрытие stdin или зависший RPC завершают конкретное ожидание ошибкой вместо бесконечной блокировки Telegram polling.
- Перед запуском `Agent Hub Server` проверяет только локальные HTTP MCP из пользовательского `config.toml`. Недоступные порты отключаются аргументами лишь для запускаемого им экземпляра Codex App Server, поэтому не создают повторяющиеся fatal-записи и не меняют глобальную конфигурацию. На следующем безопасном перезапуске проверка выполняется заново, и уже запущенные MCP снова подключаются.
- При обрыве Telegram polling бот продолжает работу локальных ходов и повторяет `getUpdates` с ограниченной задержкой `3 → 6 → 12 → 24 → 30` секунд. После первого успешного запроса задержка сбрасывается; при долгом обрыве одинаковые ошибки журналируются разреженно.
- Служебный `answerCallbackQuery` выполняется в фоне с коротким таймаутом: временная потеря сети не отменяет уже выбранное действие и не выдаётся за ошибку переключения задачи. Если `/status` не может отправить графическую шапку, бот повторяет ответ обычным текстовым сообщением.
- `telegramApiBaseUrl` применяется ко всем JSON- и multipart-запросам, загрузке файлов, изображениям и голосу — локальный Bot API server или прокси не обходится прямыми обращениями к `api.telegram.org`.
- Если новое состояние прогресса пришло во время уже выполняющегося `editMessageText`, оно помечается ожидающим и отправляется сразу после текущей правки, а не теряется до следующего события.
- Сессия Claude хранит свой фактический `cwd` отдельно от корня разрешённого проекта. При `--resume` Agent Hub повторно читает каталог из transcript, проверяет, что он остаётся внутри проекта, и запускает CLI именно там; поэтому задачи из вложенных папок не теряются после выбора в общем каталоге. Ошибки Claude разбираются одновременно из финального JSON, stream-событий и сохранённого `stderr`, даже при ненулевом коде процесса. Для `rate_limit_event` бот показывает настоящую причину и время сброса вместо общего сообщения «завершился с кодом 1».
- Telegram offset сохраняется после обработки конкретного update. Если обработчик завершился ошибкой, полный update и причина сначала атомарно сохраняются в `data/failed-updates/`; только затем offset продвигается и пользователю отправляется диагностика. Если сохранить запись не удалось, offset не подтверждается. Штатный `/restart` запускает замену лишь после записи offset и runtime-state, поэтому новая копия не обрабатывает повторно саму команду рестарта.
- Пока управляемый Telegram-ход выполняется, бот обновляет отдельную progress-карточку. После терминального события точный `threadId + turnId` атомарно сохраняется в ledger журнала, а затем ставятся в durable outbox Markdown-проекция и, только для Telegram-хода, обычный полный финальный ответ. Ledger имеет резервную копию, восстанавливается после повреждения основного JSON и хранит `projectRoot`, поэтому один проект не может попасть в журнал другого. Ошибка Markdown-проекции не теряет ход: проекция повторяется при следующем запуске. Если внешний ход остановился во время остановленного Hub, потоковый terminal-аудит дочитывает событие с сохранённой позиции и уточняет ту же запись поздним настоящим terminal-событием. Только после надёжного сохранения финала progress-карточка удаляется.
- Ключ каждого ручного подтверждения — неповторимый UUID, привязанный к точному Telegram chat/message и активному run. Кнопки до рестарта честно протухают и не могут разрешить уже другую операцию. Меню, меняющие текущую задачу, проект, агента, модель или режим, содержат отпечаток контекста; старая кнопка не архивирует и не перенастраивает задачу, выбранную позднее.
- Привязки Telegram-сообщений записываются независимыми append-only событиями в `data/telegram-thread-bindings.d`. Параллельные `agent-hub-server.mjs`, `send-message.mjs` и `send-images.mjs` больше не перезаписывают общий JSON друг у друга; прежний `telegram-thread-bindings.json` читается как совместимый базовый слой. После 500 событий журнал под межпроцессной блокировкой атомарно сворачивается в базовый JSON, поэтому каталог не растёт бесконечно и конкурентная запись во время компактации не теряется.
- При штатной остановке очищаются индикатор набора, таймеры очереди, прогресса и наблюдения; незавершённые очереди и запуски остаются в состоянии для восстановления после старта. Отложенные сообщения одной задачи всегда запускаются по `createdAt`: более новое сообщение не обходит ни старую очередь, ни старую запись, требующую решения. На время фактической передачи запись получает состояние `dispatching`, исчезает из блока ожидания и после создания точного run переводит сохранённую квитанцию в `accepted`; временный обрыв Codex App Server повторяет тот же первый элемент с задержкой, а не запускает следующий.
- Изображения, голосовые и запросы озвучивания до фиксации Telegram offset атомарно сохраняются отдельными работами в `data/background-jobs/`. Ограниченные FIFO-очереди восстанавливаются после аварийного завершения процесса, сохраняют исходную задачу, модель и режим и удаляют запись после обработки. Отложенные пользовательские сообщения имеют TTL `deferredInputTtlHours` (по умолчанию 168 часов); после него временные файлы и старая кнопка очищаются предсказуемо. Внешние API не имеют общего ключа идемпотентности, поэтому гарантия — at-least-once: потеря принятой работы закрыта, но при падении точно между внешним действием и локальной отметкой его завершения редкий повтор теоретически возможен.
- Потенциально медленные команды просмотра `/status`, `/tasks`, перелистывание списка и `/diff` выполняются в отдельной ограниченной очереди с параллелизмом два. Они не задерживают приём следующей команды, в частности `/cancel`; изменяющие задачу callbacks остаются в основном последовательном контуре, чтобы сохранить порядок мутаций состояния.
- Каждый финальный ответ до закрытия run сначала сохраняется отдельными атомарными файлами в `data/delivery-outbox/`; уведомления из `send-message.mjs` попадают туда при временной сетевой ошибке. Для медиа-карточки при ошибке загрузки используется текстовый fallback. Очередь безопасно принимает сообщения от параллельных процессов Codex/Claude, переживает рестарт, сохраняет порядок частей одного ответа, заменяет устаревший недоставленный progress и повторяет доставку с экспоненциальной задержкой, учитывая Telegram `Retry-After`. Отложенная или временно ошибочная группа не блокирует готовые сообщения других задач, повреждённый файл изолируется с суффиксом `.invalid-*`, а окончательно отвергнутый Telegram-запрос сохраняется как `.failed-*` для диагностики вместо удаления ответа. Служебные действия (`typing`, callback-ответы и редактирование старого прогресса) намеренно не ставятся в очередь. При сетевом таймауте Telegram не поддерживает ключ идемпотентности, поэтому редкий повтор уже принятого сервером сообщения технически возможен.
- `agent-hub.log` и `agent-hub-error.log` ротируются внутри процесса. По умолчанию каждый файл ограничен 5 МБ и хранится до пяти архивов; лимиты задаются через `logMaxBytes` и `logMaxFiles`.

### Озвучка

- Последние 100 текстов, связанных с кнопками `🔊 Озвучить`, сохраняются в `data/speech-texts.json`. Кнопки новых сообщений продолжают работать после рестарта бота.
- Silero TTS использует один worker последовательно до `ttsIdleTimeoutSeconds`, поэтому модель не загружается заново при каждом нажатии. Python обрабатывает stdin в основном потоке без фонового reader-потока, конфликтующего на Windows с `torch.package`; idle-timeout контролирует Node-клиент. Таймаут или повреждение канала останавливают всё дерево worker; следующий запрос запускает чистый процесс. Старые кнопки, созданные до появления постоянного хранилища, восстановить невозможно.

### Настройки интерфейса и доступа

Панель быстрых действий отправляется как постоянная `ReplyKeyboardMarkup`. Обычные ответы без собственных inline-кнопок повторно прикрепляют её, чтобы Telegram Desktop восстанавливал панель после локального скрытия. Если клиент всё же не показывает значок клавиатуры, синяя системная кнопка `Меню` содержит первой команду `⌨️ Показать кнопки` (`/menu`); она заново отправляет панель. Это обход клиентского ограничения Telegram: `is_persistent` является запросом к приложению, а не принудительной блокировкой скрытия.

- `showTaskProject` управляет префиксом проекта в `/tasks`, когда включена кнопка проекта; если `showProjectButton` или `showTaskProject` равен `false`, список остаётся компактным.
- `guardConcurrentRepositoryWrites` по умолчанию равен `false`: разные задачи могут параллельно изменять один Git-репозиторий. Значение `true` включает предупреждение и требует явного подтверждения перед запуском второй задачи в том же Git-корне.
- `autoApproveOnStart` включает автоматические подтверждения после каждого запуска. Для Codex автоматически принимаются запросы команд, файловых изменений, дополнительных разрешений и безопасно заполняемые MCP-формы разрешений; произвольные формы ввода не автозаполняются. Для Claude используется `bypassPermissions`. В публичном примере значение оставлено `false`.
- `codexRpcTimeoutSeconds` ограничивает ожидание ответа локального Codex App Server; значение по умолчанию — 30 секунд.
- Выбранные проект, агент, задача, модели, Reasoning и режим Plan/Work сохраняются между перезапусками.
- В итоговой статистике Codex используются официальные credits per 1M tokens для конкретной модели: `GPT-5.6 Sol` и `GPT-5.5` — `125 / 12,5 / 750`, `GPT-5.6 Terra` и `GPT-5.4` — `62,5 / 6,25 / 375`, `GPT-5.6 Luna` — `25 / 2,5 / 150`, `GPT-5.4 mini` — `18,75 / 1,875 / 113` для входа / кэша / выхода. Reasoning входит в output. Fast умножает расход `GPT-5.6` и `GPT-5.5` на `2,5`, `GPT-5.4` — на `2`; Spark по принятому локальному правилу учитывается как `0 cr`. Для каждой категории выводится её доля от точной общей суммы; округлённые доли всегда складываются ровно в 100%.
- `cr` — общая межпровайдерная единица расчётного расхода: `1 cr = $0,04` API-эквивалента. Для Claude итоговый `total_cost_usd`, который Claude CLI рассчитывает по всему ходу вместе с субагентами, умножается на `25`; если общего итога нет, Agent Hub суммирует доступный `modelUsage[*].costUSD`, а для внешних и исторических транскриптов рассчитывает стоимость по официальным API-тарифам модели и категориям токенов. Учитываются cache write 5m (`1,25×`), cache write 1h (`2×`), cache read (`0,1×`), Fast и US-only inference; для Sonnet 5 применяется вводная цена `$2/$10` за MTok до 31 августа 2026 и `$3/$15` после. Это API-эквивалент, а не фактический счёт подписки Anthropic. Старые несопоставимые `кТЭ` не используются; неизвестная модель остаётся без выдуманной оценки.
- Единица расхода переключается глобально между `$`, `₽`, `cr` и `ПТЭ`. `ПТЭ` — приведённые токен-эквиваленты: `1 cr = 8 000 ПТЭ`; коэффициенты модели и Fast уже входят в credits. Доллары и рубли не сокращаются до `k/M`: до одной денежной единицы показываются два знака после запятой, начиная с одной — один, разряды разделяются пробелами. Рубли рассчитываются через долларовый API-эквивалент (`25 cr = $1`) и официальный курс USD/RUB Банка России. Agent Hub обновляет курс при запуске без блокировки запуска сервера и сохраняет последнее успешное значение в `data/exchange-rates.json`; при временной недоступности источника используется кэш.

### Codex models

`/model` switches the Codex model used for the next `turn/start` request. `/reasoning` selects the reasoning effort, and `/mode` selects `Work` (`default`) or `Plan` (`plan`). The Reasoning and Plan/Work buttons are in the second menu row. The selected values are saved in `data/state.json` and sent explicitly with every Codex turn, including turns in resumed tasks. Defaults are configured in `config.json`:

On Windows, the bot prefers the newest Codex binary bundled with the VS Code extension. Set `codexExecutable` or `CODEX_EXECUTABLE` only if you need to force a specific CLI path.

```json
{
  "codexExecutable": "",
  "codexModel": "gpt-5.6-sol",
  "codexReasoningEffort": "high",
  "codexCollaborationMode": "default",
  "codexRolloutContext": {
    "enabled": false,
    "keepRecentImages": 4,
    "minReclaimBytes": 1048576,
    "scanIntervalSeconds": 900,
    "maxFilesPerPass": 8
  },
  "logMaxBytes": 5242880,
  "logMaxFiles": 5,
  "deliveryRetryIntervalSeconds": 15,
  "codexModels": [
    { "value": "gpt-5.5", "label": "GPT-5.5" },
    { "value": "gpt-5.6-sol", "label": "GPT-5.6-Sol" },
    { "value": "gpt-5.6-terra", "label": "GPT-5.6-Terra" },
    { "value": "gpt-5.6-luna", "label": "GPT-5.6-Luna" },
    { "value": "gpt-5.4", "label": "GPT-5.4" },
    { "value": "gpt-5.4-mini", "label": "GPT-5.4-Mini" },
    { "value": "gpt-5.3-codex-spark", "label": "GPT-5.3-Codex-Spark" }
  ]
}
```

For Claude Code, `/model` still switches `sonnet`, `opus`, or `haiku`.

### Claude Code (опционально)

Codex остаётся провайдером по умолчанию. Чтобы использовать Claude Code, сначала установите и авторизуйте CLI, затем укажите:

```json
{
  "provider": "claude",
  "claudeExecutable": "claude",
  "claudeModel": "sonnet",
  "claudePermissionMode": "acceptEdits"
}
```

Либо запустите установщик с `python install.py --provider claude`. Провайдер также переопределяется переменной `AI_PROVIDER`, путь к CLI — `CLAUDE_EXECUTABLE`, модель — `CLAUDE_MODEL`. При стандартном значении `claude` в Windows Agent Hub на каждом старте выбирает самый новый установленный native binary из расширений Claude Code для VSCode и глобального npm-пакета; поэтому обновление расширения автоматически выравнивает версию. Явный путь или `claudeExecutableArgs` всегда отключает автопоиск и используется без подмены.

Claude запускается в headless-режиме с `stream-json` и сохраняет `session_id` сразу после события инициализации; продолжение доступно через `/resume <ID>`. Поскольку CLI не предоставляет отдельный машиночитаемый реестр сессий, `/tasks` безопасно индексирует локальные transcript-файлы `~/.claude/projects`, отбрасывает subagent-сессии и служебные command-only сессии (`/usage` и подобные), затем оставляет только задачи из разрешённых папок. Для названий HUB сначала использует пользовательский `custom-title` из `/rename`, затем автоматически сгенерированный `ai-title`, а пользовательский запрос служит запасным вариантом. Возобновление запускается из исходного корня сессии, даже если последние действия Claude выполнялись во вложенном каталоге. `/status` получает актуальные лимиты через встроенную команду Claude Code `/usage`, не обращаясь к модели. Режим `acceptEdits` разрешает правки в рабочей папке, но не произвольные команды. Telegram-кнопка автоподтверждения включает `bypassPermissions` и должна использоваться лишь в доверенной рабочей папке. По умолчанию автоматический режим сбрасывается после перезапуска; постоянное включение задаётся локальным параметром `"autoApproveOnStart": true`.

### Несколько рабочих папок

Добавьте разрешённые папки в `projects`. Значение `projectRoot` задаёт папку по умолчанию и должно совпадать с одним из путей:

```json
{
  "projectRoot": "C:\\Projects\\Main",
  "projects": [
    { "name": "Основной", "path": "C:\\Projects\\Main" },
    { "name": "Сайт", "path": "C:\\Projects\\Website" }
  ]
}
```

Если `projects` отсутствует, бот продолжает работать с единственным `projectRoot`. В Telegram используйте `/projects` или кнопку «📁 Проект». Кнопка показывается по умолчанию; чтобы скрыть её, установите `"showProjectButton": false` — команда `/projects` продолжит работать. Имя проекта перед названием задачи в `/tasks` показывается только вместе с кнопкой проекта; `"showTaskProject": false` позволяет отдельно скрыть этот префикс. При переключении проекта создаётся новая выбранная задача, а уже запущенные задачи в других проектах продолжают выполняться.

## Безопасность

- Доступ проверяется одновременно по `allowedUserIds` и `allowedChatIds`.
- По умолчанию принимаются сообщения только из приватных чатов.
- Codex работает с `workspaceWrite`, без сетевого доступа для команд агента.
- Claude Code использует собственную систему разрешений; рекомендуемый режим — `acceptEdits`.
- Подтверждения команд, изменений файлов и дополнительных профилей разрешений отправляются владельцу в Telegram.
- Автоподтверждение после запуска определяется локальной настройкой `autoApproveOnStart`; безопасное значение в примере — `false`.
- Не публикуйте внешний `config.json`, каталоги runtime-`data`, окружения моделей и логи.

Бот предоставляет удалённый доступ к Codex и папкам из `projects` (либо к `projectRoot` в однопроектной конфигурации). Не добавляйте недоверенных пользователей в разрешённый список. Текущая версия не предназначена для совместного использования одного процесса несколькими людьми: состояние Codex и активная задача общие.

`npm run test:e2e` выполняет полностью локальную CLI-приёмку настоящего `agent-hub-server.mjs` через fake Telegram Bot API, Codex App Server и Claude CLI. Рабочий бот, токен, задачи и `data` не затрагиваются. Полное покрытие сценариев перечислено в [E2E_TEST_MATRIX.md](E2E_TEST_MATRIX.md). `telegramApiBaseUrl`, `codexExecutableArgs`, `claudeExecutableArgs` и `progressStartDelayMs` служат безопасными точками подмены для стенда; производственные значения по умолчанию остаются прежними. На Windows процессные ожидания автоматически получают двукратный запас для нестабильного времени запуска дочерних процессов; это не меняет проверяемые лимиты отзывчивости. Для диагностики медленной машины множитель можно переопределить через `TELEGRAM_E2E_TIMEOUT_MULTIPLIER`.

Telegram сразу показывает `typing`, а содержательная progress-карточка по умолчанию появляется через 500 мс после безопасной проверки активности и Git-снимка. Проверка внешней активности и конфликта репозитория выполняется параллельно; лишний `thread/resume` перед каждым ходом удалён, а восстановление незагруженного треда остаётся в retry-маршруте `turn/start`. `/status` получает каталог и лимиты параллельно, держит лимиты в минутном кэше и после первой загрузки каждого баннера повторно использует Telegram `file_id`. Обработка update дольше двух секунд записывает в лог отдельные времена handler/state и возраст доставки, чтобы задержку Telegram не путать с задержкой приложения. Итоговый ответ сначала сохраняется в durable-outbox и отправляется немедленным flush; заменяемая progress-карточка остаётся видимой до подтверждённой доставки последней части финала.

`npm run check` одним процессом синтаксически разбирает все `.mjs` модули без их исполнения. `npm test` проверяет модули функционально, а `npm run test:e2e` — жизненный цикл отдельного процесса бота.

Текущий план выделения компонентов из исторически выросшего `agent-hub-server.mjs`, границы этапов и критерий завершения описаны в [AGENT_HUB_MODULES.md](AGENT_HUB_MODULES.md). Стабилизационные исправления и архитектурная декомпозиция учитываются раздельно в [STABILIZATION_CHECKLIST.md](STABILIZATION_CHECKLIST.md).

## Совместимость после переименования

Исходники и пользовательские названия используют `Agent Hub`, `Agent Hub Server`, `Agent Hub Desktop`, каталог `AgentHub` и точку входа `agent-hub-server.mjs`. Сокращённый владелец хода в карточках — `HUB`.

Внешний runtime Agent Hub находится в `%LOCALAPPDATA%\AgentHub`. Управляющие named pipe, переменные окружения и точки запуска используют единый префикс `Agent Hub`.

Основная декомпозиция выполнена. Telegram Bot API обслуживают `TelegramClient` и `TelegramPollingController`; входящие сообщения и callback-кнопки разбирают `TelegramMessageController` и `TelegramCallbackController`; подтверждения принадлежат `ApprovalController`, список и история задач — `task-picker.mjs` и `TaskViewController`, изображения/голос/TTS — `MediaController`. Жизненный цикл хода разделён между фабриками `task-runs.mjs`, `TaskProgressController`, `TaskObserverController`, `DeferredInputController` и политикой `task-recovery.mjs`. Desktop-снимок, история, маршрутизация RPC и отправка сообщений разделены между `desktop-snapshot.mjs`, `desktop-task-history.mjs`, `desktop-control-router.mjs` и `desktop-message-controller.mjs`. `agent-hub-server.mjs` связывает эти компоненты с прикладными правилами Codex/Claude и persistent runtime-state; оставшиеся безопасные границы и критерии дальнейшего разделения зафиксированы в [AGENT_HUB_MODULES.md](AGENT_HUB_MODULES.md).

Низкоуровневый Codex App Server transport вынесен в `codex-app-server-transport.mjs`: модуль владеет дочерним процессом, JSON-RPC request/response, таймаутами, разбором событий, остановкой дерева и коротким ограниченным кэшем `thread/read`. `agent-hub-server.mjs` получает уже разобранные события и определяет прикладную политику переподключения и восстановления конкретных задач.

Lifecycle Claude CLI вынесен в `claude-run-controller.mjs`: контроллер запускает detached-процесс, ведёт файлы потока, читает `stream-json` с сохранённого офсета, завершает или отменяет дерево и подключается к ходу после рестарта. Смысловая реакция на события, progress и доставка ответа остаются в композиции бота.

Lifecycle progress-карточки вынесен в `task-progress-controller.mjs`: модуль владеет отложенным созданием, последовательными edit, heartbeat-активностью, повтором временных ошибок, удалением старых bindings и финальным закрытием карточки. Формат текста и фактический Telegram transport передаются ему как зависимости.

Polling уже подключённого внешнего или восстанавливаемого хода вынесен в `task-observer-controller.mjs`. Контроллер управляет таймером и переходами `active/completed/unknown/error`, а после каждого асинхронного чтения повторно проверяет, что run всё ещё актуален; поэтому поздний snapshot не применяется к завершённой или переключённой задаче.

`npm run doctor` не ограничивается поиском файлов: он проверяет Telegram Bot API через `getMe`, запускает изолированный Codex App Server и выполняет `initialize + thread/list`, а также проверяет авторизованную сессию Claude через `/usage`. Все live-probes имеют таймаут и не создают новых задач.

В Windows также доступны `start.ps1` и `install-autostart.ps1`. После активации они направляют запуск во внешний runtime; PowerShell используется только как launcher и для интеграции с автозапуском Windows, сам бот работает в Node.js.

Команды: `/agent`, `/model`, `/reasoning`, `/mode`, `/projects`, `/new`, `/tasks`, `/resume`, `/rename`, `/archive`, `/current`, `/thread`, `/status`, `/approvals`, `/restart`, `/diff`, `/cancel`, `/help`. Старое имя `/engine` сохранено как совместимый псевдоним.

`/archive` архивирует текущую задачу Codex и автоматически выбирает первую оставшуюся задачу из списка. Та же команда доступна кнопкой `❌ Архивировать текущую задачу` в конце `/tasks`. При архивации через кнопку исходное меню обновляется на месте: архивированная задача исчезает, а автоматически выбранная помечается как текущая.

При обычном выборе задачи Codex или Claude через `/tasks` бот сразу переключает локальный адрес агента, проекта и thread/session, а дорогое `thread/resume` выполняет только перед фактическим обращением к Codex. Удаление списка и отправка уведомления выполняются параллельно. Если выбрана другая задача, бот присылает то же форматированное уведомление `Текущая задача изменена`, что и при переходе по ответу на привязанное сообщение. Повторный выбор текущей задачи через список, карточку статуса или `/resume <ID>` присылает уведомление `Текущая задача уже выбрана` с кнопкой показа последнего сообщения.

`/thread` показывает ID выбранного потока. Откройте активную папку в Codex App или VS Code и выберите этот поток в истории; из CLI его можно продолжить командой `codex resume <ID>`. Telegram сам не запускает второй turn в занятом потоке. Если VS Code всё же создаёт несколько параллельных turns одного треда, локальный rollout-индекс хранит их тексты раздельно по настоящему `turn_id`; карточка остаётся закреплена за наблюдаемым turn, показывает общее число активных turns и не закрывается при завершении соседнего.

## Голосовые сообщения

Голос распознаётся локально через `faster-whisper`. Модель выбирается параметром `whisperModel`; файлы модели и временные аудиофайлы не попадают в Git.

Для каждого непустого итогового ответа бот по умолчанию показывает кнопку `🔊 Озвучить`. Синтез выполняется локально через Silero TTS, а результат отправляется как Telegram voice message в OGG Opus. Запросы выполняются последовательно через ограниченную и сохраняемую на диск очередь максимум из десяти работ: повторные нажатия не создают неограниченное число одновременных синтезов, а принятый запрос переживает рестарт процесса. Один worker обслуживает последовательные запросы и держит модель загруженной до `ttsIdleTimeoutSeconds`; после штатного idle-exit следующий запрос создаёт новый процесс. Worker сообщает о принятии запроса, загрузке модели, начале и завершении каждого фрагмента и кодировании результата. Если текущий этап не даёт прогресса дольше `ttsRequestTimeoutSeconds` (по умолчанию 60 секунд), всё дерево зависшего worker принудительно останавливается; следующий запрос получает чистый процесс. Поэтому длинное исправно обрабатываемое сообщение не обрывается через 60 секунд от начала синтеза. Последние 100 текстов кнопок сохраняются в `data/speech-texts.json`, поэтому новые кнопки переживают рестарт. Модель, голос, idle timeout, минимальная длина обычного ответа и максимальный объём озвучиваемого текста задаются параметрами `ttsModel`, `ttsSpeaker`, `ttsIdleTimeoutSeconds`, `ttsButtonMinChars` и `ttsMaxChars`; значение `ttsButtonMinChars` по умолчанию равно `1`. При первом озвучивании Silero скачивает модель во внешний runtime-кэш `data/models/silero`.

Команда `npm run tts:smoke` проходит тот же Node → Python → Silero → OGG тракт без отправки в Telegram, проверяет непустой результат и удаляет диагностический файл.

Процессный E2E отдельно проверяет пользовательский путь от callback кнопки до multipart-вызова `sendVoice`, освобождение очереди после зависшего worker и однократную доставку принятой озвучки после аварийного рестарта бота.

Если пользователь отвечает на сообщение Telegram через «Ответить», бот добавляет текст или подпись цитируемого сообщения в запрос как отдельную цитату. Команды `/...` при этом продолжают распознаваться по самому новому сообщению.

### Пакеты пересланных сообщений

Первая пересылка — текст, фотография, изображение-документ или альбом — не запускает ход немедленно, а открывает сохраняемый черновик для выбранной в этот момент задачи. Следующие пересылки, изображения и обычные сообщения пользователя добавляются в ту же пачку; одна компактная карточка показывает количество реплик и изображений и предлагает `✅ Отправить пачку`, `↩️ Убрать последнее` или `🗑 Отменить`. Telegram передаёт альбом как несколько обновлений с общим `media_group_id`; Agent Hub сохраняет их отдельными упорядоченными элементами одной пачки. Таймер автоматической отправки намеренно не используется: Telegram не сообщает боту, что пользователь закончил пересылать переписку или дописывать собственный комментарий.

При отправке Agent Hub формирует один запрос в исходном порядке. Пересланные реплики помечаются как `Переслано · <автор>`, а собственные дополнения — как `Вы`. Для современного `forward_origin` и совместимых legacy-полей сохраняются доступные Telegram имя пользователя, скрытое имя, канал или чат; если источник не раскрыт, явно указывается `источник скрыт`. Текст, скопированный вручную вместо функции Telegram «Переслать», технической отметки источника не имеет и считается собственным сообщением пользователя.

Черновик закреплён за исходной задачей, моделью и режимом, сохраняется в `state.json` и переживает рестарт Agent Hub. Изображения загружаются долговечной фоновой очередью, не блокируют обработку Telegram-команд и передаются агенту только вместе с пачкой. До завершения загрузки кнопка отправки не запускает ход; при ошибке следующее нажатие повторяет загрузку. `Убрать последнее`, отмена и истечение срока черновика удаляют уже загруженные временные файлы. Если к моменту отправки задача уже занята, вся пачка вместе со всеми изображениями становится одним сохранённым входом с обычным выбором очереди, а не набором независимых сообщений.

## Изображения

Бот принимает Telegram-фотографии и файлы с MIME-типом `image/*`. Одиночное непересланное изображение вне открытой пачки по-прежнему запускает самостоятельный запрос: подпись используется как запрос, а без подписи Codex анализирует картинку с учётом предыдущей переписки. Пересланные изображения и любые изображения при уже открытой пачке обрабатываются по правилам раздела выше. Загрузка изображений и распознавание голоса выполняются вне последовательного цикла Telegram-обновлений: долгий файл не блокирует команды и переключение, а будущий ход остаётся закреплён за задачей, моделью и режимом, выбранными в момент получения. Общая сохраняемая FIFO-очередь обрабатывает один медиафайл за раз и принимает максимум 20 работ, поэтому серия голосовых не запускает параллельно несколько тяжёлых Whisper-процессов и не теряется при аварийном рестарте бота. Временный файл удаляется после завершения задачи.
