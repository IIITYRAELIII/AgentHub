# Проверка готового runtime перед публикацией

Это отдельный этап проверки Windows RuntimeHost и замены процесса. Он не
пересобирает релиз, не обновляет dev-контур и не обращается к production control.

После единственной сборки кандидата, до установки его в production:

```powershell
node test-contour.mjs accept-release --artifact <candidate-release-directory> --previous-artifact <previous-release-directory> --json
```

Каталоги должны содержать готовые `runtime-manifest.json` и файлы артефакта.
Кандидат должен содержать поддержку persistent acceptance environment в
RuntimeHost. Старый артефакт может предшествовать этой поддержке: оба поколения
запускает launcher кандидата, как после установки нового stable launcher.

Каждый запуск создаёт новый каталог `AgentHub-TestContour/release-acceptance/run-*`.
Опциональный `--output-root` выбирает другой родительский каталог вне исходников,
production и входных артефактов. Файл `acceptance-manifest.json` содержит хеши
обоих manifests, PID/identity готовых runtime, наблюдение живых старого и нового
процессов, статус очистки, проверенные и исключённые сценарии. Runtime-процессы
после проверки останавливаются; доказательства и изолированные данные остаются.

Очистка сначала закрывает постоянный запрет новых запусков в этом root и
завершает его Windows Job Object. Launcher регистрируется в нём до проверки
артефакта и появления `bot.lock`, поэтому независимый WMI-процесс также
попадает под очистку. Общий mutex сериализует регистрацию/запуск с закрытием;
запоздалый launcher после закрытия не запустит Node. Поле `cleanup.launchFenceClosed`
фиксирует успешное закрытие; ошибка закрытия делает весь acceptance неуспешным.
Capability кандидата обязана содержать `cleanupFence: 1`.

В синтетическом профиле перед перезапуском локальный Telegram-двойник отправляет один `/new` и ждёт
канонического подтверждения и точной привязки синтетического Stream/Thread.
Это также поддерживает старый артефакт, где перезапуск из окна Hub использует
выбор Telegram; после выхода таких артефактов из поддерживаемой миграции
подготовку можно перевести на команду окна Hub. Production-команды не повторяются.

Опциональный `--recording-input <input.json>` выбирает отдельный recording-профиль:
вход содержит `captureManifestFile`, `sourceConfig:{projectRoot,projects}` и
необязательные `attachmentRoots`. Существующий владелец подготовки создаёт свежий
`prepared-*` root из неизменяемого raw capture. Исходный контур не копируется и не
останавливается. Marker v2 связывает четыре SHA256 и точные root/profile;
RuntimeHost с capability `recordingProfile:1` проверяет их при каждом независимом
запуске. Используется сохранённый Stream/Thread без `/new` или replay. Активная
команда может удерживать штатный restart barrier; harness не завершает её
принудительно и не выдаёт ожидание за успешную замену. Подробности и границы —
в [recording-контуре](recording-contour.md).

Отметка тестового интерфейса добавляется в staging до вычисления manifest.
После фиксации хешей файлы релиза неизменяемы. Старые артефакты, в которых отметка
добавлялась после manifest, не проходят acceptance; проверка не игнорирует
расхождение даже у `index.html`.

Явный отказ control RPC немедленно завершает проверку и сохраняется в manifest.
Транспортный тайм-аут остаётся неоднозначным и проверяется по readiness.
При ошибке код выхода ненулевой, manifest сохраняет причину. Отсутствие
наблюдения одновременных процессов означает непроверенный сценарий, даже если
кандидат затем ответил ready. Не повторять неоднозначный restart RPC вручную.

После успеха продвигайте **тот же артефакт**, сопоставив
`artifacts.candidate.manifestSha256`, и снова проверяйте hashes при установке.
Повторная сборка создаёт другой артефакт и требует нового acceptance.

`scope: windows-runtime-replacement`, `status: passed` подтверждают только
указанный lifecycle. `productionParity: false` пока остаётся обязательным:
синтетический профиль не проверяет captured cohort, а recording-профиль отдельно
фиксирует его подготовку. Восстановление принятых очередей/outbox, преднамеренно
сломанный кандидат и реальные сетевые маршруты этим этапом не доказаны.
Внешние Telegram/provider вызовы заменены
локальными; фоновые внутренние механизмы самого runtime работают штатно.

Команда не добавляется автоматически в `test:all`: её применяют к готовому
кандидату по явному решению о проверке, с отдельным учётом времени.
