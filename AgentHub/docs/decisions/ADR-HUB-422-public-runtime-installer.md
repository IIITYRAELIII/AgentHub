# Public package installation from the release pipeline

## Status and scope

The principal update consumer is an active Codex turn inside the running Hub.
Public package intake returns an addressed `yield_current_turn` acknowledgement
after durable admission. The agent must finish that turn, allowing the existing
restart controller to drain the managed cohort. The public CLI preserves this
acknowledgement as its final JSON output and same-original readback repeats it
only for an exact known pending package binding. It does not poll Ready while
holding its own active turn. Native Host remains the independent continuation
owner. The isolated `whole_update.mjs` inside-hub scenario uses a real managed
provider Job, public CLI, canonical maintenance store and native backup/install/
launch with controlled external providers and download peers. Actual recipient
and production delivery remain separately observed outcomes.

Implementation in progress in HUB-422. The separately reviewed queue component
ends at SOURCE b284 and CURRENT 6b483. These additional common-installer changes
have their own pending execution and review boundary.

The user requires local production installation from the release pipeline to use
the same versioned public install_release.py and published package as participants.
Root selected this route for the accepted queue correction. The existing source
deployment compatibility CLI remains a distinct historical mechanism. There is
no additional source-only or partial-Task publication admission in this change.

## Authorization and target order

New normal local Hub release admissions record public-package-v1 in their
immutable authorization. The RM supplies a separately approved GitHub package
target for the same repository. Missing or foreign target authority refuses at
the existing intake owner. Public targets execute before local installation
regardless of identifier sorting, without changing the original authorization.
Historical originals retain their recorded protocol, target authority and tool
executor on replay. Publication-only targets retain their existing path.
Before any first target worker for the new policy, the existing pinned tool
must expose the matching installer handoff capability. An incompatible executor
refuses before creating a runner pin or public package effects, so compatibility
can be corrected before that generation has admitted an executor.

The selected tool root and digest remain explicit inputs of the actual release
executor. Its durable runner binds tool name, version and digest. The existing
package replacement inherits the old runtime environment. During a bootstrap
cutover with a different installed tool pin, the original-compatible source API
caller continues that same original with its explicit pin through terminal
completion. Root owns the separate installed-environment handoff. This preserves
the existing executor compatibility boundary across the public installer.

## Pending installation boundary

The existing artifact adapter prepares the original immutable runtime once. A
typed public-runtime-installer-handoff-v1 binds original operation, generation,
candidate and target. The INSTALL step records waiting and preserves its completed
prefix in the existing checkpoint. It gains no completed label or fingerprint.
Both changed and full publication entry points return the addressed handoff
before readiness verification, state publication or finalization, releasing the
outer publication lock.

The Hub-owned continuation then invokes the versioned public installer outside
that lock. Its dispatch intent and exact input belong to the existing publication
journal. Live updates retain the existing package maintenance original and native
handoff owner. A lost reply reads those same originals and bindings. Neither an
absent reply nor a partial filesystem body grants another launch. The child is
joined and the existing owner retains an explicit pending or unknown outcome.
The release can resume its exact remaining stages after verified installation
and readiness, using the same frozen source, public version and artifact build.

The consumer reads the canonical applied public target, its original result and
GitHub journal, and its PACKAGED/PREPARED identities. Fresh canonical repository,
tag, release and complete asset digests precede dispatch. It copies only the
verified public installer into a physically bound external scratch directory.
The public CLI uses the exact version and archive digest. Live update uses one
stable package maintenance ID derived from the release binding. Its dispatch
intent precedes spawn under the installation lease, which ends before child join.
Inherited publication/restart ownership is cleared for that independent child.
Missing or unreadable originals after dispatch remain UNKNOWN without another
launch. A successful maintenance original must retain the exact old current,
physical runtime/data owner and admitted public asset identities.
Canonical requested, blocked or running consumer state prevents another
publication worker. Readback observes that same consumer until its terminal
outcome permits remaining stages, while UNKNOWN still requires its own evidence.

Stopped installation uses the same public CLI. The existing cold-start owner
then starts the installed Host, with a durable intent in the same publication
journal. A lost start reply permits Ready readback, without repeating the start.
An existing private config remains byte-preserved. A first installation can pass
the same public --project-root option to initialize a nonempty selected project
through the configuration owner. This changes no provider or account choices.

Alias paths to one physical publication lock reuse only a live owning lease.
Directory identity supplements logical path equality, and delegated stages still
verify the original owner token, process identity and session. A foreign physical
lock, expired async lease or forged delegation retains the existing refusal.

## Consumer proof

Public package availability precedes local consumption. The same approved target
and frozen runtime receipt bind the published assets and installer. Installation,
download integrity and rollback use the public recipient interfaces and existing
runtime owners. Config, selected project, data and history remain under their
existing owners. First-run readiness requires a valid selected project through
that configuration owner, while established installations retain their settings.

An applied Git revision or generic publication-state record alone cannot prove
this local consumer. Active publication readback must bind the public input,
exact installer and artifact, its original maintenance outcome, actual current
manifest and expected running Ready instance. Unknown or failed maintenance
remains explicit and never restarts automatically under a new identity. Stored
historical completed effects retain their original attribution after later releases.
