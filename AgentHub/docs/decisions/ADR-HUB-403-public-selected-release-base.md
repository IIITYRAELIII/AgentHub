# ADR-HUB-403: Separate operational source from PUBLIC composition

The user requires PUBLIC releases to contain published code plus all exact
accepted Await results. A reviewed private repair installed as an operational
prerequisite does not grant release membership. Actual captured preparation
selected three results but used the whole installed private source as its base;
all three were reported contained and the private changes survived in PreRelease.

Keep the existing installed-local-source provenance and verification owner.
Its optional `compositionBaseCommit` is valid only when it equals the exact
published baseline, including the existing exact OWN Git-publication proof when
that original has already advanced Git before full delivery (ADR-HUB-329). The
same receipt/membership/origin proof is freshly rederived; a field alone grants
no such authority. Retained source commit/tree/patch, installed release/manifest,
original agreed main and selection pins remain distinct and fully checked.
The PUBLIC producer sets this field after verifying installation and source.
The ordinary no-carry native envelope uses the same published composition pin
without relabelling agreed main. Explicit reviewed-main authority stays separate.

Prepare through existing native selected-result composition from that published
pin. Installed objects can be fetched as verification inputs, never merged or
used as PUBLIC history/metadata allowances. Exact selected Task boundaries,
adoptions, origin, source, primary, lease, CAS and conflict review remain enforced.
No installed bytes or private work are deleted or rolled back by this choice.

Old provenance remains parseable as historical/operational evidence, including
native Test. A legacy installed-carry candidate cannot become a new PUBLIC
generation, reviewed-main recovery or frozen publication. The existing ordinary
Await/preparation owner rebuilds it; release capture never silently recomposes
Task branches. Old receipts, effects, manifests and journals remain under their
original identities. Once old prepared candidates retire, only their historical
readback needs the legacy shape. No API, registry, ledger, source overlay,
publisher, runtime cutover or additional release engine is introduced.

Validation uses actual Git preparation with published P, installed private I and
three selected results: the former candidate contains an unselected repair;
the corrected candidate retains P and each selected result, excludes that repair,
and leaves the installation untouched. Substitution, stale selection/publication,
legacy carry, source and late current-state changes must fail before acceptance.
