# ADR-HUB-385: preserve historical captures without recertifying results

Status: prospective correction; managed source and current operational review
are required before applying it to accumulated captures.

## Failure and owning boundary

An old completed native capture can have an automatic merge that preserves all
original objects and files while today's forced agreed-base content replay
demands a duplicate suffix. Archive creation succeeds, but current result
certification leaves the admitted storage child UNKNOWN before any deletion.
Repeating the intake or replacing that child would not fix this distinction.

The native retention owner already holds terminal Task evidence, a complete
inventory, the full immutable binding and the deterministic archive intent.
Storage preservation consumes those authorities. It must neither manufacture
fresh result acceptance nor relax the native graph/review proof.

## Decision

The existing native core exposes its complete graph/review traversal separately.
The ordinary result verifier calls that same traversal and then its unchanged
selected-content check. Current Test/Await, publication and historical Task
result certification keep their full behavior.

Only the existing archive verifier called with an admitted SAME storage original
may use the preservation route. It checks kind, owner, scope, candidate and
entire binding; successful deterministic archive intent; state and inventory;
the plain single-link canonical integration record's raw hash and identity;
exact staging path, journal hash and canonical completed Task evidence. The
original before/result/head commits and exact target tree must be preserved.
The complete graph/parent/automatic-entry/existing-review traversal remains
mandatory. Original row revision and raw record hash are checked again.

Archive math and the final archive verification/native batch use the existing
object-store lease. All original objects, separate tag anchors and raw files
remain subject to the full archive checks. Task/process/installation custody,
fresh owner guards, sealed deletion and SAME-original partial/lost-reply
recovery remain unchanged. No new command, ledger, public option, boolean
waiver, review capability, archive identity or deletion sink is introduced.

This is a distinction between storage preservation and result certification,
not a fallback that accepts an otherwise invalid result. An unreviewed graph,
unknown/foreign original, changed raw integration or incomplete archive still
retains the source. The ordinary verifier must reject the same duplicate replay
both before and after storage retirement.

## Observable evidence

Two owning cases use actual Git, SQLite, TaskGit and the Windows sealed native
boundary. Mapped line-equivalence data produces a real automatic Git merge and
a conflicting current certification expectation without copying repository
history or dependencies. The parent remains UNKNOWN at SAME-original recovery;
the correction finishes retirement with the same successful archive and keeps
all original objects/raw records. A distinct unreviewed graph stays UNKNOWN with
zero native effects. Foreign original/binding and raw-record drift also refuse.

Fixture allocation and logical batch counters are not production savings.
Actual cleanup needs a separately reviewed current-bound consumer and physical
AFTER accounting including the complete pool, proofs and new validation bodies.
