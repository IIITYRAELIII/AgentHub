# ADR-0114 — Owned restart and terminal failure delivery

Status: accepted for the explicit focused recovery requested on 2026-10-16.

The prior Windows restart submitted WMI launches, waited only 15 seconds for a lock, retried twice and finally used a direct fallback. A WMI-created host was outside the helper tree being cleaned up. Two delayed replacements reached the instance channel after the old runtime had already restored ownership. Historical logs do not isolate WMI and manifest durations, so that missing attribution remains unknown. The input factory also omitted isRestartPending: its coordinator default admitted a postrestart continuation into the runtime being stopped. Failed recovery then retained lifecycle ownership as a misleading running projection; the failure notice expired before the user reconnected.

Use one directly owned RuntimeHost process per durable restart. Its legacy --spawn-independent alias now runs the host synchronously and propagates its Node exit instead of submitting WMI. Ownership wait covers actual launcher/manifest/startup time (120 seconds), with no retry/fallback after a timeout; exact cleanup precedes rollback. The existing restart operation persists intended release before launch, rejects completion by a different release, and the instance lock binds restart operation identity. Existing command tracing pairs quiesce/save/drain/close/release/launcher-to-lock/lock-to-ready under the original operation ID. Telemetry never changes lifecycle outcomes.

The factory passes the reservation to actual input admission. Retained unproven provider activity remains an admission fence and exact Stop target but is presented as unknown; exact active observations clear it. No new ledger, lane, expiry or terminal evidence is introduced. The latest persisted failed restart remains visible until a later successful restart; elapsed time no longer counts as notice delivery. Public health exposes only terminal operation identity/status/time, without its error text. This lets the startup overlay exit its failed wait while authenticated snapshots retain the precise reason.

The existing local immutable runtime preparation/installation and safe restart remain the delivery owners. Preserve the earlier accepted repair as the base and rollback. A continuation may be sent through native Hub only after existing publication readiness proves the intended release against ready lock and responding process identity. A failed or unknown wait cannot enqueue that continuation or authorize a kill/cold start. No new review gate, full suite or provider/browser probe is part of this incident correction.
