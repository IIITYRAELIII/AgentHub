# ADR-0114 — Owned restart and terminal failure delivery

Status: accepted for the explicit focused recovery requested on 2026-10-16.

The prior Windows restart submitted WMI launches, waited only 15 seconds for a lock, retried twice and finally used a direct fallback. A WMI-created host was outside the helper tree being cleaned up. Two delayed replacements reached the instance channel after the old runtime had already restored ownership. Historical logs do not isolate WMI and manifest durations, so that missing attribution remains unknown. The input factory also omitted isRestartPending: its coordinator default admitted a postrestart continuation into the runtime being stopped. Failed recovery then retained lifecycle ownership as a misleading running projection; the failure notice expired before the user reconnected.

Use one directly owned, detached RuntimeHost process per durable restart. Ownership wait covers actual launcher/manifest/startup time (120 seconds), with no retry/fallback after a timeout; exact cleanup precedes rollback. The existing restart operation persists intended release before launch, rejects completion by a different release, and the instance lock binds restart operation identity. Existing command tracing pairs quiesce/save/drain/close/release/launcher-to-lock/lock-to-ready under the original operation ID. Telemetry never changes lifecycle outcomes.

The factory passes the reservation to actual input admission. Retained unproven provider activity remains an admission fence and exact Stop target but is presented as unknown; exact active observations clear it. No new ledger, lane, expiry or terminal evidence is introduced. The latest persisted failed restart remains visible until a later successful restart; elapsed time no longer counts as notice delivery. Public health exposes only terminal operation identity/status/time, without its error text. This lets the startup overlay exit its failed wait while authenticated snapshots retain the precise reason.

The existing local immutable runtime preparation/installation and safe restart remain the delivery owners. Preserve the earlier accepted repair as the base and rollback. A continuation may be sent through native Hub only after existing publication readiness proves the intended release against ready lock and responding process identity. A failed or unknown wait cannot enqueue that continuation or authorize a kill/cold start. No new review gate or full suite is part of this incident correction. The user subsequently authorized bounded live chat/turn/Stop acceptance and observing survival for more than five minutes after the old launcher exits.

The synchronous compatibility alias in the first repair was a regression: a cold start submitted inside a command parent's lifetime could die when that parent exited. A real compiled-host regression reproduces loss for an inherited synchronous launch, while the corrected cold and controlled paths survive parent exit. Historical OS termination events are absent, so this establishes the mechanism without claiming an exact unrecorded exit cause for both production deaths. Cold `--spawn-independent` now uses synchronous native CreateProcess with explicit job breakaway and no inherited handles, then returns the actual creation outcome. Denied breakaway is a visible failure, with no broker fallback or delayed WMI effect. It rejects a managed restart operation environment. Controlled restart continues using the direct detached owned host, never that cold-start command; failure cleanup still owns its complete tree. The cold path introduces no restart retry. Host entry, inherited job membership, host-to-Node identity and observed Node exit codes are recorded without payload or environment data.

The message ledger remains acceptance/dispatch authority. Desktop reads overlay only their bounded exact receipt IDs from that owner, including after terminal commit; the in-memory intake registry cannot mask a newer failed command. Terminal revision and timestamps cross the same snapshot and projection path, invalidate snapshot reuse and dominate delayed accepted/live updates. Labels distinguish saved, queue, launch, active, explicit provider retry, terminal and unknown; clocks display durations only and never infer outcomes. Only an exact structured provider `error` with `willRetry=true` reports a retry. A failed input is not replayed. Generic legacy failures retain their known failed status and direct the user to the detailed answer and an explicit manual submission, without guessing a historical network error code.


The authorized live Stop acceptance exposed an exact Codex `turn/completed` with `turn.status=interrupted`. The terminal commit and command reconciliation now use the existing provider terminal normalizer (`aborted` → command `cancelled`); a Stop request ACK alone remains insufficient. Terminal status is retained in durable and in-memory last-message projections and passed into history merge. A text-only legacy last answer cannot overwrite an existing aborted/failed history outcome with completed. No historical SQL/terminal rewrite or provider replay is introduced. Regression drives the observed event shape through actual completion, SQLite terminal/command stores, last-message projection and history/reload.

A registry-bound visible run also supersedes stale catalog activity uncertainty. Catalog-only runs retain the catalog unknown flag; actually unknown runs remain occupied and Stop-addressable. Status presentation cannot combine unknown and running labels.
